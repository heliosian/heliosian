Description: `POST /auth/login` checks only Google's double-submit cookie, so a page able to plant that cookie under `heliosian.com` could sign a member in as someone else, and `POST /auth/logout` is held from other sites only by the session cookie being `SameSite=Lax`.
Status: fixed
Severity: low
---
`logout` (`internal/auth/auth.go`, `logout`) sits behind `Wrap`, since `/auth/logout` is not in `auth.Public`, and so needs a session. The session cookie is set `SameSite=Lax` (`setSession`), which a browser does not send on a POST from another site, top-level or not; such a post reaches `Wrap` with no session and gets the login page, and `logout` never runs. Nothing but that attribute stood in the way, and a sign-out now ends every session the address holds, on every device, through `sessions.SignOut`.

`login` (`auth.go`, `login`) holds the exchange to the `g_csrf_token` cookie equalling the form field, and nothing else about where the post came from. Only a page under `heliosian.com` can set that cookie; the wildcard CNAME sends every name under it to our own Cloud Run service and development lives under `heliosiandev.com` (`production-cookies-reach-local-hostnames.md`), so planting it takes a page served from production itself. Could it be planted, the page would post its own Google credential for the victim, who would then be signed in as the attacker's school account, with their edits, uploads and questions landing there.

Fixed by `sameOrigin` in `internal/auth/auth.go`, which both `login` and `logout` call first: a post the browser does not mark `Sec-Fetch-Site: same-origin` or `none`, the header missing included, gets a 403 and no cookies. `TestSignInAndOutRefuseOtherSites` holds it, and `docs/dev.md` says so. The login page (`web/public/common/login.js`) uses Google's button in its default popup mode with a `login_uri`, where Google's script on the page posts the form, so the post is same-origin; the redirect mode would post from `accounts.google.com` and be refused.
