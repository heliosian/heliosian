# Development

## Principles

- **One static Go binary.** The server is Go, compiled to a static binary, running on Google Cloud Run. A new app joins the same binary at its own hostname rather than deploying as a new service; the only other production binary is the scheduled job in `cmd/periodicsync`.
- **Frameworkless client.** Client code is plain JavaScript with no client-side framework and no build step.
- **Great local development.** A single command runs the server locally, content changes show on a refresh without a restart, and fictional sample data makes it possible to develop and test without touching real community data.
- **Agent-friendly repository.** Most development happens through coding agents driven by community contributors. The repo is structured, documented and instrumented (screenshots, browser driving, load checks) so agents can build, verify and iterate without hand-holding.
- **Open source, minimal configurability.** The code is public and specific to Helios; it does not aim to be a generic configurable product. It contains no secrets, credentials or private community data.
- **Sheets and a bucket.** Structured data lives in Google Sheets and blobs (photos and other uploads) in Cloud Storage (`docs/storage.md`). The system of record for families and staff is Veracross, reaching the directory's sheet through `tools/import`; a direct integration replaces that when Veracross offers an API.

## Run

    go run ./tools/startserver

Every app answers at `https://<app>.heliosiandev.com:8080`, under the same label as its production hostname (override the port with `PORT`), clicking past the browser's warning about the self-signed certificate the first time. The dev server serves the fictional community in `sampledata/`, signs every request in as a sample parent, and answers every outside service the server calls in-process — no credentials or configuration. Run from a shell holding `tools/devenv`'s variables (Real data, below), the Maps browser and picture library keys put the real services, at their real cost, behind the map and the image picker. The sample server runs the production clients and starts `internal/intercept` for each host they reach, so their requests are answered on loopback:

- `api.anthropic.com` (`Claude`) answers a request carrying a JSON schema with a sample that fits it - Staff Birthdays' and Loop's descriptions, the key points - and a request offering tools, Helios Ask's, with a call of the first tool and then a canned answer a word at a time.
- `geocode.googleapis.com` (`Geocode`) places each address at a point hashed from it around Palo Alto, the same address always at the same point; `places.googleapis.com` (`Places`) suggests from a few made-up Bay Area addresses.
- `us-west1-aiplatform.googleapis.com` (`Vertex`) embeds each text as a hashed bag of its words, so a search finds passages sharing the question's words. The Vertex client logs in through Google's application-default credentials, so `GoogleLogin` writes an `authorized_user` credentials file under `local/google/`, points `GOOGLE_APPLICATION_CREDENTIALS` at it, and answers `oauth2.googleapis.com`'s token endpoint, and the client never reaches Google or a developer's own login.
- `api.mailgun.net` (Mail, below).

All sample-mode composition lives in `tools/startserver`; the production binary and the shared wiring in `internal/app` carry none of it. Templates and served files are read from disk on every request; edit a file and refresh. The sample CSVs back a fake spreadsheet that loads each tab on first read and keeps every write in memory, so `sampledata/` never changes on disk — restart to get the fixtures back. The sample HCA Meeting carries a sent guest list the sample parent co-hosts, with two people from outside the community on it; their `/ext/{token}` pages are reached by the Token column of `sampledata/calendar/Invites.csv`. The sample parent also co-hosts the Hawks and Falcons CAFE, an event the school's calendar brings, with a guest list not yet started.

## Hosts and files

One binary serves every app, and the hostname picks the app by convention: `<app>.heliosian.com` is production and `<app>.heliosiandev.com` is a developer's machine, so `who.heliosian.com` and `who.heliosiandev.com` both mean the directory. Home additionally answers as the bare and `www` domain, the volunteer portal (`team`) as `hca` on every tier, and any other host gets a 404 (`internal/app`). Each server answers one domain only - the deployed service `heliosian.com`, the dev server in every mode `heliosiandev.com` (`app.Domain` and `app.DevDomain`) - and its session and spoof cookies are scoped to that domain, so a production sign-in is never sent to a developer's names: nothing under `heliosian.com` resolves to loopback. Public DNS has to point `heliosiandev.com` and `*.heliosiandev.com` at loopback - `dig +short who.heliosiandev.com` answering `127.0.0.1`; the records live at the registrar (`docs/deploy.md`, Domain) - so that local development uses real hostnames with no hosts-file entry, and the OAuth client and Maps key can name them (Google refuses made-up domains such as `.localhost`).

## Local HTTPS

The dev server speaks HTTPS in every mode. Google sign-in only accepts a plain-HTTP login URI on `localhost` itself, and the dev hostname is a real name, so it has to be HTTPS. `internal/devtls` mints a self-signed certificate for `heliosiandev.com` and `*.heliosiandev.com` in memory every time the dev server starts; nothing is written to disk. Browsers warn about it; click through. Headless captures pass `--ignore-certificate-errors`; the capture browser needs the warning clicked once in its own profile. The production binary itself stays plain HTTP, because Cloud Run terminates TLS in front of it. The security headers every response carries, HSTS among them for production alone, are `secure` and `policy` in `internal/app`.

Within an app, a request resolves in this order: `web/public/<app>/<path>`, then `web/public/common/<path>`, served to anyone with no sign-in; on the portal, the `Redirects` tab, which sends an old address on with a `302` before sign-in (`model.ActivitiesRedirected`; `docs/team/team.md`, Redirects); then sign-in; then `web/<app>/<path>`, then `web/common/<path>`; then the app's routes. Public URLs are the file's own path, with no prefix: `/style.css`, `/brand/icon-192.png`, `/fonts/fonts.css`. The public tree holds exactly what a browser fetches without credentials and what the sign-in and no-access pages need: the manifest, icons, splash art, login art, fonts, the login page's script, the element helpers the outside invitation page shares with the apps (`elements.js`), and the no-access page (`web/public/common/no-access.html`) sign-in serves to anyone the directory does not list. Everything else, every page, script, style, image, and API, requires a session for someone the directory lists, but for what `auth.Public` names: the sign-in exchange and three prefixes. The sign-in exchange (`POST /auth/login`) and signing out (`POST /auth/logout`) answer only a post the browser marks `Sec-Fetch-Site: same-origin` or `none`, and refuse any other, or one unmarked, with a `403`, so a page elsewhere can neither sign someone out nor sign them in as another account. Sign-in makes both checks in one place (`auth.Wrap`, and the sample server's `auth.Fixed`), for every host and every request past the public paths, the app's own files included: a session says who someone is, and the directory says whether they are in; a spoofed request is checked as the person viewed as. An address the directory does not list - a family that opted out or never answered the consent form, someone who has left, an admin with no row of their own - gets the no-access page, or a bare `403` on `/api/` paths, on every host, with only signing out (`/auth/logout`) and the way to the consent form (`app.OptInPath`, registered on every host and handed to `auth.New` as the one path open to them, sending on to the Config sheet's address) still answering them. `/hooks/` is every callback the service asked another service for - the school calendar's watch at `/hooks/calendar`, the calendar's reply route at `/hooks/replies/mime` and its delivery events at `/hooks/events` (the bounces), Loop's mail route and delivery events at `/hooks/mail/mime` and `/hooks/events`, Helios Ask's forwarded school mail at its own `/hooks/mail/mime` - each checking its caller's secret; the mail routes end in `mime` because that is what makes Mailgun post the raw message in the call. `/open/` is every address the service hands out for something other than a signed-in browser to follow - the share cards chat apps fetch at `/open/share/`, the calendar's personal feeds at `/open/feed/`, Loop's unsubscribe links at `/open/unsubscribe/`, the calendar's routes for someone invited from outside at `/open/ext/`, its event pictures for that page at `/open/banner/` - each an address whose token is the whole of the check. `/ext/` is the calendar's page for that outside person, `/ext/{token}`, self-contained under `web/public/when/ext.html` since the app's own files sit behind sign-in (`docs/when/calendar.md`, Invitations).

## Real data

    eval "$(go run ./tools/devenv)"
    go run .

runs the production binary: the production spreadsheets, the media bucket (see `docs/who/data.md`), real geocoding, and Google sign-in, with no sample fallback — every input is required and the server refuses to start without one. `tools/devenv` prints every variable the dev server and the tools read, as shell exports: each spreadsheet id, found among the sheets the service account can see, each key, read from Secret Manager through the list in `internal/env`, the same list `tools/deploy` hands the service, and `SESSION_KEY` as a fixed local key of its own, so a session minted on a laptop is never good in production. Nothing reads a key from a file. The model loads at startup — the server refuses to start if the load fails — and reloads every five minutes. Real data never leaves the process: nothing is written to disk. The one exception is the dev tools that read the buckets - `go run ./tools/startserver --real`, the same assembly under the dev server, and `loadcheck`, `importartifacts` and `artifactsprobe` - which start `internal/devcache` before anything else: a proxy on loopback that every Google client in the process reaches `storage.googleapis.com` through, trusting a certificate authority minted in memory for the run. It keeps each object it reads under `local/cache/blobs/<bucket>/<object>` (gitignored, kept out of the image), with a `.meta` file of the response headers beside it, each landed whole, and answers the next read of that name from there, so a restart takes seconds rather than fetching every photo again. Every name in both buckets is written once, so a cached copy never goes stale; a delete through the proxy drops its copy, and metadata reads, writes and misses always reach the bucket. The server itself carries no cache. Delete the directory to start clean. Requirements:

- **Sign-in** — everything sits behind Google sign-in restricted to the school's Workspace domain. Signed out, an API or media path and a request the browser names as an asset - a stylesheet, script, image, font, manifest or worker, by `Sec-Fetch-Dest` (`assetDests` in `internal/auth`) - get a bare 401, since a browser keeps whatever an asset's address answered and would use the login page as that stylesheet or script again once signed in. Anything else gets the login page at the address asked for: a navigation, a chat app reading a link's preview with no destination named, a service worker fetching the page for its tab, which says `empty`, and a destination nobody has seen before. Nothing answered signed out may be stored (`Cache-Control: no-store`), and each such answer logs a `signed out` line with the path, whether it got the login page, and the three `Sec-Fetch` headers, for reading what a browser actually sent. Every page's API calls go through `api` in `web/common/api.js`: it sends a JSON or `FormData` body, returns the parsed answer (`null` for a 204), throws an `Error` carrying the server's text (with the parsed body as `conflict` when a refusal answers in JSON), and runs each response through `signedIn`, which reloads the page on a 401, landing on the login page and, once signed in, back where it was. Helios Ask's streamed chat reads its response itself and calls `signedIn` directly. The top bar's own requests (the badges in `alerts.js` and `shell.js`, the app switch's list, Spoof Mode) go through it too; any other failure there is kept by `noteError` (`web/common/feedback.js`) among the recent errors a problem report carries, and leaves the badge off, puts a `?` in the new-year count, or leaves the app switch listing Heliosian alone (`docs/toolbar.md`). The OAuth web client id is read from `GOOGLE_CLIENT_ID` and handed to the login page by `/auth/client`; the client's authorized JavaScript origins must include each app's development origin, port included (`docs/deploy.md`, OAuth, for where that list lives). The server issues its own HMAC-signed session cookie, keyed by the required `SESSION_KEY`: the address and the moment of issue, good for `sessionLength` (`internal/auth`) from then, and refused from the moment the address signs out, on any browser, since sign-out records the time in the Config sheet's `Signed Out` tab (`docs/config.md`). The session's length is the server's alone, so changing the constant, or a sign-out, takes effect on cookies already issued. Signing in sets the cookie for the domain and deletes the host-only copy, since a browser sends every copy of the name and the server reads the first, so a stale host-only one from before the cookie was scoped to the domain would otherwise shadow the session just set on that host alone.
- **The previous host's service worker** — the domains were hosted by Glide before, and browsers that visited then still hold its service worker, which catches page loads and fetches them itself and which a 404 for its script does not remove. `web/public/common/sw-prod-v4.js` sits at its script's address on every host, answering without a session whatever version its query names: a browser checking for an update installs it, and it deletes the origin's Cache Storage, which nothing of ours uses, unregisters itself and reloads the open tabs. It can go once nothing asks for it, which the request log shows:

      gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="heliosian" AND httpRequest.requestUrl:"sw-prod"' --project heliosian --freshness 30d --format "value(timestamp,httpRequest.requestUrl,httpRequest.status)"

- **Data access** — Google credentials come from application-default credentials impersonating the data service account, set up once per machine:

      gcloud auth application-default login --impersonate-service-account=directory@heliosian.iam.gserviceaccount.com

  This needs `roles/iam.serviceAccountTokenCreator` on that account for the person running it. What `directory@` itself needs - membership of the community shared drive for the sheets, project IAM for the buckets - and how to read whether it has each is `docs/deploy.md`, IAM; local processes then act as exactly the identity production runs as, with no key file anywhere (an org policy is meant to forbid creating one, and the same section says how to read it).
- **Mail** — every app sends through Mailgun in both modes. The sample server starts `internal/intercept` for `api.mailgun.net`, the same loopback proxy and in-memory certificate authority `internal/devcache` uses, answering each send itself: it writes the email as an `.html` file under `local/mail/`, its attachments beside it and a raw forward as an `.eml` (`tools/startserver/mailgun.go`); open one in a browser to see it. Real-data mode needs `MAILGUN_KEY` and refuses to start without it. Replies to Helios When's invites come back through a Mailgun route only in real-data mode with `MAILGUN_WEBHOOK_KEY` set too, and only if the route points at the server, which it does not on a laptop; the sample server's invites name `rsvp@reply.example.org` and nothing receives for it.
- **Image search** — the volunteer portal's image picker ("Find an image") searches Unsplash when `UNSPLASH_KEY` (an Unsplash API access key - a demo app's 50 requests an hour is plenty) is set, with the photographer credited on each tile and the photo's download endpoint pinged on import as Unsplash's terms ask; likewise Pexels (`PEXELS_KEY`) and Pixabay (`PIXABAY_KEY`, photos plus illustrations and vectors). Those three stock libraries are the whole of it. With none of the three keys the picker is not offered. A search asks every library with a key at once and answers one list, the libraries' answers interleaved, and the browser learns nothing of where a picture came from: each hit is an id of the server's own - a hash of the library and its id - with the app's own `images/thumb` route beside the search, a size and a title, and no credit, licence or library name. The library's addresses for the picture, its credit, licence and page are kept in `stock/<id>.json` in the media bucket, read by nothing but the thumbnail route and the import. A search answers as soon as the libraries have, then writes its records and fetches every thumbnail the bucket lacks in the background, `workers` at a time, into `stock/<id>-thumb`; the process's `imagesearch.Stock`, one for every app, remembers the records of every search made here, which thumbnails the bucket holds, and which are being fetched right now, so the thumbnail route serves what is there, waits for a fetch already under way, or fetches the one thing itself, and no thumbnail is fetched twice however many tiles ask at once. The import takes the id, fetches the full image once into `stock/<id>` and stores it content addressed like an upload. A picture is pulled from a library once however often it is searched for or picked. Every write to the bucket goes up in one request: the storage client otherwise allocates its whole default upload chunk, sixteen megabytes, for each write, which is what took the service past its memory limit when a search wrote seventy-two records at once. The libraries' hosts are named nowhere in the content security policy. Every search spends one call on each keyed library, so Unsplash's demo cap of fifty an hour is drawn down by every search; a library that fails or refuses is left out of that search's answer, logged as a warning, and the search fails only when every library does. Each app gets its upload, search, thumbnail and import routes from `imagesearch.Search.Register`, with the app's prefix and image folder and a gate: HCA-Team, Celebrate and Helios When pass `imagesearch.Members`, which admits everyone the sign-in admits, and Heliosian passes its admin check. One `imagesearch.Limits` for the whole process counts, by the signed-in address, searches and pictures added (uploads and imports together) over the last hour across every app, through two `internal/ratelimit` limiters, refusing with a 429 past `searchesPerHour` and `storesPerHour`; the service runs as one instance, so the count in memory is the whole count.
- **Feedback** — the toolbar's "Report a problem or idea" writes to the `Reports` tab of the `Feedback` sheet and mails the super admins, in either mode; sample mode's lands in the sample tab and beside the other sample mail. A super admin reads the queue in Heliosian's admin, edits what an issue should say and files it in `heliosian/heliosian` as a GitHub App, which needs `GITHUB_APP_ID` and `GITHUB_APP_KEY`, both required in real-data mode; without them - sample mode has none - the queue says filing is not set up and a report can only be dismissed (`docs/feedback.md`).
- **Claude** — a real-data server talks to Claude with the Anthropic key in `ANTHROPIC_API_KEY`, required, for Helios Ask, Staff Birthdays' charity sentences, Loop's email list descriptions and the key points of school mail; sample mode answers through its intercept instead (Run, above). Every real answer costs money.
- **Helios Ask** — its search over the community's documents embeds each question through Vertex AI as `directory@`, which the impersonated credentials above already are, and reads the documents from the `Artifacts` sheet and the media bucket (`docs/ask/artifacts.md`); sample mode files the fictional messages and page under `sampledata/artifacts/` at startup, embedding through its intercept of Vertex (Run, above).
- **Helios Loop's mail** — a real-data server forwards the posts to the groups through Mailgun with `MAILGUN_KEY`, and takes them in only with `MAILGUN_WEBHOOK_KEY` set too - and even then only if Mailgun's route points at it, which it does not on a laptop; without the webhook key the routes answer 404. Every message it does forward is kept in the mail bucket as `directory@`, which the impersonated credentials above act as (`docs/loop/data.md`, Mail). Sample mode receives nothing, and a forward, were one to run, lands as `.eml` files under `local/mail/` beside the other sample mail.
- **Maps** — a server key for the Geocoding API and the Places API (New) (`GOOGLE_MAPS_SERVER_KEY`; never rendered into pages, restrict by server IP or leave unrestricted for dev; both APIs enabled on the project and allowed for the key) and a browser key for the Maps JavaScript API (`GOOGLE_MAPS_BROWSER_KEY`; rendered into pages, restrict by HTTP referer). Geocoding results are cached per address in the directory spreadsheet's `Geocode` tab (see `docs/who/data.md`).

To capture authenticated real-data pages, launch the capture browser (`go run ./tools/capturebrowser`), sign in to the local server there once, and use `tools/browse` or `tools/screenshot --remote` — the session cookie lives in the capture profile.

## Writes

No direct writes, ever: every change to a sheet or a bucket goes through the storage layers in `docs/storage.md` - IO, the store's `Commit`, each app's model, and the hooks - and nothing reaches a sheet or an object any other way.

## The rules live with the thing

Who may see a thing, what it is called, where its page is, and what else changes when it changes are written once, in the package that owns the thing and beside its model, and every app that shows or reads it - its own pages, the calendar folding it in, Helios Ask - calls that one function rather than restating it, since a restated rule drifts from the one the owner's own pages keep. So:

- **Who sees it** - every rule takes an `access.Actor`: the signed-in address, the allowances they hold in the app that owns the thing, and their household from `model.Directory.Family`, which reaches a parent's family and nobody else's, so a student sees their family's things as a stranger would. An allowance is one named exception to a normal rule (`access.Named`), declared beside the rules in the owning package's `writes.go` or `<thing>_writes.go` - seeing what is pending or hidden, acting as a party's host, curating the calendar - and a rule asks for it with `actor.May`, never for adminship as such. Each app's admin list confers the set its package names `AdminAllowances` (Who?'s is `model.WhoAdminAllowances`, When's `model.CalendarAdminAllowances`, HCA-Team's `model.ActivitiesAdminAllowances` and Celebrate's `model.PartiesAdminAllowances`; the list's `Held`), the platform super admins being on every list; there is one kind of allowance, and `access.Grant` grants everything held, always. Every actor is built by `model.Directory.Actor` from a request, or `ActorOf` from an address, so the address is resolved through the directory's aliases and the household filled the same way in every app. Whether a thing reaches the viewer at all is `model.Activities.VisibleTo` (a thing and everything above it), `model.Party.VisibleTo`, `model.EmailList.VisibleTo` and `model.EmailList.MailReadableBy`, and `model.Birthdays.Sees`; the thing as they may see it, with what is withheld from them taken out, is `model.Activities.ActivityFor` (a private volunteer list), `model.Party.For` (a ticket's buyer, price and note), `model.EmailList.For` (its rules), `model.Calendar.EventsFor` and `ResponsesFor`, and `home.Cache.CategoriesFor`. The directory model itself holds only what members may see. Helios Ask builds one actor per app, each with that app's allowances, and shows exactly what the owner's function returns. A caller with no viewer - the calendar folding in what everyone sees, a signed-out link preview - asks with an empty `access.Actor{}`.
- **Who changes it** - every rule deciding who may change what is in its package's `writes.go`: functions that take the `access.Actor` first, check it against the model as it stands, and return the rows to write or a refusal (`access.Forbidden`, `Missing`, `Invalid`, which carry the HTTP status a handler answers with). Acting for someone else's sign-up, ticket or answer goes by the actor's household, the same parent-only one as reading, so a student acts only for themselves. A handler builds the actor, calls one of them and commits what it returns; it never builds a row. JSON handlers are `func(r *http.Request, body In) (Out, error)` registered through `serve.JSON`, which decodes the body, answers a refusal with its status and message (or its `Body` as JSON), any other error with a logged 500, `serve.None` with 204 and anything else as JSON. A model the store refuses to build after a write comes back as `access.Invalid`. Handlers that need the `ResponseWriter` - pages, images, feeds, uploads, webhooks - stay plain and use `serve.Decode`, `serve.Write` and `serve.Error`. Work nobody signed in does - an import, a mailer, a sweep - is `access.System` with its own name, and goes through `writes.go` the same way. `TestRowsAreBuiltBesideTheirRules` in `internal/access` refuses `store.Insert`, `Set`, `Update` or `Delete` in any file but a `writes.go` or `<thing>_writes.go`, or a `cache.go` or `<thing>_cache.go` for the store's cascades.
- **What it is called** - the directory's `familyNameFor` for a family's `name` and `shortName`.
- **Who is whose** - `model.Directory.Household` (everyone in a person's families but them), `Members` (one family's adults and students), `Parents` (a student's), `Children` (a parent's) and `FamilyOf` (a person's first family, the one `/my-family` opens): each resolves aliases, drops anyone the directory does not list, and names each person once. An app maps their answer into its own person type and never walks `Families` itself; only the loader, building those families, and Who?'s edit permission, which asks which families a person is an adult of, read `AdultEmails` and `KidEmails` directly.
- **Where its page is** - `model.PersonPath`, `model.FamilyPath`, `model.ClassroomPath`, `model.ListPath` and `model.TagPath`; `model.EventPath` and `model.EventPage`, which says which app a linked event's page is on; `model.EmailList.Path`; `model.Activities.PathOf` and `model.Parties.PathOf`. Only the host is the caller's.

A rule an app needs that its owner lacks is added to the owner, never kept by the app that needed it.

## Tests

Helpers more than one package's tests use live in `internal/testkit`, which only `_test.go` files import, so none of it reaches the binary. It is three packages because a package's own tests cannot import anything that imports that package: `testkit` itself imports nothing above `store`, `data` and `auth`, so every app's tests can use it - image checkers (`None`, `All`, `Only`, `Files`), `Call` for a signed-in request and `Form` for a signed-in form post, sheet reads that flush the write queue first (`Rows`, `Tables`, `ChangeLog`, `ChangeLines`), `MustTime`, and the link-preview checks `Previews` and `Cards`; `testkit/mailtest` holds the mail `Recorder` and `Discard`, each a real `*mail.Mailgun` whose sends one intercept of `api.mailgun.net` per test binary answers, a recorder's kept by its API key; `testkit/sample` builds the sample calendar cache on the real `model.Directory.Roster`, and so is for packages above `model`. Tests that reach an outside service install the sample server's intercept for its host (`intercept.Claude`, `Geocode`, `Places`, `Vertex` with `GoogleLogin` into `t.TempDir()`), or a handler of their own that counts or records, and talk to it through the real client.

## Tools

Each runs as `go run ./tools/<name>`, but for `periodicsync`, which production runs too and so lives at `go run ./cmd/periodicsync`. The sheet, drive, and bucket tools authenticate with the same impersonated application-default credentials as the server (see Real data).

- `screenshot`, `capturebrowser`, `browse`, `console` — page capture, browser driving, and a page's console output; see `docs/screenshots.md`
- `deploy` — apply the full production service configuration, add any domain mapping the service lacks, and configure the periodic sync job, finding the spreadsheet ids itself; see `docs/deploy.md`
- `startserver` — the dev server: sample data in the foreground by default, `--capture` for a one-command page screenshot, `--real` for the production assembly in the foreground with the objects it reads cached under `local/cache/blobs/` (Real data, above), and `--detach` to launch that in the background with its output in a log file (needs `SESSION_KEY` and every spreadsheet id; `cookie` mints a session to reach it with)
- `cookie` — print a signed session cookie for `--email`, required, for local API testing
- `askrun` — send Helios Ask's fixed list of fifty questions, each as a fresh chat, to a running real-data server (`--base`, the dev server's ask origin by default) with a session minted for `--email`, required, and write every answer with its lookups, rounds, tokens and time to one markdown file under `local/ask-runs/` (`--out`), for reading two runs side by side when the model changes; `--as` deals the questions out across the directory addresses named, through Spoof Mode, since one person gets `perHour` calls to Claude an hour (`docs/ask/data.md`) and fifty as one person would be refused past that (needs `SESSION_KEY`, the server's own; every question costs money)
- `loadcheck` — run every app's load pipeline against the live sheets, the calendar's and Helios Ask's documents included (read through the cache under `local/cache/blobs/`, Real data, above), and print a model summary or the first thing a loader refuses
- `devenv` — print every variable the dev server and the tools read as shell exports, for `eval` (Real data, above): the spreadsheet ids, found by the sheets' titles, with every other visible spreadsheet as a comment, the keys from Secret Manager and the local `SESSION_KEY`
- `sheets` — every direct operation on one spreadsheet, as `go run ./tools/sheets <command> --sheet <id>`, the command list printed when none is named: `create` creates an empty spreadsheet titled `--title` in the same shared-drive folder as `--sheet`, refusing a title already taken there, and prints its id; `tabs` lists the tabs with their sizes and header rows; `rows` prints one tab's rows (`--rows`/`--from` for a slice, `--cells` for each filled cell with its column index); `dump` / `write` copy one tab to a local CSV / write a local CSV into a tab, header-checked; `sync` brings a tab's cells in line with a local CSV by `--keycol`, never adding rows; `set` sets the `--col` cell of the rows whose `--keycol` holds `--key`, appending the row if none does; `delete` deletes the rows whose `--keycol` holds `--key`; `rename` renames a tab; `drop` deletes named columns, header and cells, for a column an app has stopped reading. `--keycol` always names the column that picks rows and has no default; `--col` only ever names a column written. Every command that changes a sheet (`write`, `sync`, `set`, `delete`, `rename`, `drop`) only reports what it would change without `--apply`, `drop` saying how many cells each column holds
- `darkcheck` — load pages in dark mode (`--url a,b,c`, `--click` into a window first) and read the rendered page for what dark mode missed: words with too little contrast against the ground they sit on, a tab strip painted a different colour from what it sits on, and with `--light` every light surface; `--compare` reads each page by day too and marks each finding dark only or by day too
- `createtabs` — create the tabs of every spreadsheet that has a layout with their header rows, adding missing columns to tabs that exist (needs each of those spreadsheets' id variables, and refuses a spreadsheet whose title isn't the layout the variable promised)
- `import` — run a fresh Veracross export and a fresh export of the school website's staff page, upload the portraits from both, and commit in one go, as `import`, the import tabs' changed rows, the overrides those imports have caught up with cleared and the `Name to Email` entries Veracross now has an address for dropped (`docs/who/data.md`, Every write is a commit), or report what that would change with `--dry-run`, which still runs both exports against the live sites (needs `DIRECTORY_SHEET`, `PREFERENCES_SHEET`, and `CONFIG_SHEET`, and `VCEXPORT` and `WEBEXPORT`, both required, naming a `vcexport` and a `webexport` checkout)
- `archivesite` — save every page the school website's sitemap names under `local/imports/site/`, less the pages `internal/artifacts` excludes, five seconds apart as the site's robots.txt asks (`docs/ask/artifacts.md`)
- `archivebrowser` — crawl a signed-in site through the capture browser from `--start`, following every link under `--prefix`, and save each page's `--selector` content and the Google Docs, Slides and Drive PDFs it links under `--out`; the portal goes to `local/imports/portal/` and HELP to `local/imports/help/`. Run it rarely, since the portal notices a reader who comes through too often (`docs/ask/artifacts.md`)
- `importartifacts` — read saved messages (`local/imports/mail/*.json`), saved website pages (`local/imports/site/*.json`) and saved browser resources (`local/imports/portal/*.json`, `local/imports/help/*.json`) into Helios Ask's documents: each to markdown, cut into chunks, embedded through Vertex AI, written to the media bucket and indexed in the `Artifacts` sheet. A message that went to none of the school-wide or class lists and an excluded page are refused, one already on file is skipped, and one rendered differently now is imported again with its old object dropped. `--dry-run` reports what a run would embed and writes nothing; naming one file prints its markdown; a run that writes refuses without `--i-have-user-permission-to-spend-money`. It loads the documents on file first, through the cache under `local/cache/blobs/` (Real data, above) (needs `ARTIFACTS_SHEET`; `docs/ask/artifacts.md`)
- `artifactsprobe` — load Helios Ask's documents from the live sheet and bucket the way the server does, reading through the same disk cache, then search them for the words given (`go run ./tools/artifactsprobe when is picture day`), printing the top passages with their scores, so retrieval can be judged without the app (needs `ARTIFACTS_SHEET`)
- `periodicsync` — the scheduled job, run by hand: it reads the school's published year calendar into the `Calendar` sheet and has Claude classify its entries, exiting non-zero if any part of that failed; the school's Google Calendar is the serving binary's to keep up with (`docs/when/data.md`). `--dry-run` reports what it would change, writing nothing to the sheets; either way it refuses to start without `--i-have-user-permission-to-spend-money`, since every run that reaches Claude costs real money and only the person paying says when (needs `CALENDAR_SHEET`, `DIRECTORY_SHEET`, `PREFERENCES_SHEET`, `CONFIG_SHEET`, an Anthropic API key in `ANTHROPIC_API_KEY`, the one the server requires (Real data, Claude, above), and poppler's `pdftoppm`, `brew install poppler`)
