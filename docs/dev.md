# Development

## Principles

- **One static Go binary.** The server is Go, compiled to a static binary, running on Google Cloud Run. A new app joins the same binary at its own hostname rather than deploying as a new service, and it is the only binary production runs.
- **Frameworkless client.** Client code is plain JavaScript with no client-side framework and no build step.
- **Great local development.** A single command runs the server locally, content changes show on a refresh without a restart, and fictional sample data makes it possible to develop and test without touching real community data.
- **Agent-friendly repository.** Most development happens through coding agents driven by community contributors. The repo is structured, documented and instrumented (screenshots, browser driving, load checks) so agents can build, verify and iterate without hand-holding.
- **Open source, minimal configurability.** The code is public and specific to Helios; it does not aim to be a generic configurable product. It contains no secrets, credentials or private community data.
- **Sheets and a bucket.** Structured data lives in Google Sheets and blobs (photos and other uploads) in Cloud Storage (`docs/storage.md`). The system of record for families and staff is Veracross, reaching the data model through `tools/import` (`docs/datamodel.md`, Veracross import); a direct integration replaces that when Veracross offers an API.

## Run

    go run ./tools/startserver

Every app answers at `https://<app>.heliosiandev.com:8080`, under the same label as its production hostname (override the port with `PORT`), clicking past the browser's warning about the self-signed certificate the first time. The dev server serves the fictional community in `sampledata/`, signs every request in as a sample parent, or as anyone the sample lists with `--email <address>`, and answers every outside service the server calls in-process — no credentials or configuration. Run from a shell holding `tools/devenv`'s variables (Real data, below), the Maps browser and picture library keys put the real services, at their real cost, behind the map and the image picker. The sample server runs the production clients and starts `internal/intercept` for each host they reach, so their requests are answered on loopback:

- `api.anthropic.com` (`Claude`) answers a request carrying a JSON schema with a sample that fits it - Staff Birthdays' and Loop's descriptions, the key points - and a request offering tools, Helios Ask's, with a call of the first tool and then a canned answer a word at a time.
- `geocode.googleapis.com` (`Geocode`) places each address at a point hashed from it around Palo Alto, the same address always at the same point; `places.googleapis.com` (`Places`) suggests from a few made-up Bay Area addresses.
- `us-west1-aiplatform.googleapis.com` (`Vertex`) embeds each text as a hashed bag of its words, so a search finds passages sharing the question's words. The Vertex client logs in through Google's application-default credentials, so `GoogleLogin` writes an `authorized_user` credentials file under `local/google/`, points `GOOGLE_APPLICATION_CREDENTIALS` at it, and answers `oauth2.googleapis.com`'s token endpoint, and the client never reaches Google or a developer's own login.
- `api.mailgun.net` (Mail, below).

All sample-mode composition lives in `tools/startserver`; the production binary and the shared wiring in `internal/app` carry none of it. Templates and served files are read from disk on every request; edit a file and refresh. The sample CSVs back a fake spreadsheet that loads each tab on first read and keeps every write in memory, so `sampledata/` never changes on disk — restart to get the fixtures back. Being local, it refreshes once as it starts rather than after production's deploy overlap, so the picture worker makes every `PHOTO` row's re-encode, crop and thumbnail from its original under `sampledata/bucket/photos/` within a few seconds, and the fixtures carry only originals. The data model's sample is a school of about a hundred people across every grade, classroom and crew, with staff in several departments, so every page of Who? has something to draw; its pictures are drawn faces and bird tiles, never photographs. A row keeps its ID once it has one, since tests and the iPhone app's recorded answers name rows by ID: a change adds rows rather than renumbering. The sample parent has children in two classrooms of two gradebands, a co-parent and a family photo, runs a tag of their own and shares another, and is on an email list; the sample also holds a student in two households, a staff member who is a parent and one with no family, a parent with no photo of their own whose family has one, so the family's picture stands in for them, a withheld family and a hidden person who never show, and families sharing a whole address, only a city, and no phone. The sample Fall Picnic (`/g/fall-picnic` on When) has a guest list the sample staff member hosts, with the sample parent on it, answered yes, and a guest they brought; nothing has been sent, so it shows pending to its host.

## Hosts and files

One binary serves every app, and the hostname picks the app by convention: `<app>.heliosian.com` is production and `<app>.heliosiandev.com` is a developer's machine, so `who.heliosian.com` and `who.heliosiandev.com` both mean the directory. Home additionally answers as the bare and `www` domain, the volunteer portal (`team`) as `hca` on every tier, and any other host gets a 404 (`internal/app`). Each server answers one domain only - the deployed service `heliosian.com`, the dev server in every mode `heliosiandev.com` (`app.Domain` and `app.DevDomain`) - and its session and spoof cookies are scoped to that domain, so a production sign-in is never sent to a developer's names: nothing under `heliosian.com` resolves to loopback. Public DNS has to point `heliosiandev.com` and `*.heliosiandev.com` at loopback - `dig +short who.heliosiandev.com` answering `127.0.0.1`; the records live at the registrar (`docs/deploy.md`, Domain) - so that local development uses real hostnames with no hosts-file entry, and the OAuth client and Maps key can name them (Google refuses made-up domains such as `.localhost`).

## Local HTTPS

The dev server speaks HTTPS in every mode. Google sign-in only accepts a plain-HTTP login URI on `localhost` itself, and the dev hostname is a real name, so it has to be HTTPS. `internal/devtls` mints a self-signed certificate for `heliosiandev.com` and `*.heliosiandev.com` in memory every time the dev server starts; nothing is written to disk. Browsers warn about it; click through. Headless captures pass `--ignore-certificate-errors`; the capture browser needs the warning clicked once in its own profile. The production binary itself stays plain HTTP, because Cloud Run terminates TLS in front of it. The security headers every response carries, HSTS among them for production alone, are `secure` and `policy` in `internal/app`.

Within an app, a request resolves in this order: `web/public/<app>/<path>`, then `web/public/common/<path>`, served to anyone with no sign-in; on the portal, its old addresses, sent on with a `301` or `302` before sign-in (`ActivityPages.Redirected` in `internal/db/redirects.go`; `docs/team/team.md`, Redirects); then sign-in; then `web/<app>/<path>`, then `web/common/<path>`; then the app's routes. Public URLs are the file's own path, with no prefix: `/style.css`, `/brand/icon-192.png`, `/fonts/fonts.css`. The public tree holds exactly what a browser fetches without credentials and what the sign-in and no-access pages need: the manifest, icons, splash art, login art, fonts, the login page's script, the element helpers the outside invitation page shares with the apps (`elements.js`), and the no-access page (`web/public/common/no-access.html`) sign-in serves to anyone the directory does not list. Everything else, every page, script, style, image, and API, requires a session for someone the directory lists, but for what `auth.Public` names: the sign-in exchange, three prefixes, and the paths an MCP client reaches without a cookie. The sign-in exchange (`POST /auth/login`) and signing out (`POST /auth/logout`) answer only a post the browser marks `Sec-Fetch-Site: same-origin` or `none`, and refuse any other, or one unmarked, with a `403`, so a page elsewhere can neither sign someone out nor sign them in as another account. The sign-in page is served at whatever address was asked for, and its script posts to `/auth/login?next=` that address, which sign-in sends the browser back to once it is a path on the same host (`returnPath` in `internal/auth/auth.go`), and to `/` otherwise. Sign-in makes both checks in one place (`auth.Wrap`, and the sample server's `auth.Fixed`), for every host and every request past the public paths, the app's own files included: a session says who someone is, and the data model says whether they are in: the address must be a `PERSON_EMAIL` of a person the consent step shows who is neither `hidden` nor `deactivated`, and never a guest's address - a guest reaches only their invitation's `/ext/` page, by its token, and no app, API or MCP (`TestGuestsNeverSignIn`) (`db.Model.SignedIn`, wired as `Core.SignedIn` in `internal/app/wiring.go`; `docs/datamodel.md`); a spoofed request is checked as the person viewed as. An address that fails - a family that opted out or never answered the consent form, someone who has left, someone hidden, an address on no person - gets the no-access page, or a bare `403` on `/api/` paths, on every host, with only signing out (`/auth/logout`) and the way to the consent form (`app.OptInPath`, registered on every host and handed to `auth.New` as the one path open to them, sending on to the `platform` setting `Helios Who Opt-In URL`) still answering them. `/hooks/` is every callback the service asked another service for - the school calendar's watch at `/hooks/calendar`, the calendar's reply route at `/hooks/replies/mime`, Loop's mail route at `/hooks/mail/mime`, the delivery events of both their sending domains at `/hooks/events` on each host, Helios Ask's forwarded school mail at its own `/hooks/mail/mime` - each checking its caller's secret; the mail routes end in `mime` because that is what makes Mailgun post the raw message in the call. `/open/` is every address the service hands out for something other than a signed-in browser to follow - the share cards chat apps fetch at `/open/share/` - drawn, with the page's link preview, for every event, party and activity by its ID, slug or alias, whoever may see it and whatever its status, since a card that refuses is a link that cannot be shared - the calendar's personal feeds at `/open/feed/`, Loop's unsubscribe links at `/open/unsubscribe/`, the calendar's routes for someone invited from outside at `/open/ext/`, the invitation's flyer among them - each an address whose token is the whole of the check. `/ext/` is the calendar's page for that outside person, `/ext/{token}`, self-contained under `web/public/when/ext.html` since the app's own files sit behind sign-in (`docs/when/calendar.md`, Invitations). The MCP client's paths are everything under `/.well-known/`, `/oauth/register`, `/oauth/token`, and the MCP endpoint at `/mcp` and as a `POST` to `/`, which checks a bearer token of its own; only Helios MCP's host routes them, so on any other host they are a 404 or a 405 (`docs/mcp/mcp.md`).

It stays fictional — real community data never goes here. `sampledata/directory/Website Staff Import.csv` covers what the staff page layer has to resolve: a bio an override outranks, a title Veracross outranks, an entry with no address matched by name through `Name to Email`, another matched by name against the staff import, an entry under a second address resolved through `Email Aliases`, and entries matching nobody — a vendor the directory drops, and a staff member added by hand, whom the layer runs too early to see. `sampledata/preferences/` is the consent form's response sheet, exercising every combination the loader has to resolve: both permissions, each alone, neither, a family that never answered, a staff member's own opt-out, a superseded submission, and a two-household student whose parents answered differently.

## Real data

    eval "$(go run ./tools/devenv)"
    go run .

runs the production binary: the production spreadsheets, the media bucket (`docs/storage.md`), real geocoding, and Google sign-in, with no sample fallback — every input is required and the server refuses to start without one. `tools/devenv` prints every variable the dev server and the tools read, as shell exports: each spreadsheet id, found among the sheets the service account can see, each key, read from Secret Manager through the list in `internal/env`, the same list `tools/deploy` hands the service, and `SESSION_KEY` as a fixed local key of its own, so a session minted on a laptop is never good in production. Nothing reads a key from a file. The model loads at startup — the server refuses to start if the load fails — and reloads every `refreshInterval` (`internal/store/store.go`). The dev tools that read the buckets - `go run ./tools/startserver --real`, the same assembly under the dev server, `--snapshot` (Snapshot, below) and the one-offs under `local/` that read the bucket - start `internal/devcache` before anything else: a proxy on loopback that every Google client in the process reaches `storage.googleapis.com` through, trusting a certificate authority minted in memory for the run. It keeps each object it reads under `local/cache/blobs/<bucket>/<object>` (gitignored, kept out of the image), with a `.meta` file of the response headers beside it, each landed whole, and answers the next read of that name from there, so a restart takes seconds rather than fetching every photo again. Every name in both buckets is written once, so a cached copy never goes stale; a delete through the proxy drops its copy, and metadata reads, writes and misses always reach the bucket. The server itself carries no cache. Delete the directory to start clean. Requirements:

- **Sign-in** — everything sits behind Google sign-in restricted to the school's Workspace domain. Signed out, an API or media path and a request the browser names as an asset - a stylesheet, script, image, font, manifest or worker, by `Sec-Fetch-Dest` (`assetDests` in `internal/auth`) - get a bare 401, since a browser keeps whatever an asset's address answered and would use the login page as that stylesheet or script again once signed in. Anything else gets the login page at the address asked for: a navigation, a chat app reading a link's preview with no destination named, a service worker fetching the page for its tab, which says `empty`, and a destination nobody has seen before. Nothing answered signed out may be stored (`Cache-Control: no-store`), and each such answer logs a `signed out` line with the path, whether it got the login page, and the three `Sec-Fetch` headers, for reading what a browser actually sent. Every page's API calls go through `api` in `web/common/api.js`: it sends a JSON or `FormData` body, returns the parsed answer (`null` for a 204), throws an `Error` carrying the server's text (with the parsed body as `conflict` when a refusal answers in JSON), and runs each response through `signedIn`, which reloads the page on a 401, landing on the login page and, once signed in, back where it was. Helios Ask's streamed chat reads its response itself and calls `signedIn` directly. The top bar's own requests (the badges in `alerts.js` and `shell.js`, the app switch's list, Spoof Mode) go through it too; any other failure there is kept by `noteError` (`web/common/feedback.js`) among the recent errors a problem report carries, and leaves the badge off, puts a `?` in the new-year count, or leaves the app switch listing Heliosian alone (`docs/toolbar.md`). The OAuth web client id is read from `GOOGLE_CLIENT_ID` and handed to the login page by `/auth/client`; the client's authorized JavaScript origins must include each app's development origin, port included (`docs/deploy.md`, OAuth, for where that list lives). The server issues its own HMAC-signed session cookie, keyed by the required `SESSION_KEY`: the address and the moment of issue, good for `sessionLength` (`internal/auth`) from then, and refused from the moment the address signs out, on any browser, since sign-out records the time as the person's `PERSON.signed_out` (`docs/datamodel.md`, Server jobs). The session's length is the server's alone, so changing the constant, or a sign-out, takes effect on cookies already issued. Signing in sets the cookie for the domain, and signing out deletes it there.
- **The previous host's service worker** — the domains were hosted by Glide before, and browsers that visited then still hold its service worker, which catches page loads and fetches them itself and which a 404 for its script does not remove. `web/public/common/sw-prod-v4.js` sits at its script's address on every host, answering without a session whatever version its query names: a browser checking for an update installs it, and it deletes the origin's Cache Storage, which nothing of ours uses, unregisters itself and reloads the open tabs. It can go once nothing asks for it, which the request log shows:

      gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="heliosian" AND httpRequest.requestUrl:"sw-prod"' --project heliosian --freshness 30d --format "value(timestamp,httpRequest.requestUrl,httpRequest.status)"

- **Data access** — Google credentials come from application-default credentials impersonating the data service account, set up once per machine:

      gcloud auth application-default login --impersonate-service-account=directory@heliosian.iam.gserviceaccount.com

  This needs `roles/iam.serviceAccountTokenCreator` on that account for the person running it. What `directory@` itself needs - membership of the community shared drive for the sheets, project IAM for the buckets - and how to read whether it has each is `docs/deploy.md`, IAM; local processes then act as exactly the identity production runs as, with no key file anywhere (an org policy is meant to forbid creating one, and the same section says how to read it).
- **Mail** — nothing sends mail but production on Cloud Run. Every app sends through Mailgun, and anywhere else - the sample server, `--snapshot`, and real-data mode alike - `internal/intercept` answers `api.mailgun.net` itself, the same loopback proxy and in-memory certificate authority `internal/devcache` uses: it writes each email as an `.html` file under `local/mail/`, its attachments beside it and a raw forward as an `.eml` (`intercept.Mail`), and sends nothing; open one in a browser to see it. Real-data mode installs it in `app.Production` whenever `K_SERVICE` is unset, as it leaves the workers that write data unstarted, so a write made there records its mail as sent without anyone getting it. Real-data mode still needs `MAILGUN_KEY` and refuses to start without it. Replies to Helios When's invites come back through a Mailgun route only in real-data mode with `MAILGUN_WEBHOOK_KEY` set too, and only if the route points at the server, which it does not on a laptop; the sample server's invites name `rsvp@reply.example.org` and nothing receives for it.
- **Image search** — the volunteer portal's image picker ("Find an image") searches Unsplash when `UNSPLASH_KEY` (an Unsplash API access key - a demo app's 50 requests an hour is plenty) is set, with the photographer credited on each tile and the photo's download endpoint pinged on import as Unsplash's terms ask; likewise Pexels (`PEXELS_KEY`) and Pixabay (`PIXABAY_KEY`, photos plus illustrations and vectors). Those three stock libraries are the whole of it. With none of the three keys the picker is not offered. A search asks every library with a key at once and answers one list, the libraries' answers interleaved, and the browser learns nothing of where a picture came from: each hit is an id of the server's own - a hash of the library and its id - with the app's own `images/thumb` route beside the search, a size and a title, and no credit, licence or library name. The library's addresses for the picture, its credit, licence and page are kept in `stock/<id>.json` in the media bucket, read by nothing but the thumbnail route and the import. A search answers as soon as the libraries have, then writes its records and fetches every thumbnail the bucket lacks in the background, `workers` at a time, into `stock/<id>-thumb`; the process's `imagesearch.Stock`, one for every app, remembers the records of every search made here, which thumbnails the bucket holds, and which are being fetched right now, so the thumbnail route serves what is there, waits for a fetch already under way, or fetches the one thing itself, and no thumbnail is fetched twice however many tiles ask at once. The import takes the id, fetches the full image once into `stock/<id>` and stores it content addressed like an upload. A picture is pulled from a library once however often it is searched for or picked. Every write to the bucket goes up in one request: the storage client otherwise allocates its whole default upload chunk, sixteen megabytes, for each write, which is what took the service past its memory limit when a search wrote seventy-two records at once. The libraries' hosts are named nowhere in the content security policy. Every search spends one call on each keyed library, so Unsplash's demo cap of fifty an hour is drawn down by every search; a library that fails or refuses is left out of that search's answer, logged as a warning, and the search fails only when every library does. Each app gets its upload, search, thumbnail and import routes from `imagesearch.Search.Register`, with the app's prefix and image folder and a gate: every app passes `imagesearch.Members`, which admits everyone the sign-in admits. One `imagesearch.Limits` for the whole process counts, by the signed-in address, searches and pictures added (uploads and imports together) over the last hour across every app, through two `internal/ratelimit` limiters, refusing with a 429 past `searchesPerHour` and `storesPerHour`; the service runs as one instance, so the count in memory is the whole count.
- **Feedback** — the toolbar's "Report a problem or idea" writes a `REPORT` row and mails the super admins, in either mode; sample mode's lands in the sample data and beside the other sample mail. A super admin reads the queue in Heliosian's admin, edits what an issue should say and files it in `heliosian/heliosian` as a GitHub App, which needs `GITHUB_APP_ID` and `GITHUB_APP_KEY`, both required in real-data mode; without them - sample mode has none - the queue says filing is not set up and a report can only be dismissed (`docs/feedback.md`).
- **Claude** — a real-data server talks to Claude with the Anthropic key in `ANTHROPIC_API_KEY`, required, for Helios Ask, Staff Birthdays' charity sentences, and Loop's email list descriptions, though the digest of school mail (`docs/datamodel.md`, Digest) runs on Cloud Run alone and search entries are made only by production or the sample server (`docs/datamodel.md`, Search); sample mode answers through its intercept instead (Run, above). Every real answer costs money.
- **Helios Ask** — reads the data model's documents (`docs/ask/ask.md`), and search embeds through Vertex AI as `directory@`, which the impersonated credentials above already are; sample mode embeds through its intercept of Vertex (Run, above).
- **Helios Loop's mail** — the worker that forwards posts to the groups runs only on Cloud Run and in the sample and snapshot servers, never in real-data mode on a laptop, so production's waiting posts are left for production; a real-data server takes posts in only with `MAILGUN_WEBHOOK_KEY` set - and even then only if Mailgun's route points at it, which it does not on a laptop; without the webhook key the routes answer 404. Every post it takes in is kept in the media bucket as `directory@`, which the impersonated credentials above act as (`docs/loop/data.md`, Mail). Sample mode receives nothing, and a forward, were one to run, lands as `.eml` files under `local/mail/` beside the other sample mail.
- **Maps** — a server key for the Geocoding API and the Places API (New) (`GOOGLE_MAPS_SERVER_KEY`; never rendered into pages, restrict by server IP or leave unrestricted for dev; both APIs enabled on the project and allowed for the key) and a browser key for the Maps JavaScript API (`GOOGLE_MAPS_BROWSER_KEY`; rendered into pages, restrict by HTTP referer). Geocoding results are kept per address as `GEOCODE` rows (`docs/datamodel.md`).

To capture authenticated real-data pages, launch the capture browser (`go run ./tools/capturebrowser`), sign in to the local server there once, and use `tools/browse` or `tools/screenshot --remote` — the session cookie lives in the capture profile.

## Snapshot

    eval "$(go run ./tools/devenv)"
    go run ./tools/snapshot
    go run ./tools/startserver --snapshot --email <address>

runs the dev server over production's data with nothing reaching production, for working with real sizes and shapes - timing a write, say - without touching anything. `tools/snapshot` reads every tab of every spreadsheet in `internal/spreadsheets` in one batch request per spreadsheet and writes each as `local/snapshot/<sheet>/<tab>.csv`, laid out as `sampledata/` is, replacing the snapshot before it; it holds the community's real data, so delete it (`rm -r local/snapshot`) when done. `--snapshot` serves it as the sample server serves `sampledata/` (`localCore` in `tools/startserver`): every write stays in memory and a restart goes back to the snapshot, mail is written under `local/mail/`, and Claude, Vertex, Geocoding and Places are answered locally; and it signs every request in as `--email`, which has to be someone the snapshot's directory lists. The media bucket is production's, read through the cache under `local/cache/blobs/` (Real data, above) and wrapped in `blob.Overlay`, which keeps every write and delete in memory and answers every read it does not hold from the bucket, so the bucket is read and never written. None of production's workers run - extraction, fetching, classifying, the sweeper, the consent sync. It reads the bucket with the impersonated credentials from Real data, above.

## Writes

No direct writes, ever: every change to a sheet or a bucket goes through the storage layers in `docs/storage.md` - IO, a transaction on the store, the data model, and the hooks - and nothing reaches a sheet or an object any other way.

## The rules live with the thing

Who may see a thing, who may change it, what follows when it changes and where its page is are written once, in the data model, and every app that shows or writes it - its own pages, another app folding it in, Helios Ask and Helios MCP - goes through that one place rather than restating it, since a restated rule drifts from the one the owner's pages keep. So:

- **Who sees it and who changes it** - the policies (`internal/db/policy.go`, `docs/datamodel.md`, Permissions), which every read through `/api/q` and every write through `/api/q` and `/api/do/` are checked against as the signed-in person. A page never decides what its viewer may see: it asks, and the answer holds only what the policies let through. A handler that writes builds an `access.Actor` and an `Env`, stages its edits through `db.Write`, and answers the refusal it gets (`access.Forbidden`, `Missing`, `Invalid`, which carry the HTTP status). Work nobody signed in does - an import, a mailer, a sweep - names itself in `Env.System` (`docs/datamodel.md`, Server jobs). `TestRowsAreBuiltBesideTheirRules` in `internal/access` refuses `store.Insert`, `Set`, `Update` or `Delete` in any file but a `writes.go` or `<thing>_writes.go`.
- **What follows from a change** - the data model's triggers (`internal/db/trigger.go`, `docs/datamodel.md`, Triggers): a family's name, a person's school groups, a document's to-dos, an event's answer groups.
- **Where its page is** - generated columns on `PERSON`, `GROUP` and `DOCUMENT` (`internal/db/link.go`), under the host of the domain the store was made with (`db.NewStore`'s origin). `path` is the address within an app: `/p/<slug, else ID>` for a person, `/g/<slug, else ID>` for a group, which every app routes to its own view of that group, and a wiki page's address on Helios Wiki. `href` is the row's main page: a person's, family's, classroom's or grade's on Who?, an event's on When, an activity's on Team, a party's on Celebrate, any other group's `loop_href` (blank on a group Loop has no page for, such as a `category`), a wiki page's on Helios Wiki, any other document's `url`. `who_href`, `loop_href`, `when_href`, `team_href` and `celebrate_href` are each app's page for the row and blank where the row is not that app's kind of thing (each column's description in `internal/db/schema.go` says which), so a page links across to another app only when its column is filled. A page links within its own app by `path` and across apps by the app's href, and builds no address itself; the router (`web/common/router.js`) takes the clicks on a relative link and the browser follows an absolute one. Like any column, a query that names its columns answers these only when they are among them. Each app answers the old prefixes of its pages, listed in `Moved` on each app in `internal/app/wiring.go`, with a `301` to the same rest under the new one, before sign-in and after the app's own `REDIRECT` rows.

JSON handlers outside the data model's API are `func(r *http.Request, body In) (Out, error)` registered through `serve.JSON`, which decodes the body, answers a refusal with its status and message (or its `Body` as JSON), any other error with a logged 500, `serve.None` with 204 and anything else as JSON. Handlers that need the `ResponseWriter` - pages, images, feeds, uploads, webhooks - stay plain and use `serve.Decode`, `serve.Write` and `serve.Error`.

A rule an app needs that the data model lacks is added to the data model, never kept by the app that needed it.

## Tests

Helpers more than one package's tests use live in `internal/testkit`, which only `_test.go` files import, so none of it reaches the binary. It is two packages because a package's own tests cannot import anything that imports that package: `testkit` itself imports nothing above `store`, `data` and `auth`, so every app's tests can use it - image checkers (`None`, `All`, `Only`, `Files`), `Call` for a signed-in request and `Form` for a signed-in form post, sheet reads that flush the write queue first (`Rows`, `Tables`, `ChangeLog`, `ChangeLines`), `MustTime`, and the link-preview checks `Previews` and `Cards`; `testkit/mailtest` holds the mail `Recorder` and `Discard`, each a real `*mail.Mailgun` whose sends one intercept of `api.mailgun.net` per test binary answers, a recorder's kept by its API key. Tests that reach an outside service install the sample server's intercept for its host (`intercept.Claude`, `Geocode`, `Places`, `Vertex` with `GoogleLogin` into `t.TempDir()`), or a handler of their own that counts or records, and talk to it through the real client.

## Tools

Each runs as `go run ./tools/<name>`. The sheet, drive, and bucket tools authenticate with the same impersonated application-default credentials as the server (see Real data).

- `screenshot`, `capturebrowser`, `browse`, `console` — page capture, browser driving, and a page's console output; see `docs/screenshots.md`
- `deploy` — apply the full production service configuration and add any domain mapping the service lacks, finding the spreadsheet ids itself; see `docs/deploy.md`
- `startserver` — the dev server: sample data in the foreground by default, `--capture` for a one-command page screenshot, `--email <address>` to sign in as someone else the sample lists, `--snapshot --email <address>` for production's data from a snapshot, disconnected (Snapshot, above), `--real` for the production assembly in the foreground with the objects it reads cached under `local/cache/blobs/` (Real data, above), `--detach` to launch that in the background with its output in a log file (needs `SESSION_KEY` and every spreadsheet id; `cookie` mints a session to reach it with), and `--run <command…>` to start whichever of those the other flags pick with its log in the same file `--detach` uses, run the command written after the flags against it once it answers, shut it down, and exit with the command's status, so a measurement against `--real` is one foreground command whose output is the command's alone: `go run ./tools/startserver --real --run go run ./tools/q --local <address> read --trace '<query>'`
- `cookie` — print a signed session cookie for `--email`, required, for local API testing
- `askrun` — send Helios Ask's fixed list of fifty questions, each as a fresh chat, to a running real-data server (`--base`, the dev server's ask origin by default) with a session minted for `--email`, required, and write every answer with its lookups, rounds, tokens and time to one markdown file under `local/ask-runs/` (`--out`), for reading two runs side by side when the model changes; `--as` deals the questions out across the directory addresses named, through Spoof Mode, since one person gets `perHour` calls to Claude an hour (`docs/ask/data.md`) and fifty as one person would be refused past that (needs `SESSION_KEY`, the server's own; every question costs money)
- `snapshot` — copy every tab of every spreadsheet the server reads into `local/snapshot/`, for `startserver --snapshot` (Snapshot, above) (needs every spreadsheet's id, as `tools/devenv` exports them)
- `loadcheck` — load the data model (`db.NewStore`) from the live sheets, or from a directory of dumped tabs (`--dir`), each data sheet logging its own time, and print each table's row count or the first thing a sheet refuses
- `devenv` — print every variable the dev server and the tools read as shell exports, for `eval` (Real data, above): the spreadsheet ids, found by the sheets' titles, with every other visible spreadsheet as a comment, the keys from Secret Manager and the local `SESSION_KEY`
- `sheets` — every direct operation on one spreadsheet, as `go run ./tools/sheets <command> --sheet <id>`, the command list printed when none is named: `create` creates an empty spreadsheet titled `--title` in the same shared-drive folder as `--sheet`, refusing a title already taken there, and prints its id; `tabs` lists the tabs with their sizes and header rows; `rows` prints one tab's rows (`--rows`/`--from` for a slice, `--cells` for each filled cell with its column index); `dump` / `write` copy one tab to a local CSV / write a local CSV into a tab, header-checked; `sync` brings a tab's cells in line with a local CSV by `--keycol`, never adding rows; `set` sets the `--col` cell of the rows whose `--keycol` holds `--key`, appending the row if none does, and `--key` repeats to set the rows of several keys in one write; `delete` deletes the rows whose `--keycol` holds `--key`, which repeats to delete the rows of several keys in one read and one write; `rename` renames a tab; `drop` deletes named columns, header and cells, for a column an app has stopped reading; `drop-tab` deletes a tab holding nothing past its header, such as the empty `Sheet1` a new spreadsheet starts with. `--keycol` always names the column that picks rows and has no default; `--col` only ever names a column written. Every command that changes a sheet (`write`, `sync`, `set`, `delete`, `rename`, `drop`, `drop-tab`) only reports what it would change without `--apply`, `drop` saying how many cells each column holds
- `darkcheck` — load pages in dark mode (`--url a,b,c`, `--click` into a window first) and read the rendered page for what dark mode missed: words with too little contrast against the ground they sit on, a tab strip painted a different colour from what it sits on, and with `--light` every light surface; `--compare` reads each page by day too and marks each finding dark only or by day too
- `createtabs` — create the tabs of every spreadsheet that has a layout with their header rows, adding missing columns to tabs that exist (needs each of those spreadsheets' id variables, and refuses a spreadsheet whose title isn't the layout the variable promised)
- `import` — run a fresh Veracross export and a fresh export of the school website's staff page and bring the data model's people, emails, families and role and school groups in line with them through `/api/q` on production, in one batch, then add the portraits people don't have yet through `/api/do/photo` (`docs/datamodel.md`, Veracross import), and then bring the school days and dated entries of the school's year calendar PDF in line, reading it with Claude only when the PDF or the prompts that read it are new (`docs/datamodel.md`, Calendar import); `--dry-run` prints both batches and sends nothing, still running both exports against the live sites and still reading a new PDF, which costs money (signs in as `q` does, and needs `ANTHROPIC_API_KEY`, as `tools/devenv` exports it, `VCEXPORT` and `WEBEXPORT`, naming a `vcexport` and a `webexport` checkout, and poppler's `pdftoppm`, `brew install poppler`)
- `q` — run a query against production's `/api/q` and print the rows as tables, the listed table first and one more for each table the includes reach, showing only columns some row fills, each cell on one line and cut at 48 characters (`q read <query>`, the query language or the query in JSON; `q read --columns a,b <query>` prints just those columns of the listed table, whole; `q read --trace <query>` adds the round trip's time and the answer's `Trace` header, indented), or send a JSON batch of writes and print the IDs it touched (`q write <batch>`); either reads stdin when given no argument. It runs as whoever signs in; before the command, `--import` runs it in import mode, so a super admin sees and writes every row, withheld and hidden ones too, and `--spoof <address>` runs it as that person, as Spoof Mode does (`docs/datamodel.md`, The query API). `--local <address>` sends the same requests to the dev server running `startserver --real` on this machine instead, signed in as that address by an access token the tool mints from `SESSION_KEY` the way the server derives its own (`auth.AccessKey`), accepting the dev server's self-signed certificate; `--import` and `--spoof` work there as on production. Otherwise it signs in through `internal/qclient`, which the other tools here that reach production share: the first run opens the browser at the MCP host's sign-in (`docs/mcp/mcp.md`), and the access token it gets is kept in `token.json` under Go's `os.UserConfigDir()` (`~/Library/Application Support/heliosian/` on a Mac) until it expires or production refuses it, when the next request signs in again
- `fetchsignin` — fetch, through the capture browser signed in to Google, the linked documents production could not fetch without a sign-in, and hand what each answered to `/api/do/fetched` (`docs/datamodel.md`, Documents) (signs in as `q` does)
- `chooselinks` — ask Claude which links of one of production's email HTML parts (`--document`) to fetch, as the server's link chooser does, and print each link with the answer, writing nothing (`docs/datamodel.md`, Documents) (signs in as `q` does, and needs `ANTHROPIC_API_KEY`, as `tools/devenv` exports it; every run costs money)
- `searchplan` — load the live sheets, work out every row's search input and count those whose entry the media bucket lacks, by table, with an estimate of what making them would cost in Claude and Vertex tokens (`docs/datamodel.md`, Search); it writes nothing (needs every spreadsheet's id, as `tools/devenv` exports them)
