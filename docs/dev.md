# Development

## Principles

- **One static Go binary.** The server is Go, compiled to a static binary, running on Google Cloud Run. A new app joins the same binary at its own hostname rather than deploying as a new service; the only other production binary is the scheduled job in `cmd/periodicsync`.
- **Frameworkless client.** Client code is plain JavaScript with no client-side framework and no build step.
- **Great local development.** A single command runs the server locally, content changes show on a refresh without a restart, and fictional sample data makes it possible to develop and test without touching real community data.
- **Agent-friendly repository.** Most development happens through coding agents driven by community contributors. The repo is structured, documented and instrumented (screenshots, browser driving, load checks) so agents can build, verify and iterate without hand-holding.
- **Open source, minimal configurability.** The code is public and specific to Helios; it does not aim to be a generic configurable product. It contains no secrets, credentials or private community data.
- **Sheets and a bucket.** Structured data lives in Google Sheets and blobs (photos and other uploads) in Cloud Storage (`docs/storage.md`). The system of record for families and staff is Veracross, reaching the directory's sheet through `tools/import`; a direct integration replaces that when Veracross offers an API.

## Run

    go run ./tools/startserver

Every app answers at `https://<app>.heliosiandev.com:8080`, under the same label as its production hostname (override the port with `PORT`), clicking past the browser's warning about the self-signed certificate the first time. The dev server serves the fictional community in `sampledata/`, signs every request in as a sample parent, and geocodes with a deterministic fake — no credentials or configuration. All sample-mode composition lives in `tools/startserver`; the production binary and the shared wiring in `internal/app` carry none of it. Templates and served files are read from disk on every request; edit a file and refresh. The sample CSVs back a fake spreadsheet that loads each tab on first read and keeps every write in memory, so `sampledata/` never changes on disk — restart to get the fixtures back. The sample HCA Meeting carries a sent guest list the sample parent co-hosts, with two people from outside the community on it; their `/ext/{token}` pages are reached by the Token column of `sampledata/calendar/Invites.csv`.

## Hosts and files

One binary serves every app, and the hostname picks the app by convention: `<app>.heliosian.com` is production and `<app>.heliosiandev.com` is a developer's machine, so `who.heliosian.com` and `who.heliosiandev.com` both mean the directory. Home additionally answers as the bare and `www` domain, the volunteer portal (`team`) as `hca` on every tier, and any other host gets a 404 (`internal/app`). Each server answers one domain only - the deployed service `heliosian.com`, the dev server in every mode `heliosiandev.com` (`app.Domain` and `app.DevDomain`) - and its session and spoof cookies are scoped to that domain, so a production sign-in is never sent to a developer's names: nothing under `heliosian.com` resolves to loopback. Public DNS has to point `heliosiandev.com` and `*.heliosiandev.com` at loopback - `dig +short who.heliosiandev.com` answering `127.0.0.1`; the records live at the registrar (`docs/deploy.md`, Domain) - so that local development uses real hostnames with no hosts-file entry, and the OAuth client and Maps key can name them (Google refuses made-up domains such as `.localhost`).

## Local HTTPS

The dev server speaks HTTPS in every mode. Google sign-in only accepts a plain-HTTP login URI on `localhost` itself, and the dev hostname is a real name, so it has to be HTTPS. `internal/devtls` mints a self-signed certificate for `heliosiandev.com` and `*.heliosiandev.com` in memory every time the dev server starts; nothing is written to disk. Browsers warn about it; click through. Headless captures pass `--ignore-certificate-errors`; the capture browser needs the warning clicked once in its own profile. The production binary itself stays plain HTTP, because Cloud Run terminates TLS in front of it. The security headers every response carries, HSTS among them for production alone, are `secure` and `policy` in `internal/app`.

Within an app, a request resolves in this order: `web/public/<app>/<path>`, then `web/public/common/<path>`, served to anyone with no sign-in; on the portal, the `Redirects` tab, which sends an old address on with a `302` before sign-in (`team.Redirected`; `docs/team/team.md`, Redirects); then sign-in; then `web/<app>/<path>`, then `web/common/<path>`; then the app's routes. Public URLs are the file's own path, with no prefix: `/style.css`, `/brand/icon-192.png`, `/fonts/fonts.css`. The public tree holds exactly what a browser fetches without credentials and what the sign-in and no-access pages need: the manifest, icons, splash art, login art, fonts, the login page itself, and the no-access page (`web/public/common/no-access.html`) sign-in serves to anyone the directory does not list. Everything else, every page, script, style, image, and API, requires a session for someone the directory lists, but for what `auth.Public` names: the sign-in exchange and three prefixes. The sign-in exchange (`POST /auth/login`) and signing out (`POST /auth/logout`) answer only a post the browser marks `Sec-Fetch-Site: same-origin` or `none`, and refuse any other, or one unmarked, with a `403`, so a page elsewhere can neither sign someone out nor sign them in as another account. Sign-in makes both checks in one place (`auth.Wrap`, and the sample server's `auth.Fixed`), for every host and every request past the public paths, the app's own files included: a session says who someone is, and the directory says whether they are in; a spoofed request is checked as the person viewed as. An address the directory does not list - a family that opted out or never answered the consent form, someone who has left, an admin with no row of their own - gets the no-access page, or a bare `403` on `/api/` and `/blob/` paths, on every host, with only signing out (`/auth/logout`) and the way to the consent form (`/optin`, registered on every host, sending on to the Config sheet's address) still answering them. `/hooks/` is every callback the service asked another service for - the school calendar's watch at `/hooks/calendar`, the calendar's reply route at `/hooks/replies/mime` and its delivery events at `/hooks/events` (the bounces), Loop's mail route and delivery events at `/hooks/mail/mime` and `/hooks/events`, Helios Ask's forwarded school mail at its own `/hooks/mail/mime` - each checking its caller's secret; the mail routes end in `mime` because that is what makes Mailgun post the raw message in the call. `/open/` is every address the service hands out for something other than a signed-in browser to follow - the share cards chat apps fetch at `/open/share/`, the calendar's personal feeds at `/open/feed/`, Loop's unsubscribe links at `/open/unsubscribe/`, the calendar's routes for someone invited from outside at `/open/ext/`, its event pictures for that page at `/open/banner/` - each an address whose token is the whole of the check. `/ext/` is the calendar's page for that outside person, `/ext/{token}`, self-contained under `web/public/calendar/ext.html` since the app's own files sit behind sign-in (`docs/calendar/calendar.md`, Invitations).

Pages are plain files, not templates. The login page learns the OAuth client id from `/auth/client`, one of the two endpoints (with the login POST) reachable before sign-in, so the id lives only in the server's configuration, and builds its login URI from its own origin; the directory shell learns who is signed in from the model it fetches. Shared browser code goes in `web/common/` (or `web/public/common/` when it must load before sign-in) and is reached by every app at the same path: the toolbar, the app shell's buttons, drawer, page title, toast and popups with one stacking scale, and the `#page` column's padding, which Loop's sticky Save bar cancels with negative margins (`shell.css`; each app's own `style.css` keeps only the column's max-width), the rule editor and its filter widgets (`rules.js`, `rules.css`), the person picker (`picker.js`, `picker.css`), the modal and form kit (`modal.js`: `openModal` fills the page's `#modal` form, stacking over one already open unless given `replace`, with `required`, `stay`, `working`, `alternate`, `wide` and delete options, after `initModal(load)` wires it to the app's reload; `popup` is a titled layer above it; `form.js`: `field`, `text`, `textarea`, `select`, `checkbox` as a switch, `segmented`), the picture tools (`images.js`: `imageTools('/api/<app>', {state, toast})` answers an upload, a search of the picture libraries in a `popup` whose pick is imported through the app, and the image picker with Crop and Remove, each handing back `{name, url}`), the address suggestions every address box offers (`address.js`, `address.css`: `addressSuggest(input)` asks the app's `GET /api/address/suggest?q=` as the person types - Google's Places Autocomplete behind the real geocoder, a few made-up Bay Area addresses behind the sample one; one `geocode.Suggestions` serves every app, answering a query asked before from an LRU of `suggestCached` entries (`internal/lru`) and otherwise counting it against the signed-in person's `suggestPerMinute` (both in `internal/geocode/suggest.go`, counted by `internal/ratelimit`), past which the box gets no suggestions - and drops whole addresses under the box to pick with a click or the arrow keys; what is typed by hand stays as typed; When's event form and party override and Celebrate's address boxes use it), and the date card an event's banner wears (`datecard.js`, `datecard.css`: `dateCard(el, {start, end, allDay, location, add})` draws a cream tile for the first day - weekday, month, day, and the sun as it stands at the start (rising before noon, whole through the afternoon, setting until nine, a moon after) - a pale-green tile for the last day when the event runs across days, then the hours with a clock and the place with a pin, or each end with its day and how many days it runs, and, at the hours' end, an Add pill when given its link, which `googleCalendarLink({title, start, end, allDay, location, details})` builds; on a phone the card follows the banner rather than sitting on it; When, HCA-Team and Celebrate use it, and none keeps a Date & Time row in its rail for a scheduled event).

Sample-mode limits: the map section needs a real Maps JavaScript key (`GOOGLE_MAPS_BROWSER_KEY`) to render tiles, and self-service edits need real-data mode — those handlers register alongside the directory's sheet, which the sample CSVs have no counterpart for. Media has a store in sample mode, `blob.NewMemory`, a map that holds whatever is uploaded or imported until the server exits, so the image pickers and their search work there and nothing they store survives a restart. Tags do work, since they need only the writable data source.

`sampledata/` mirrors the production Sheets layout: one directory per spreadsheet, named as the server's data source names it, one CSV per tab, first row is the schema, served through the same data-source interface the Sheets backend implements. It stays fictional — real community data never goes here. `sampledata/directory/Website Staff Import.csv` covers what the staff page layer has to resolve: a bio an override outranks, a title Veracross outranks, an entry with no address matched by name through `Name to Email`, another matched by name against the staff import, an entry under a second address resolved through `Email Aliases`, and entries matching nobody — a vendor the directory drops, and a staff member added by hand, whom the layer runs too early to see. `sampledata/preferences/` is the consent form's response sheet, exercising every combination the loader has to resolve: both permissions, each alone, neither, a family that never answered, a staff member's own opt-out, a superseded submission, and a two-household student whose parents answered differently.

In sample mode `go run ./tools/startserver --capture <url> --out <png>` serves and screenshots one page of either app in a single command, and `tools/screenshot` captures against an already-running server (see `docs/screenshots.md`).

## Real data

    eval "$(go run ./tools/findsheet)"
    SESSION_KEY=<secret> go run .

runs the production binary: the production spreadsheets, the media bucket (see `docs/who/data.md`), real geocoding, and Google sign-in, with no sample fallback — every input is required and the server refuses to start without one. `tools/findsheet` prints every spreadsheet id variable the server needs, found among the sheets the service account can see. The model loads at startup — the server refuses to start if the load fails — and reloads every five minutes. Real data never leaves the process: nothing is written to disk. The one exception is `go run ./tools/startserver --real`, the same assembly under the dev server, which keeps a copy of every media object it fetches under `local/cache/blobs/` (gitignored, kept out of the image) - the bytes, the thumbnail and a `.meta` file of generation and type beside them, each landed whole - and reads from there ahead of the bucket on the next start, so a restart takes seconds rather than fetching every photo again. Every object is content-addressed, so its bytes never change under its name and a cached copy never goes stale. Delete the directory to start clean. Requirements:

- **Sign-in** — everything sits behind Google sign-in restricted to the school's Workspace domain. Signed out, an API or media path and a request the browser names as an asset - a stylesheet, script, image, font, manifest or worker, by `Sec-Fetch-Dest` (`assetDests` in `internal/auth`) - get a bare 401, since a browser keeps whatever an asset's address answered and would use the login page as that stylesheet or script again once signed in. Anything else gets the login page at the address asked for: a navigation, a chat app reading a link's preview with no destination named, a service worker fetching the page for its tab, which says `empty`, and a destination nobody has seen before. Nothing answered signed out may be stored (`Cache-Control: no-store`), and each such answer logs a `signed out` line with the path, whether it got the login page, and the three `Sec-Fetch` headers, for reading what a browser actually sent. A page that fetches and gets a 401 reloads itself through `signedIn` in `web/common/toolbar.js`, landing on the login page and, once signed in, back where it was; Helios Ask, a single page with no reload of its own, runs its fetches through it. The OAuth web client id is read from `local/creds/oauth-client.json` or `GOOGLE_CLIENT_ID` and handed to the login page by `/auth/client`; the client's authorized JavaScript origins must include each app's development origin, port included (`docs/deploy.md`, OAuth, for where that list lives). The server issues its own HMAC-signed session cookie, keyed by the required `SESSION_KEY`: the address and the moment of issue, good for `sessionLength` (`internal/auth`) from then, and refused from the moment the address signs out, on any browser, since sign-out records the time in the Config sheet's `Signed Out` tab (`docs/config.md`). The session's length is the server's alone, so changing the constant, or a sign-out, takes effect on cookies already issued. Signing in sets the cookie for the domain and deletes the host-only copy, since a browser sends every copy of the name and the server reads the first, so a stale host-only one from before the cookie was scoped to the domain would otherwise shadow the session just set on that host alone.
- **The previous host's service worker** — the domains were hosted by Glide before, and browsers that visited then still hold its service worker, which catches page loads and fetches them itself and which a 404 for its script does not remove. `web/public/common/sw-prod-v4.js` sits at its script's address on every host, answering without a session whatever version its query names: a browser checking for an update installs it, and it deletes the origin's Cache Storage, which nothing of ours uses, unregisters itself and reloads the open tabs. It can go once nothing asks for it, which the request log shows:

      gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="heliosian" AND httpRequest.requestUrl:"sw-prod"' --project heliosian --freshness 30d --format "value(timestamp,httpRequest.requestUrl,httpRequest.status)"

- **Data access** — Google credentials come from application-default credentials impersonating the data service account, set up once per machine:

      gcloud auth application-default login --impersonate-service-account=directory@heliosian.iam.gserviceaccount.com

  This needs `roles/iam.serviceAccountTokenCreator` on that account for the person running it. What `directory@` itself needs - membership of the community shared drive for the sheets, project IAM for the buckets - and how to read whether it has each is `docs/deploy.md`, IAM; local processes then act as exactly the identity production runs as, with no key file anywhere (an org policy is meant to forbid creating one, and the same section says how to read it).
- **Mail** — in sample mode the volunteer portal and Helios Celebrate write each email they would send as an `.html` file under `MAIL_DIR` (default `$TMPDIR/hca-mail`); open one in a browser to see it. Real-data mode sends through Mailgun when `local/creds/mailgun.key` (or `MAILGUN_KEY`) is present, else drops and logs. Replies to Helios When's invites come back through a Mailgun route only in real-data mode with `local/creds/mailgun-webhook.key` (or `MAILGUN_WEBHOOK_KEY`) present too, and only if the route points at the server, which it does not on a laptop; the sample server's invites name `rsvp@reply.example.org` and nothing receives for it.
- **Image search** — the volunteer portal's image picker ("Find an image") searches Unsplash when `local/creds/unsplash.key` (or `UNSPLASH_KEY`, an Unsplash API access key - a demo app's 50 requests an hour is plenty) is present, with the photographer credited on each tile and the photo's download endpoint pinged on import as Unsplash's terms ask; likewise Pexels (`local/creds/pexels.key` / `PEXELS_KEY`) and Pixabay (`local/creds/pixabay.key` / `PIXABAY_KEY`, photos plus illustrations and vectors). Those three stock libraries are the whole of it. With none of the three keys the picker is not offered. A search asks every library with a key at once and answers one list, the libraries' answers interleaved, and the browser learns nothing of where a picture came from: each hit is an id of the server's own - a hash of the library and its id - with the app's own `images/thumb` route beside the search, a size and a title, and no credit, licence or library name. The library's addresses for the picture, its credit, licence and page are kept in `stock/<id>.json` in the media bucket, read by nothing but the thumbnail route and the import. A search answers as soon as the libraries have, then writes its records and fetches every thumbnail the bucket lacks in the background, `workers` at a time, into `stock/<id>-thumb`; the process's `imagesearch.Stock`, one for every app, remembers the records of every search made here, which thumbnails the bucket holds, and which are being fetched right now, so the thumbnail route serves what is there, waits for a fetch already under way, or fetches the one thing itself, and no thumbnail is fetched twice however many tiles ask at once. The import takes the id, fetches the full image once into `stock/<id>` and stores it content addressed like an upload. A picture is pulled from a library once however often it is searched for or picked. Every write to the bucket goes up in one request: the storage client otherwise allocates its whole default upload chunk, sixteen megabytes, for each write, which is what took the service past its memory limit when a search wrote seventy-two records at once. The libraries' hosts are named nowhere in the content security policy. Every search spends one call on each keyed library, so Unsplash's demo cap of fifty an hour is drawn down by every search; a library refusing fails the whole search, loudly.
- **Feedback** — the toolbar's "Report a problem or idea" writes to the `Reports` tab of the `Feedback` sheet and mails the super admins, in either mode; sample mode's lands in the sample tab and beside the other sample mail. A super admin reads the queue in Heliosian's admin, edits what an issue should say and files it in `heliosian/heliosian` as a GitHub App, which needs `local/creds/github-app.id` and `local/creds/github-app.pem` (or `GITHUB_APP_ID` and `GITHUB_APP_KEY`), both required in real-data mode; without them - sample mode has none - the queue says filing is not set up and a report can only be dismissed (`docs/feedback.md`).
- **Helios Ask** — a real-data server talks to Claude with the Anthropic key in `local/creds/anthropic.key` (or `ANTHROPIC_API_KEY`), required; sample mode uses the key when it is there and a fake that streams a canned answer when it is not (`docs/ask/ask.md`). Every real answer costs money. Its search over the community's documents embeds each question through Vertex AI as `directory@`, which the impersonated credentials above already are, and reads the documents from the `Artifacts` sheet and the media bucket (`docs/ask/artifacts.md`); sample mode files the fictional messages and page under `sampledata/artifacts/` at startup, embedding with a fake.
- **Helios Loop's mail** — a real-data server forwards the posts to the groups through Mailgun with `local/creds/mailgun.key` (or `MAILGUN_KEY`), and takes them in only with `local/creds/mailgun-webhook.key` (or `MAILGUN_WEBHOOK_KEY`) present too - and even then only if Mailgun's route points at it, which it does not on a laptop; without both the routes answer 404. Every message it does forward is kept in the mail bucket as `directory@`, which the impersonated credentials above act as (`docs/loop/data.md`, Mail). Sample mode receives nothing, and a forward, were one to run, lands as `.eml` files under `MAIL_DIR` beside the other sample mail.
- **Maps** — a server key for the Geocoding API and the Places API (New) (`local/creds/geocoding.key` or `GOOGLE_MAPS_SERVER_KEY`; never rendered into pages, restrict by server IP or leave unrestricted for dev; both APIs enabled on the project and allowed for the key) and a browser key for the Maps JavaScript API (`local/creds/maps.key` or `GOOGLE_MAPS_BROWSER_KEY`; rendered into pages, restrict by HTTP referer). Geocoding results are cached per address in the directory spreadsheet's `Geocode` tab (see `docs/who/data.md`).

To capture authenticated real-data pages, launch the capture browser (`go run ./tools/capturebrowser`), sign in to the local server there once, and use `tools/browse` or `tools/screenshot --remote` — the session cookie lives in the capture profile.

## Writes

No direct writes, ever: every change to a sheet or a bucket goes through the storage layers in `docs/storage.md` - IO, the store's `Commit`, each app's model, and the hooks - and nothing reaches a sheet or an object any other way.

## The rules live with the thing

Who may see a thing, what it is called, where its page is, and what else changes when it changes are written once, in the package that owns the thing and beside its model, and every app that shows or reads it - its own pages, the calendar folding it in, Helios Ask - calls that one function rather than restating it, since a restated rule drifts from the one the owner's own pages keep. So:

- **Who sees it** - `team.Model.VisibleTo` (a thing and everything above it), `celebrate.Party.VisibleTo`, `loop.Group.VisibleTo` and `loop.Group.MailReadableBy`, `calendar.Model.EventsFor`, and the directory model itself, which holds only what members may see. A caller with no viewer - the calendar folding in what everyone sees, a signed-out link preview - asks with an empty address and no admin.
- **What it is called** - the directory's `familyNameFor` for a family's `name` and `shortName`.
- **Who is whose** - `who.Model.Household` (everyone in a person's families but them), `Members` (one family's adults and students), `Parents` (a student's), `Children` (a parent's) and `FamilyOf` (a person's first family, the one `/my-family` opens): each resolves aliases, drops anyone the directory does not list, and names each person once. An app maps their answer into its own person type and never walks `Families` itself; only the loader, building those families, and Who?'s edit permission, which asks which families a person is an adult of, read `AdultEmails` and `KidEmails` directly.
- **Where its page is** - `who.PersonPath`, `who.FamilyPath`, `who.ClassroomPath` and `who.ListPath`; `calendar.EventPath` and `calendar.Page`, which says which app a linked event's page is on; `loop.Group.Path`; `team.Model.PathOf` and `celebrate.Model.PathOf`. Only the host is the caller's.

A rule an app needs that its owner lacks is added to the owner, never kept by the app that needed it.

## Setup

Development happens on macOS. Two Homebrew installs cover everything here and in `docs/screenshots.md`:

    brew install go
    brew install --cask google-chrome

- **Go** 1.27 or later — builds and runs the server and all tooling (`go run`, `go vet`).
- **Google Chrome** — launched headless by the screenshot tool from its standard install location; never opened by hand.

No Node, no Docker, and no cloud credentials are needed for local development. Repository layout is in the README.

## Tools

Each runs as `go run ./tools/<name>`, but for `periodicsync`, which production runs too and so lives at `go run ./cmd/periodicsync`. The sheet, drive, and bucket tools authenticate with the same impersonated application-default credentials as the server (see Real data).

- `screenshot`, `capturebrowser`, `browse`, `console` — page capture, browser driving, and a page's console output; see `docs/screenshots.md`
- `deploy` — apply the full production service configuration, add any domain mapping the service lacks, and configure the periodic sync job (needs every spreadsheet id); see `docs/deploy.md`
- `startserver` — the dev server: sample data in the foreground by default, `--capture` for a one-command page screenshot, `--real` for the production assembly in the foreground with the media it fetches cached under `local/cache/blobs/` (Real data, above), and `--detach` to launch that in the background with its output in a log file plus a minted session cookie (needs `SESSION_KEY` and every spreadsheet id)
- `cookie` — print a signed session cookie for local API testing
- `askrun` — send Helios Ask's fixed list of fifty questions, each as a fresh chat, to a running real-data server (`--base`, the dev server's ask origin by default) with a session minted for `--email`, and write every answer with its lookups, rounds, tokens and time to one markdown file under `local/ask-runs/` (`--out`), for reading two runs side by side when the model changes; `--as` deals the questions out across the directory addresses named, through Spoof Mode, since one person gets `perHour` calls to Claude an hour (`docs/ask/data.md`) and fifty as one person would be refused past that (needs `SESSION_KEY`, the server's own; every question costs money)
- `loadcheck` — run every app's load pipeline against the live sheets, the calendar's and Helios Ask's documents included (read through `local/cache/blobs`), and print a model summary or the first thing a loader refuses
- `findsheet` — print the spreadsheet ids the server needs as shell exports, found by the sheets' titles, with every other visible spreadsheet as a comment
- `sheets` — every direct operation on one spreadsheet, as `go run ./tools/sheets <command> --sheet <id>`, the command list printed when none is named: `create` creates an empty spreadsheet titled `--title` in the same shared-drive folder as `--sheet`, refusing a title already taken there, and prints its id; `tabs` lists the tabs with their sizes and header rows; `rows` prints one tab's rows (`--rows`/`--from` for a slice, `--cells` for each filled cell with its column index); `dump` / `write` copy one tab to a local CSV / write a local CSV into a tab, header-checked; `sync` brings a tab's cells in line with a local CSV by `--keycol`, never adding rows; `set` sets one cell by key column, appending the row if missing; `delete` deletes the rows matching a column value; `rename` renames a tab; `drop` deletes named columns, header and cells, for a column an app has stopped reading. `sync` and `drop` only report without `--apply`, `drop` saying how many cells each column holds
- `darkcheck` — load pages in dark mode (`--url a,b,c`, `--click` into a window first) and read the rendered page for what dark.css missed: words with too little contrast against the ground they sit on, a tab strip painted a different colour from what it sits on, and with `--light` every light surface; `--compare` reads each page by day too and marks each finding dark only or by day too
- `createtabs` — create the tabs of every spreadsheet that has a layout with their header rows, adding missing columns to tabs that exist (needs each of those spreadsheets' id variables, and refuses a spreadsheet whose title isn't the layout the variable promised)
- `import` — run a fresh Veracross export and a fresh export of the school website's staff page, upload the portraits from both, and commit in one go, as `import`, the import tabs' changed rows, the overrides those imports have caught up with cleared and the `Name to Email` entries Veracross now has an address for dropped (`docs/who/data.md`, Every write is a commit), or report what that would change with `--dry-run` (needs `DIRECTORY_SHEET`, `PREFERENCES_SHEET`, and `CONFIG_SHEET`, and a `vcexport` and a `webexport` checkout, found at `../vcexport` and `../webexport` or wherever `VCEXPORT` and `WEBEXPORT` point)
- `archivesite` — save every page the school website's sitemap names under `local/imports/site/`, less the pages `internal/artifacts` excludes, five seconds apart as the site's robots.txt asks (`docs/ask/artifacts.md`)
- `archivebrowser` — crawl a signed-in site through the capture browser from `--start`, following every link under `--prefix`, and save each page's `--selector` content and the Google Docs, Slides and Drive PDFs it links under `--out`; the portal goes to `local/imports/portal/` and HELP to `local/imports/help/`. Run it rarely, since the portal notices a reader who comes through too often (`docs/ask/artifacts.md`)
- `importartifacts` — read saved messages (`local/imports/mail/*.json`), saved website pages (`local/imports/site/*.json`) and saved browser resources (`local/imports/portal/*.json`, `local/imports/help/*.json`) into Helios Ask's documents: each to markdown, cut into chunks, embedded through Vertex AI, written to the media bucket and indexed in the `Artifacts` sheet. A message that went to none of the school-wide or class lists and an excluded page are refused, one already on file is skipped, and one rendered differently now is imported again with its old object dropped. `--dry-run` reports what a run would embed and writes nothing; naming one file prints its markdown; a run that writes refuses without `--i-have-user-permission-to-spend-money`. It loads the documents on file first, through `local/cache/blobs` (needs `ARTIFACTS_SHEET`; `docs/ask/artifacts.md`)
- `artifactsprobe` — load Helios Ask's documents from the live sheet and bucket the way the server does, reading through the same disk cache, then search them for the words given (`go run ./tools/artifactsprobe when is picture day`), printing the top passages with their scores, so retrieval can be judged without the app (needs `ARTIFACTS_SHEET`)
- `periodicsync` — the scheduled job, run by hand: its stages in turn, each carrying on past the last's failure and the run exiting non-zero at the end naming what failed. Its one stage reads the school's published year calendar into the `Calendar` sheet and has Claude classify its entries; the school's Google Calendar is the serving binary's to keep up with (`docs/calendar/data.md`). `--dry-run` reports what it would change, writing nothing to the sheets; either way it refuses to start without `--i-have-user-permission-to-spend-money`, since every run that reaches Claude costs real money and only the person paying says when (needs `CALENDAR_SHEET`, `DIRECTORY_SHEET`, `PREFERENCES_SHEET`, `CONFIG_SHEET`, an Anthropic API key in `local/creds/anthropic.key` or `ANTHROPIC_API_KEY` - the same key lets the dev server suggest charity sentences in Staff Birthdays and write group descriptions in Loop - without it those buttons say they are not set up in production, and the sample server uses a fake - and answer in Helios Ask - and poppler's `pdftoppm`, `brew install poppler`)
