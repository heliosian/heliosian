# How Helios Ask answers

Helios Ask has no sheet. It reads everything through `ask.Sources` - the data model's store, the shared tools, the apps' origins and the school's clock (`internal/app/wiring.go`) - with `Model.Run`, as the person signed in (`auth.Email`, the one viewed as in Spoof Mode, through `Model.SignedIn`), the community's documents included (`docs/datamodel.md`, Documents), and talks to Claude through the Anthropic API. This file carries what reading `internal/ask` cannot tell you.

## The call

Each turn is one `Respond`: the two system blocks, the conversation so far with the new message last, the tool definitions, and a way to run a tool. `Claude` in `internal/ask/claude.go` makes it through the beta Messages API, streaming, on the model its `model` constant names with adaptive thinking left on at medium effort, and the server's default fallback for a policy refusal (`fallbacks: "default"` under the `server-side-fallback-2026-07-01` beta), so a question the model declines is re-served by the fallback model inside the same call; one still refused ends in a fixed sentence. Text deltas go to the page as they stream. A `tool_use` stop runs the requested tools here, all at once, and sends the results back as one user message in the order they were asked for, for at most `maxRounds` rounds; the last of them closes the tools with `tool_choice: none`, so the turn always ends in words. Every message including the tool exchanges is kept as the conversation, thinking blocks and all, since the same model reads them back.

The prompt's two blocks each carry a cache breakpoint, and the tool definitions sit in front of them, so the tools and the prompt are read from the cache from a conversation's second call on. The request's top-level cache control puts a third breakpoint on the last block of the messages, so each call writes the conversation as it stands and the next - the next round of the same turn, or the next question - reads everything before its own new tail from the cache, earlier tool results included, rather than paying for them again. What changes during a conversation reaches the model as a `role: "system"` message in the messages rather than as an edit to the prompt, so the prefix stays whole: when the day has moved on from the one the prompt names, or recent mail has come in that the conversation has not been told of, the turn's user message is followed by one system message saying so, which stays in the conversation from then on. The prefix must stay whole for more than the cache: the API binds each thinking block's signature to everything before it, and refuses a request that sends one back under a changed prompt. Each turn logs `ask: prompt` with the day the prompt states, the server's time, whether the prompt was carried and whether a new day was told. The turn's log line records the input tokens, how many came from the cache, the output tokens, the rounds, the tools run and how long it took, under `ask: answered`, so the cost of a day's questions is a query away (`docs/deploy.md`, Logs).

The key is the one the calendar import and Staff Birthdays already use: `ANTHROPIC_API_KEY`, which `tools/devenv` exports locally, and required in real-data mode. It never reaches a browser.

## The conversation

`POST /api/ask/chat` takes `{conversation, message, context, known, prompt}` - an id the browser made up, kept only for the log lines, the new message, the conversation as the model last saw it, and the ids of the documents the chat has been told of - and answers `text/event-stream`: `text` with each piece of the answer, `tool` with the words for each lookup as it starts, `card` with what a person, family, classroom, event, volunteer thing, party or group link in the answer points at - its address, kind, name, and its picture or, for an event, its day - once per link and ahead of the text that holds it (`ask.md`, The page), `done` with the messages the turn added to the conversation, the document ids now known, the sealed prompt, the turn count, the whole answer and its tools for the browser to keep, and the usage, and `error` when a turn fails - in which case the browser's copy stands as it was, so the person can send again. A turn the browser stops by closing the request is neither: the server logs `ask: stopped` and keeps nothing; the browser keeps the question and the words written so far as a plain exchange, counted as a question, and a turn stopped before any words keeps nothing. `GET /api/ask/model` is the toolbar's user and badges, the starters and the turn limit.

`GET /api/ask/key` is the key the browser keeps its chats under, answered `no-store` so no cache holds it beside them: an HMAC of the address asked as (`Registry.Actor`; the one viewed as, in Spoof Mode) under a key derived from `SESSION_KEY` (`ChatKey` in `internal/app`), the same on every load and never stored in the browser. The page imports it as a non-extractable AES-GCM key and keeps the chats as one sealed value, a JSON array; which one is open is the page's alone and starts empty on each load, a fresh IV before its ciphertext, under `chats-` and the hex SHA-256 of the address. On each load it removes every local storage entry on the Ask origin not named in that form, and an entry that will not decrypt - a changed `SESSION_KEY`, or anything else - is removed and the chats start empty.

The browser is the whole record and the server keeps nothing between requests: each chat sits in the browser's local storage under the signed-in address, its turns as drawn beside `context` - the API messages with every tool call, result and thinking block, as `done` handed them over, addresses written out - `known`, and `prompt`. Each request is answered from what it carries: `prompt` is the chat's system prompt as its first question built it - its two blocks with addresses written out, the links in them with the rows they name (for chips), and the day it was last told - sealed with an HMAC under the chat key and the address asked as (`sealed.go`), and sent back by the browser unchanged; a request carrying one that fails the seal is refused with a word to start a new chat, and one carrying none (a new chat, or one from before prompts were carried) has its prompt built from the person and the documents `known` names; `context` goes back to the model as it saw it, with the addresses shortened again (Links, below), so it reuses what it already looked up rather than looking again; and a chat with no `context` is a new one, whose `known` starts as the recent documents its prompt lists. A document joins `known` only once a turn naming it succeeds, so a failed turn names it again on the next. Since nothing is held, a restart or deploy loses nothing, two devices are two records, and a request is the person's own whoever's transcript it carries: the prompt and every tool bind to the signed-in viewer, and an answer reaches nobody but them, so a transcript the browser makes up can steer the model for nobody but its maker. Nothing is written to any sheet or bucket.

Every limit is a constant, and the constant is the only statement of it: the const block at the top of `internal/ask/ask.go` holds how long a message may be, how many questions a conversation takes, how long a conversation may run in all - runes across `context` as the browser sends it, questions, answers, tool calls and results alike, which is what bounds what any request can put in front of the model - and how long a turn may run; `perHour` in `internal/claude/limit.go` holds how many calls to Claude a person may make in an hour, one window counted across Ask's messages and Loop's and Staff Birthdays' Generate buttons alike, held once in `internal/app/wiring.go` and handed to each; `maxRounds` and `maxTokens` in `claude.go` hold the tool rounds a turn takes and the output tokens a call may write; `maxToolOutput` in `tools.go` holds what a tool result may run to, past which the tool answers with a word on narrowing the search rather than the data; and `maxChats` in `web/ask/app.js` holds how many chats a browser keeps - or as many as its local storage takes, the oldest dropped one by one when a save runs past the browser's quota.

## The tools

The tools are the shared set (`docs/tools.md`), the ones Helios MCP serves. `definitions` offers each to the model with its name, description and the `properties` and `required` of its JSON Schema, and `turn.run` runs one through `tools.Set.Run` with the viewer the session resolved, never one from the model's arguments, on the model as it stood when the turn began. The words the page shows for a lookup are the tool's `Words`, named once per turn however many times the tool ran. A result past `maxToolOutput` is refused with a word on narrowing it.

Every `href` a tool wrote for a person or group is noted with the row it names (`Answer.Links`), for the rest of the request, and so is every link the prompt writes; a chip is that row read again as the person asking (`linkCard` in `internal/ask/cards.go`), and a link nothing noted gets no chip.

Dates are Claude's to weigh against today, which the prompt names. A document's age in the prompt's lists is reckoned here (`timing`). `helios_search` calls out - one embedding request to Vertex AI for the words, made on the tool's context, which is the turn's, so a turn that times out ends it too.

## Links

Claude never reads or writes a web address. Every address it is shown - in the prompt, in the person's question, in the system message naming new documents, in every tool result and tool error, and inside a document's markdown - stands as a key: `L` and the first eight hex digits of the address's SHA-256 (`internal/ask/links.go`), so the same address is the same key in every conversation and on every request, and nothing about the keys has to be kept. Each request keeps a table of the addresses it shortened, which is what its keys expand through. The prompt tells Claude to link as `[the words](L3f2a9c01)`, and never to write out an address or make one up. A link then costs Claude a few tokens rather than the dozens a long address takes, which is what kept the page waiting after a link's words, and it can only point at something it was given: a key the table does not hold is logged as an error and left as written, and an address or a link target Claude wrote out is logged and dropped from the page.

A tool's input has any value that is a whole key put back as its address before the tool runs. Tool results are encoded without HTML escaping, so an address in them reads as it is and is found whole.

On the way out, the text stream holds back a tail that could still be the start of a key's link target - a `]`, then `(`, `L` and hex digits, and a quoted title after them - until it closes or cannot, and every `](Lkey)` is put back as its address before the piece goes to the page, anything Claude wrote after the key inside the parentheses - a markdown title (`](Lkey "")`) or words of its own (`](Lkey — see below)`) - dropped, since the page draws only the address, and held back while it streams for up to a hundred and twenty characters on the line; whatever is held goes out before a lookup's chip, so the order stands. The whole answer in `done` is expanded the same way. The messages `done` hands the browser for its `context` are expanded another way, every string of them but a thinking block's - the question, the answer, tool inputs and tool results - with each key put back as its address wherever what follows the key could not be read as more of an address, so that shortening the message again gives exactly the bytes the model wrote and a thinking block's signature still holds; a key that could not be expanded that way stays a key in the browser's copy, harmlessly. The browser and its stored chats otherwise see only real addresses, and no table travels with them.

## Sample and tests

The sample server and the tests reach no Claude: `intercept.Claude()` answers `api.anthropic.com` in-process, calling the first tool offered and then streaming a canned answer, so the page, the chips and the stream can be tried through the real client. The tests in `internal/ask` load the sample data model (`sampledata/data*/`) and the shared tools the way the server does, with Ask's and the tools' today pinned to 2026-09-28 (`Sources.Now`), three days after the sample's mail, so what counts as recent does not move with the clock; what each tool answers is pinned in `internal/tools` (`docs/tools.md`). Ask's pin the prompt for the sample parent and for someone the directory does not list, the school as the data model has it, the recent mail it lists and none for someone who may read none, mail filed mid-conversation named once in a system message after the question, every tool offered with its schema, a link's chip as the viewer reads it, tinted for a classroom, none for someone who may not read the row and none for a link no tool gave, the prompt's link examples covering every kind of chip and saying what each shows, tools run together without sharing state (run under `--race`) and their links noted for chips, the stream over the intercept, its tool round included, with the messages and the known document ids handed back and carried into the next turn as the browser carries them, a browser's context read with its addresses as keys and the recent mail told of when it knows none, a stopped answer left to the browser, and the limits. Those in `links_test.go` pin addresses shortening to keys and keys expanding back in text and in a tool's input, every key expanding for the browser only where shortening gives the same text back, a thinking block left as it came, a context reading in with keys and writing out with addresses, and a key split across stream pieces coming out whole and before the chip that follows it.
