# The resource API

One data-centric API, served identically on every app's host, that pages compose instead of each app's own `/api/<app>/` routes. `internal/api` is the machinery and knows nothing about any app; `internal/model` declares the types and builds the registry, `api.Registry[*model.Model]`, over the one store (`model.NewRegistry(store, queue, calendarHooks, partiesHooks, activitiesHooks, homeHooks, feedbackHooks, documentFiler)` in `internal/model/resources.go`). Which types are registered is the list `NewRegistry` gathers: `DirectoryResources`, `BirthdayResources`, `EmailListResources`, the calendar's, Celebrate's, HCA-Team's, Heliosian's and the feedback queue's `Resources`, `MagicTagResources` and `DocumentResources`. Each `Hooks` is what the app's `Register…` answers when `internal/app` wires its routes (`RegisterHome` for Heliosian, `RegisterFeedbackAdmin` for the feedback queue).

## The model

Every type reads the store's one `model.Model` (`docs/storage.md`, Store). `store.Queue.OnSwap` runs its hook under the commit lock after every commit's swap and every refresh's swap, and the hook publishes the store's current model to the registry (`Registry.Publish`), which also builds the alias index then. A request takes the published model once and reads nothing else, so a batch answers from one consistent world. A write reads the model as its transaction has staged it (`Config.Staged`, which is `Store.In`), so each write in a batch sees the ones before it.

Every request then reads the model through its scope (`Config.Scope`, which is `(*Model).at` in `internal/model/scope.go`): a copy of the model with a fresh `scope` holding the request's time, made once from the request's query before anything is read, and dropped with the request. The scope holds what a type works out from the query, each worked out lazily, the first time anything in the request asks: Loop's membership of every email list and its suggestion keys, When's viewer events, guest-list and feed indexes and responses, HCA-Team's widget lists, Heliosian's links and categories as the viewer is shown them and their school email, and the email lists whose mail the viewer may read. Every `Has`, `Get`, `List`, relation, filter, `Can` and `Do` of the request - a whole batch of reads, or each write of a batch over what the writes before it staged - gets that scope, so whatever a type works out from the query, it works out at most once per request and at the request's own time. `Registry.Taken` outside a request scopes the model at the current time. The per-app routes not on the API read `Store.Model()`.

## Types

Every type is declared in `internal/model`, in each app's `<app>_resources.go`, as `api.Type[*Model]` against the one model. The helpers every app's types share are in `internal/model/resources.go`: `logAfter` (a log line in `Tx.After`), `Store.stage` (stage a write's operations into its sheet), `permitted` (a rule's error as a `Can`) and `Model.personID`. A type has:

- `Shape` - a zero value of the struct `Get` answers, required at registration. A `Get` answering any other type fails the read, so the spec below always matches what is served.
- `Has` - whether an ID is one of its rows, whoever is asking.
- `Get` - the row as the viewer may see it, after the owner's redaction rule, or false when they may not see it at all. Its JSON is the resource's fields; the envelope adds `id`, `can` and any included relations.
- `List` - the IDs of the collection the viewer may see.
- `Aliases` - alias to ID: slugs for friendly URLs and IDs the row used to have. Aliases only name public addresses; references between rows are always IDs. An alias is unique within its type; the owner's load refuses duplicates.
- `Relations` - name, target type, one or many, and the function listing related IDs for the viewer. Every type reads the one model, so a relation may target any app's type.
- `Filters` - named functions narrowing a collection. A filter the owner didn't declare is a 400. `include`, `limit`, `can` and `mine` are the API's own and can't be a type's.
- `Rankers` - named functions that answer a collection in an order of their own, each ID with a `score` (`api.Hit`), in place of `List`. A ranker is handed the query's filters as one predicate and ranks only what passes them, so a filter narrows what is ranked, not just what is shown.
- `Actions` - each a `Can` rule and a `Do` handler, both required at registration, so a button can't exist without its route or a route without its flag. `can` on a resource is every action's `Can`.
- `Create` - optional.

## Reads

- `GET /api/{type}/{id-or-alias}` - a path segment resolves as an ID of that type, then as an alias of it. IDs parse case-insensitively.
- `GET /api/{type}?{filters}` - a collection. Besides the type's own filters, `can=<action>` keeps what the viewer may do that to, `mine` keeps what the resource's `me.mine` says is theirs, and `limit=N` keeps the first N after ranking and filters. One of the type's rankers may be named too, at most one a read; the collection then comes in the ranker's order, and its `result` is a list of `{"id", "score"}` rather than of IDs.
- `GET /api/r/{id}` - any resource by ID, whatever its type; IDs are unique across every type. Aliases don't resolve here.
- `POST /api/query` with `{"name": {"path": "/api/..."}}` - several reads from one model, one set of `resources`.
- `include=a,b.c` on any read - dotted relation paths. An include only reaches what a direct fetch would.

Every read answers `{"now", "result", "resources"}`: `now` is the server's clock in the school's zone, `result` the ID or IDs the read answers with, in the type's order (by read name in a batch), and `resources` every resource reached, the result's and those its includes brought in, keyed by type then ID, each once.

`GET /api/me` answers the viewer's address, `email`, and every allowance they hold, `allowances`, a plain list of names.

Inside the server, `Registry.Read(request, paths)` is `POST /api/query` without the HTTP: the same envelope for the same named paths, read as the request's viewer at the API's time from the published model, so a caller reads exactly what that viewer's pages read. `Registry.Actor(request)` is the viewer it reads as. Helios Ask reads everything through them (`docs/ask/data.md`).

This API has no OpenAPI description; `/api/openapi.json` describes the data model's query API that replaces it (`docs/admin/admin.md`, The spec).

## Writes

`POST /api/{type}` creates and answers the new `id`; `POST /api/{type}/{id}/{action}` acts, answering nothing, or the new `id` for an action that makes something; `DELETE /api/{type}/{id}` is the `delete` action. The resource must be visible to the viewer. `POST /api/act` takes a list of writes, each `{"method", "path", "body"}` in the same forms, and runs them in order as one change: all go in or none do, a refusal naming the write that failed, and the answer lists each write's result (`id` for a create). A single write is a batch of one.

An action is built with `api.Do(can, do)` and a create with `api.Make(do)`, where `do` takes an `api.Write` and the body already decoded into its own input type; `serve.None` is an action that takes no body. `api.DoFrom(can, seed, do)` decodes the body over what `seed` answers, so fields the client leaves out keep their current values. `api.DoMaking(can, do)` is an action that makes something, its `do` answering the new ID, so the `can` for making a thing can sit on the resource it is made under. The input type is also the operation's request body in `/api/openapi.json`. An `api.Write` holds the request, the transaction, the model as the batch has left it, the query, the resolved ID, the raw body and `Taken`, the check a minted ID must pass. Handlers call the package's `writes.go` and stage its operations into the transaction (`Store.Stage`, `docs/storage.md`), never commit; mail and logging go in `Tx.After`, which runs only once the change is in (`docs/dev.md`, The rules live with the thing).

## Client

`web/common/data.js`: `query(path)` and `batch({name: path})` each answer a result of their own, holding that read's `result` and `now` and `get(id)`, `all(type)` and `follow(resource, relation)` over that read's `resources` only. There is no page-wide store: a page keeps its read's result and replaces it when it reads again, and a picker keeps its own, so no read ever disturbs another. `act`, `create` and `remove` write, and `actAll` sends a batch to `/api/act`, after which the page reads again; `me()` is `/api/me`.

`web/common/directory.js` is the directory every picker, the person window and Spoof Mode read, in every app, from the data model rather than these types: `directory()` reads, once per page, through `/api/q`, everyone in the `everyone` group who is not hidden, their primary addresses, their ready photos, family memberships, the students, parents and staff role groups' effective members, and the grade, classroom and department groups. `listed()` is those `PERSON` rows as they are; `known(email)` and `personByEmail` find one by address, `emailOf`, `photoOf` (their own photo, else their family's), `gradeOf`, `placeOf` and `wordsOf` read one, `isStudent`, `isParent` and `isStaff` place them, `relativesOf(p, parents|children|partners|siblings)` reads their families, `profileLink` is their Who? page (by `slug`, else ID), and `contactLine` is the line under a name (a student's grade and classroom, a parent's children, anyone else's words).

## Staff Birthdays

`internal/model/birthdays_resources.go` registers `birthdays`, `donations`, `birthday-notes`, `charities`, `newsletter-dates`, `birthday-team`, `birthday-settings` and `birthday-invites`, reading the directory through the index the Birthdays part builds when it loads (`staffEmails`, `staffKeys` and `staffOrder` on `model.Birthdays`), since the part reads the directory (`docs/storage.md`, Store). Everything but the settings is seen by the birthday team only (`Birthdays.Sees`); anyone may read the settings resource, which answers how the viewer stands with the team (`me`) and the viewer's own person (`viewer`), and carries the settings themselves for the team alone. A birthday is one per directory-listed staff member, whether or not the sheet has a row for them yet (`missing`), and resolves by the person's addresses and slug; its dates, `stage` and `urgency` are the server's. `late` is the step the viewer owes that is past its day, with that day (`step` one of `info`, `outreach` or `newsletter`, and `due`; `lateFor` in `internal/model/birthdays_late.go`, `docs/toolbar.md`, Late birthdays), there only when there is one, and `birthdays?late` keeps the birthdays that carry it. `next` is the step a birthday waits on and its day (`step` `outreach` by the day to ask, `info` by the day the charity is due, `newsletter` on the issue), absent once it is complete. Heliosian's Birthdays widget reads two ordered relations of `birthdays` on the settings (`internal/model/birthdays_widget.go`): both reach only the birthdays whose newsletter is one of the next two issues from today: `mine`, the viewer's assignments waiting on an outreach or charity step, by that step's day; `all`, for a birthday admin alone, everyone in the pipeline, by issue. A birthday's relation `fallback-charity` and its `fallbackNote` are what the newsletter copy uses when no charity is recorded for the year: last year's charity and note while that charity is still allowed, else the `Default Charity` setting's charity and no note (`Birthdays.fallback`). A donation, a note and a team row have IDs derived from their keys; charities, newsletter dates and invites are minted, and charities and newsletter dates resolve by name and by date. Invites are created, never edited or deleted: the server fills in each one's sending.

## The directory

`internal/model/directory_resources.go` registers `people`, `families`, `classrooms`, `grades`, `crews`, `departments` (in the directory's order) and `tags`. Every member sees all but the tags, as every member sees Who?: consent masking and opt-outs are applied when the directory loads, so no rule depends on the viewer. A person with no real address has no `email` and is left out of `people?listed`. A person resolves by their address, any Email Aliases address of theirs, and their `slug`, the part of their address before the @, unless someone else's address has the same part, when only the full address resolves. Classrooms and grades resolve by the slug in their Who? page's path; `grades?enrolled` keeps the grades some student is in.

`people` filters: `q` (words of a name, preferred name, job title or shown address), `role` (`student`, `parent` or `staff`), `grade` and `classroom` (by name; a student's or staff member's own, and a parent's through their children, as Who?'s filters read them) and `department`. `families` filters: `q` (the family's name or a member's), `classroom` and `grade` (a student of the family's in it).

A tag is seen by its owner and the people they share it with, and only while it holds someone: `tags` lists the viewer's own, then those shared with them, with `me.mine` saying which, its Who? page as `path`, and relations `owner`, `people` and `managers`. A rule names a tag as `tag:<id>` (`docs/loop/loop.md`, A rule discloses the tags it names).

A family carries `veracrossAddress` and `veracrossPhone`, how Veracross shows its address and phone, which the map and My Privacy read. A grade's `room-parents` are the room parents of its band, and a person's `room-parent-for` the grades whose band they are a room parent of. A classroom carries its `band` and the `grades` of its students (`Directory.Roster`), with relations `students`, `crews`, `teachers` (its crews' teachers and the staff placed in it) and `room-parents` (its band's).

## Helios Who?

Who? is on the data model and uses none of the types above. A page loads everything it needs in one named batch to `/api/q`, writes with `POST /api/q` batches, and adds photos and recordings through `/api/do/photo` and `/api/do/pronunciation` (`docs/datamodel.md`, The query API). Its server adds only `GET /maps.js`, the browser Maps key as `export const mapsKey`, and the page routes (`internal/who/who.go`). Loop's pages are on the data model the same way: one named batch to `/api/q` for every list the viewer may see with its members, hand additions, rules, aliases and managers, `POST /api/q` batches for every change, and `/api/do/draft-members`, `/api/do/describe-group` and `/api/do/guest` for the editor (`docs/datamodel.md`, The query API).

The directory types above are the old directory, read-only and frozen since Who? moved: nothing writes their sheet but the geocoder. The apps still on the old model read them - Loop and Heliosian's rule editors `classrooms`, `grades?enrolled` and `tags`, Staff Birthdays `departments` - and `people` and `families` are reached as relations of other apps' types.

## Magic Tags

A Magic Tag is a group of people worked out from something a person runs, which that person holds and may name in a rule or a picker: a grade band's parents for its room parents (`room:<band>`), a party's ticket holders and buyers for its hosts (`party:<id>`), an activity's volunteers, and those under it, for its co-chairs and those of anything above it (`activity:<id>`; a Team admin holds every activity's), and an email list's members for its managers (`group:<id>`). `Model.MagicTagsOf` in `internal/model/magic_tags.go` is the one rule, and rule evaluation, the rule editors' options, Who?'s Lists and Ask all read it. A rule may name an email list's Magic Tag; saving an email list whose rules would have lists name each other in a circle is refused.

`internal/model/magic_tags_resources.go` registers `magic-tags`: the Magic Tags the viewer holds, each ID derived from its key and the key itself an alias (`/api/magic-tags/activity:<id>`). Fields `key`, `name`, `kind`, `slug` (an email list's name), `archived` (a past party or activity, or an email list the viewer archived), `guests` (people outside the directory, by name) and `path`, its list on Who?. Relations `people` (the members in the directory), `holders`, `parent` (the Magic Tag of the activity above), `email-lists` (the email lists whose rules name it) and what it is worked out from, `party`, `activity` or `email-list`.

## Helios Loop

`internal/model/email_lists_resources.go` registers `email-lists`, `email-list-members`, `email-list-messages`, `email-list-copies`, `email-list-suggestions` and `loop-settings`, reading the Loop model, the directory, the grade colours and the managers' Magic Tags, through `Model.Audience`, by `Model` methods in that file (`listSources`, `listPlacement`, `listMembers`, ...).

- **Membership** is worked out in the request's scope (The model, above), at the request's time, for every email list together the first time anything in the request asks (`Model.listPlacement`), so a page listing every email list with its members evaluates the rules once. Magic Tags of parties and activities depend on the time: a past party has none.
- **`email-lists`** is every email list the viewer sees (`docs/loop/loop.md`, Visible). An email list resolves by its name and each of its aliases; `slug` is the name. `rules` (each with its `tagLabels`), `additions`, `excluded` and `sent` are there for its managers and the app's admins alone (`EmailList.Sees`). `memberCount` is the members as the rules, additions and excluded list pick them out now; `me` says whether the viewer manages it, whether the rules or additions place them on it (`member`, whatever the excluded list says), whether they are on its excluded list (`unsubscribed`) and whether they have archived it. A manager the directory does not hold is in `managersOutside` rather than the `managers` relation. Relations `managers`, `members` and `messages`. `q` keeps those whose title, name or description holds the words.
- **Writes** on an email list: `POST /api/email-lists` makes one with every field; `edit` lays the fields it is sent over the email list as it stands and saves the whole, writing only what changed (`groupOps`), so the Managers box sends `managers` alone; `delete` removes its posts from Helios Ask once the change is in; `unsubscribe` and `resubscribe` add and remove the viewer's own excluded row, for someone the email list places on it; `archive` and `unarchive` are the viewer's own. Each refuses what would change nothing, so its `can` is exact.
- **`email-list-members`**: one per email list and member, ID derived from both. A directory member is its `person` relation; an addition carries `email`, `name` and `outside`. `reasons` - the rules or the addition that put them on - go to the email list's managers and the admins alone.
- **`email-list-messages`** and **`email-list-copies`** are History: each `sent` message with its delivered, failed and pending counts, its `sender` (or `fromEmail` and `fromName` when the directory does not hold them) and its `copies`, failed first, then pending, then delivered; a copy has its `state`, `when`, its `attempts` and its `person` (or `email`). Managers and admins alone see them. IDs are derived from the email list, the message's row and the address.
- **`email-list-suggestions`**: the viewer's own suggestions (`docs/loop/loop.md`, Suggestion), each an ID derived from the tag's or Magic Tag's key, with the `managers` the email list would start with and, for a Magic Tag's, its `magic-tag`.
- **`loop-settings`**: one resource for everyone, answering the domain, the grade colours, the roles and relations a rule offers, and the `viewer`. The editor reads the Magic Tags a rule may name from `/api/magic-tags` (Magic Tags, below).

Preview and Generate with AI read an unsaved draft and stay Loop's own routes (`POST /api/loop/preview`, `POST /api/loop/describe`); the preview answers each member's address and reasons with a directory member's person ID, or an addition's name.

## Helios When

`internal/model/calendar_resources.go` registers `events`, `guest-lists`, `invite-groups`, `calendar-feeds` and `when-settings`, and `calendar_days_resources.go` `day-types`, reading the When model, the directory, the settings, and the linked Celebrate parties and dated Team activities (`Model.LinkedEvents`), at the request's time, through `calendarApp` pinned to the request's scoped model (`calendarApp.at`). The viewer's events, the guest lists' and feeds' IDs and everyone's answers are each worked out once per request, the first time anything asks.

- **`events`** lists the viewer's calendar (`EventsFor`: the linked events and those their answers fold in among them, and the pending ones they shared, or every pending one for an admin); any event the viewer may open reads by its ID or any alias - the `Aliases` tab's old IDs and its address - on or off that list (`docs/when/calendar.md`, Who can see an event). `path`, `app` and `slug` are the event's page; `hosted` and `hostNames` are the viewer's; `me.answer` is the viewer's answer. `provenance` and `adminOnly` (an event the admin opens only as an admin) go to admins alone, `responses` to its poster and admins. Relations `hosts` (people), `guest-list` and `day-type`; the classrooms among its tags are its `classrooms`.
- **Filters** on `events` narrow the viewer's calendar, never reach past it: `from` and `to` (dates, `YYYY-MM-DD`) keep what ends on or after `from` and starts on or before `to`; `calendar=<calendar-feeds id>` keeps what that calendar of the viewer's admits (`InView` under its classrooms and tags - My Heliosian's being the viewer's own view - with a yes under Going and an invitation always in, and what the viewer said no to or hid always out), and refuses a calendar that is not theirs; `waiting` keeps the invitations still to answer (invited, not cancelled, unanswered, not past, not one the viewer hosts); `app=<key>` keeps those whose page is on that app (`when`, `celebrate` or `team`, `EventPage`); `status=pending` keeps what waits for approval (not declined or cancelled); `q` keeps those whose title, description or keywords hold the words; `classroom=<name>` those for that classroom and those for everyone; `tag=<name>` those filed under that category or classroom. Heliosian's rail and Upcoming read `events?from=&to=&calendar=`, its toolbar's RSVP badge `events?waiting`, its Celebrate widget `events?app=celebrate&from=<today>`, and the approvals badge `events?status=pending&can=approve` (`docs/toolbar.md`).
- **Writes** on an event: `POST /api/events` adds one (or a repeat of them) and answers the first's `id`, with the host's own yes staged in the same change. `edit`, on a hand-added event, and `correct`, on an imported one's `Overrides` row, are partial: the fields sent are laid over the event as it stands and only their columns written. `image` sets an imported event's picture, for an admin or a host; `keywords`, `approve`, `decline` and `move` are an admin's; `cancel` is a host's, on a hand-added event; `answer` is the viewer's own and `answer-for` someone they answer for. `invite`, `uninvite`, `bring-guest`, `settings`, `step-down`, `send`, `skip`, `message`, `change-email`, `delete-invitation` and `start` are what a host does with the guest list (`bring-guest` and `invite` also whoever the hosts let invite). Mail goes out from the recorded state once the change is in, never from the write (`docs/when/calendar.md`).
- **`guest-lists`**: one per event that keeps a guest list, ID derived from the event's, and read through its `guest-list` relation. It is the invitation as the viewer may see it (`inviteView`); `attendees` and `onList` go to someone who may invite, and on a party `ticketHolders` to the hosts. Reading writes nothing: `opened` stamps the viewer's Opened, and its `can` holds only while that would write something. Relations `event` and, for the hosts, `invite-groups`.
- **`invite-groups`**: an event's rules, seen by its hosts, with `count`, the people each put on. `POST /api/invite-groups` takes the event's `id`, the `rule` and `auto` and answers the group's `id`; `edit` sets `auto`; `DELETE` takes the group off.
- **`calendar-feeds`**: the viewer's calendars in their order, My Heliosian among them, each ID derived from the owner and its token; `url` is the `/open/feed/` address, My Heliosian's once its token is made. `days` holds every school day in the school calendar, date to the kinds of day it is for that calendar's own classrooms other than Regular, each `name` and `words` as the day words are ("Early Dismissal · Hummingbirds" when only some of them; `dayKinds` in `internal/model/calendar_month.go`): an empty list is a regular day, and a date not there is outside the school calendar. Heliosian's rail month and Upcoming's day bars read it from the calendar picked. Created with `POST /api/calendar-feeds`, `edit` partial; `delete` refuses My Heliosian (`locked`).
- **`when-settings`**: one resource for everyone, answering the parts of the page that are not events - the `user`, classrooms, colours, tags, day types, years, days, grade colours, names and whether image search is on - with relations `feeds` and `viewer`. Its actions are the viewer's own: `save-view`, `forget-view`, `order-feeds`, `default` and `feed-token`, and `tags` for the calendar's admins. The calendar page reads it and `/api/events` in one `POST /api/query`.
- **`day-types`**: the Day Types tab, read-only, in its order.

Group preview, the rule editor's options and image search read drafts and stay When's own routes (`POST /api/when/invites/preview`, `GET /api/when/invites/options`, and the image routes under `/api/when/`).

## Helios Celebrate

`internal/model/parties_resources.go` registers `parties`, `tickets`, `celebrations`, `party-categories`, `celebrate-settings` and `celebrate-addresses`, reading the Celebrate model and the directory, and the calendar for a party's guest list answers.

- **`parties`** lists every party the viewer may see (`Party.VisibleTo`: an open one, or any the viewer hosts or an admin sees), dated or not, in date order; `?celebration=<id>` keeps one celebration's, `?q=` those whose title, subtitle, summary or category holds the words, `?past=true` or `false` those that have or have not happened by the query's time, and `?status=pending` the ones waiting for approval (the toolbar's approvals badge reads `parties?status=pending&can=status`). A party's resource ID is derived from its Party ID, since a dated open party's Party ID is already its `events` ID; the Party ID is `partyId`, and it, the party's friendly address, its old IDs and the Redirects tab's old addresses all resolve as aliases. The fields are the party as the viewer may see it (`Party.For`) with its ticketing: `availability`, `sold`, `remaining`, `waiting`, `raised`, the hosts by face, `attendees` and `waitlisted` (each with its ticket's `ticketId`), `hosting`, and for the hosts and admins `started` and `invited` (its guest list on Helios When) and each attendee's `rsvp`; `path` is its page; `admits` is who in the viewer's household the party takes and who holds no ticket yet. Relations `event` (the party on the calendar, when it is there), `hosts`, `tickets`, `celebration` and `category`.
- **Writes** on a party: `edit` is partial (only the fields sent are written, `hostEmails` included; someone who is not an admin is refused a `status`, `celebration` or `category` that differs from the party's); `delete` and `status` are an admin's; `buy` takes tickets (purchaser, note, the attendees, and for a host `free` and `raiseCapacity`, or `invoice`, the adult a paid ticket is billed to) and `join-waitlist` asks for places, or changes the viewer's family's request. The confirmation, the calendar invite and the waitlist note to the hosts are mailed from the write once the change is in.
- **`tickets`**: one per Tickets row, ID the Ticket ID (old ticket IDs resolve), each the attendee as the party shows it. `edit` (the note, or a waitlist request's quantity), `delete`, `reassign` (who holds a sold ticket) and `offer` (a host lets a waitlist request's family buy that many tickets past the party's status, as an `Offered` ticket that `buy` counts down and `delete` withdraws). A party's `offered` is how many its viewer's family may buy that way.
- **`celebrations`** (the code resolves) and **`party-categories`**, in their order: created, `edit`ed partially and deleted by an admin; a celebration or category a party names can't be deleted.
- **`celebrate-settings`**: one resource for everyone: the viewer's `user` and household, `today`, the settings, the `current` and `banner` celebrations, `billable` (whom the viewer may bill a ticket to), `imageSearch`, and `invoicing` for admins. Actions: `host` posts a party (anyone while hosting is open, else an admin; a party posted by someone who is not an admin waits as Pending), `settings`, `order-categories` and `move-address` (an admin moves an address the directory does not hold on every party, and on its guest lists on Helios When).
- **`celebrate-addresses`**: the Addresses panel, `problems` and `moved`, for an admin who may move addresses.

The invoicing CSV (`GET /api/celebrate/invoices.csv`) and image search stay Celebrate's own routes.

## HCA-Team

`internal/model/activities_resources.go` registers `activities`, `volunteers`, `activity-links`, `activity-categories`, `team-settings` and `activity-redirects`, reading the Team model and the directory, the email lists for an activity's list, and the calendar for its event and guest list answers. A volunteer's ID and each activity's event are worked out once per request, the first time anything asks.

- **`activities`** lists every activity the viewer may see (`Activities.VisibleTo`), flat, in the tree's order, each naming its `parent`; old IDs and an event's friendly address resolve. The fields are the activity as the viewer may see it, with `taken`, `full` (every spot taken, or Volunteers Complete), `past` (Done, or its own or inherited end or start before the query's day), `path` and `app`; `started` and `invited` (its guest list on Helios When) for whoever runs it and the admins. `day` and `dayTiming` are its start day and free timing, its own, else those of the nearest activity above it with either; `picture` its own picture, else the nearest above it; `under` the titles of what it sits under, outermost first; `wants`, on an Open activity, what it still wants (the co-chair, else its first open role with spots and how many volunteers it and the roles under it need). `me.runs` is whether the viewer co-chairs it or anything above it, `me.position` the viewer's position on it when they are signed up. Relations `parent`, `children`, `volunteers`, `links`, `category` (the one it is in), `categories` (an event's own), and `event` (the activity on the calendar, when it is there). Filters `q` (words of its title or description), `year` (a school year, or `current`, the query's), `past` (`true` or `false`, as `past` reads) and `under=<id>` (everything below that activity).
- **Writes** on an activity: `POST /api/activities` adds one and answers its `id`; `add` adds one under it and answers the `id`, its `can` being whether the viewer may add there. `edit` is partial (`docs/team/data.md`, Saving an activity). `approve` (an admin, or whoever runs what a pending activity sits under) and `decline` (an admin) decide a Pending one. `delete` and `copy` (into next year, answering the copy's `id`) are an admin's; `order` and `order-categories` whoever edits it. `sign-up` takes the address, position, note and the activity a sign-up moves from; its `can` is whether the viewer may sign up as a volunteer. The thank-you, calendar invite, removal and admins' notices are mailed from the write once the change is in.
- **`volunteers`**: one per sign-up, ID derived from the activity and the address, read through an activity's `volunteers` relation, co-chairs first, with a hidden list already cut to what the viewer may see; `rsvp` goes to whoever runs it. `edit` changes the position and note, `delete` removes the sign-up; either is the volunteer's household's or an editor's. Relations `activity` and `person`.
- **`activity-links`** (created with the `activity` they sit on) and **`activity-categories`** (the page's, in their order, then each visible event's own): created, `edit`ed and deleted by whoever edits them. A category's `settings` sets an event category's volunteer flags, and its `add` adds an activity in it and answers the `id`.
- **`team-settings`**: one resource for everyone: the viewer's `user` and household, `years`, `today`, the settings, grade colours, `imageSearch`, the built-in `uncategorized` category when an event sits in it, `people` for admins, and `notify` (the viewer's notification kinds) for admins. Actions `settings`, `notify` and `order-categories` (the page's). Heliosian's Team widget reads its three ordered relations of `activities` (`widget` in `internal/model/activities_widget.go`, worked out once per request): `mine`, what the viewer is on this school year at any depth that has not passed or been marked done, by day; `needed`, the first twelve of the Volunteers needed order the viewer is not on; `priority`, everything marked a priority that still wants people and the viewer is not on, by day.
- **`activity-redirects`**: the Redirects tab, for admins, each ID derived from its old address; created, `edit`ed and deleted. Old and moved addresses are followed on the server before a page loads (`ActivitiesRedirected`).

Generate with AI (`POST /api/team/describe`), image search and the share cards stay Team's own routes.

## Heliosian

`internal/model/home_resources.go` registers `links`, `link-categories`, `apps`, `home-widgets`, `home-settings`, `school-emails`, `to-dos` (`todos_resources.go`) and `alerts`, reading the Apps sheet (`docs/home/data.md`), the directory and Helios Ask's documents. The front page reads them, with When's, HCA-Team's and the directory's types, in two `POST /api/query` batches (`loadModel` in `web/home/state.js`). Every write is a Heliosian admin's (`home.configure`).

- **`links`** lists the viewer's links as `HomeCategoriesFor` gives them, category by category in their order: a link that is visible and whose rules take the viewer in, or for an admin every link, hidden ones and those kept from them included, with its `rules` (each with its `tagLabels`) and `forMe` false on one kept from them. A link into a community app the `Visibility` tab keeps from the viewer is left out for everyone, admin or not: which app a link points into is worked out when the sheet loads, by matching its host against every app's hosts on each domain in `model.Domains` (`appOfLink` in `internal/model/home.go`), since a query carries no host. `order` is the link's key in its category (Ordering, below). Relation `category`; `q` keeps those whose title or description holds the words. `POST /api/links` adds one (title, description, url, image, category, visible, rules) and answers its `id`; `edit` is partial, the fields sent laid over the link as it stands; `delete`.
- **`link-categories`**: the categories the viewer is shown, in their order - the events and apps sections among them - with `rules` and `forMe` as a link's. Relation `links`, in their order. Created and `edit`ed partially as links are, the body's `sidebar` setting its widget's in the same write; `delete` only while no link names it, and never the events section.
- **`apps`**: Heliosian itself, then every community app in the switch's order, each resolving by its key as well (`/api/apps/when`): `key`, `name` and `tagline` (the Visibility tab's, else the registry's), `mark`, `order`, and `me.listed`, false when the tab keeps the app from the viewer. An admin also gets `visibility`, `emails` and `rules`. `edit` is partial and sets the app's Visibility row; Heliosian itself has no row and no `edit`. Every toolbar's app switch reads `/api/apps` (`docs/toolbar.md`).
- **`home-widgets`**: the front-page widgets in their order, each ID derived from its name and the name an alias (`when`, `team`, `celebrate`, `school`, `birthday`, `todo`, and `category:<Category ID>` for every category but the events section): `key`, `order`, `sidebar` (whether its first items go in the rail), `me.shown` (whether its rules take the viewer in) and, for an admin, `rules`. `edit` sets its rules, its order and `sidebar`; a category's widget's rules are the category's own.
- **`home-settings`**: one resource for everyone: `imageSearch`, the `roles` and `relations` a rule offers, `layout` (each row's split, from the Layout tab) and `layouts` (the splits a row can take), with relation `viewer`. `layout` sets the rows from a `rows` list of splits, writing only what changed. The rule editor's other choices are `/api/classrooms`, `/api/grades?enrolled`, `/api/tags` and `/api/magic-tags`, and each rule carries its own `tagLabels`.
- **`school-emails`**: the Inbox widget - the school's mail of the last `model.SchoolMailWindow` that reaches the viewer (`Documents.SchoolMail`, `docs/home/home.md`), newest first, each ID derived from its document's key: `title`, `date`, `time`, `kind`, `channel`, `audience`, `summary`, the email's one-sentence summary, `points`, `repeats`, each key point's number, 1 for the first, mapped to the ID of another email's to-do it repeats, and `to`, the chip's words for whom it went to.
- **`to-dos`**: the Reminders widget (`docs/home/home.md`) - the to-dos read out of the email that reaches the viewer (`docs/ask/artifacts.md`, Key points and to-dos), those still current or saved, by due day and then the undated, newest email first, each ID derived from its email's key and its title: `title`, `summary`, `details`, `link`, `due`, `email` (the `school-emails` ID of a school email's to-do) and `point` (the number of that email's key point it restates, absent when none does), `source` (the email's `title`, `date`, `time` and `to`, the Inbox chip's words, or an email list's title) and `me.state`, `done` or `saved` when the viewer marked it. `complete`, `save` and `clear` are the viewer's own marks, each `can` exact.
- **`alerts`**: one resource per viewer, the toolbar's `stale` and `privacy` lists (`Directory.Alerts`, `docs/toolbar.md`).

**Ordering is a field.** `order` on a link, a category, an app or a widget is its sort key (`docs/storage.md`, Order), and moving one is a partial `edit` sending `order` alone for the thing moved, the key the browser works out between its new neighbours (`movedKey` in `web/common/order.js`); the server refuses a key that is not one. A link or category created lands after the last of its list, and a link an `edit` moves to another category lands last there, whatever `order` it was sent.

Audience preview reads an unsaved draft and is Heliosian's own route (`POST /api/apps/audience/preview`, the thing's Audience key and its rules), beside image search (`/api/apps/image`, `/api/apps/images/…`) and the share card (`/open/share/apps.png`). When the server starts it writes a Visibility row for any app of the registry that has none, and a Widgets row for any widget that has none, each with a key after the last (`discover` in `internal/model/home_routes.go`, `docs/home/data.md`).

## Admin lists

`admin-lists` (in `home_resources.go`) is one resource per app's admin list (`adminApps` in `internal/model/model.go` lists them), each ID derived from the app's key and the key an alias (`/api/admin-lists/team`). It is seen, listed and written only by someone holding that app's `<app>.admins` allowance: `app`, and `admins`, the Admins tab's addresses and the platform super admins. `edit` takes `admins` and writes the tab to match, the super admins left out of it, since they stand on every list from the Config sheet. The super admins are a list of their own, `super`, seen and written only by someone holding `super-admins`, over the Config sheet's Super Admins tab, which may not be left empty; no page draws it. Every old app's Admin Tools card reads and writes its own list (`appAdmins` in `web/common/admin.js`, `docs/toolbar.md`, Admin Tools).

## Feedback reports

`feedback-reports` (`FeedbackHooks.Resources` in `internal/model/feedback_routes.go`) is the feedback queue (`docs/feedback.md`): one per report, ID the report's ID and its older IDs aliases, newest first, seen only by someone holding the `feedback` allowance, which the super admins hold. Each is the report as the row holds it - who, where and what they wrote, whether it has a `screenshot` - and `draft`, the issue as it would be filed with the personal detail taken out (`model.StripReport`) and the `repo` it goes to. `file` takes the draft as edited, opens the issue and marks the report Filed, its `can` false once filed or on a server with no GitHub App; `dismiss` marks it Dismissed. The screenshot itself is a byte route on Heliosian's host, `GET /api/admin/feedback/{id}/screenshot`.
