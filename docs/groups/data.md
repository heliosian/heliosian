# Data model

The tabs, columns, and validation rules are in `internal/groups`; this file carries only what reading that code cannot tell you.

The groups live in one Google Sheet, `Groups`, in the community shared drive, reached through drive membership like the other sheets. `GROUPS_SHEET` names it, and `cmd/createtabs` reads that variable to lay it out from an empty spreadsheet titled `Groups`, or to add the tabs and columns an older one lacks.

## Tabs

- `Groups` — Name, Title, Description, Created By, Created, Subject Prefix. One row per group. Name is the address's local part and the key of every other tab. Subject Prefix is `off` for a group whose subjects go out as written; blank, or anything else, means the title goes in front.
- `Managers` — Group, Email. One row per manager per group; every group needs at least one.
- `Rules` — Group, Kind, Roles, Search, Classrooms, Grades, Tags, Family, Owner. One row per rule, in the order the editor shows them. Kind is `include` or `exclude`. Roles, Classrooms, Grades, Tags and Family are comma-separated lists; Tags holds tag names, Magic Tag keys (`party:<id>`, `activity:<id>`, `room:<band>`) and shared tags (`shared:<owner's address>:<name>`, one the owner has let the rule's Owner manage) alike, read as Owner's. A tag with a comma in its name cannot be used in a rule. Every group needs at least one include rule, and every rule at least one of the facets.
- `Additions` — Group, Email, Name. One row per person added by hand from outside the directory (`groups.md`, Addition). Email is lowercased and must be an address; Name may be blank, the address standing in for it. A group holds at most two hundred, once each by address. The load never asks the directory about them, so an address that has since joined the directory is not a refused load; the app refuses one at save alone.
- `Unsubscribed` — Group, Email, Timestamp. One row per person who unsubscribed from a group (`groups.md`, Unsubscribed), the address as the copy was sent to it and when they asked. The evaluator leaves them off the group whatever the rules and additions say; a manager's Remove in the editor deletes the row.
- `Messages` — ID, Group, Received, From, Subject, State, Recipients, Object, Detail. One row per message per group it was addressed to, keyed by ID (Resend's id for the received message) and Group: when it came, who from, the subject, where it stands (Mail, below), how many copies went out, the archive object holding it whole, and what went wrong or why it was dropped. Written by the server alone and read back only to resume what a restart cut short; the archive it indexes is the record.
- `Deliveries` — Timestamp, Group, Email, Event, Message, Detail. One row per copy Resend could not deliver as sent: which group's, to whom, what happened (`bounced`, `complained`, `delivery_delayed`, `failed`, `suppressed`), Resend's id for the copy, and its words. Appended by the server, never edited; the group's page shows the last twenty for it.
- `Admins` — Email. Who sees and may change every group, beyond the platform super admins (`docs/config.md`).
- `Change Log` — Timestamp, Actor, Action, Group, Detail. Appended on every save, delete and unsubscribe; never read back.

**A load either succeeds whole or refuses**, the stance every app takes: a group with no manager or no include rule, a rule, addition or unsubscribe naming a group the sheet does not have, an unknown kind, role or relation, or a name that cannot be an address refuses the load, so a hand edit that breaks a rule surfaces as a refused start or a failed refresh rather than a group quietly matching nobody. The app checks the same rules before it writes, so nothing it saves can refuse the next load. `Messages` and `Deliveries` are records, not rules: a row of either naming a group since deleted is kept and ignored.

**Saving rewrites a group's rows whole.** A save upserts the group's `Groups` row and replaces its `Managers`, `Rules`, `Additions` and `Unsubscribed` rows, so the sheet's rows for a group are always exactly what the editor last held. A delete removes all five; its messages and deliveries stay.

## The membership

A group's members are never stored. They are computed from the directory model, the owner's tags (`Cache.Tags`, or `who.TagsOf` over the tab for a tool), the tags shared with them (`Cache.SharedTags`, or `who.SharedTagsOf`) and their Magic Tags (`app.SmartLists` plus the directory's room-parent lists) whenever anything asks: the group's page, the editor's preview, every forward and `cmd/loadcheck` all call the one evaluator in `internal/groups/eval.go`, a port of Who?'s client-side filter with the same reading of a parent's grade and classroom through their children. The rules' result is then unioned with the group's additions, each on once by address whatever the exclude rules say, with `Added` as its reason, and the unsubscribed taken away last. The tests pin it to the sample community.

The group's Magic Tag in Who? (`GroupLists` in `internal/app/lists.go`) sorts the same members by whether the directory holds them: the directory's people are the list's People, and the rest are its Guests under the name the manager typed, keyed `<group name>:<address>` - the one `who.Guest` shape a party's ticket holders outside the directory use, keyed by the ticket there.

## Mail

**Receiving.** `loop.heliosian.com` is a domain verified in Resend for sending, with receiving enabled on it: its MX record points at Resend (the one Resend's Domains page shows, which must be the domain's lowest-numbered MX), so every message to any address under it lands at Resend, and a webhook on the `email.received` event calls `POST /api/loop/mail` (public, signed the Svix way with `LOOP_WEBHOOK_SECRET`, `internal/mail/receive.go`; `docs/deploy.md`). The webhook carries only the message's id, sender, recipients and subject; the message itself is fetched back from Resend by its id, raw, up to forty megabytes. Resend's webhooks are account-wide, so the calendar's reply webhook sees Loop's mail and this one sees the calendar's replies: each reads the recipients in the event and takes only what was sent to its own addresses. Loop takes every recipient under its domain - the `to`, `cc`, `bcc` and `received_for` lists together - that names a group in the sheet, and logs and ignores the rest.

**The pipeline.** For each group a message was sent to, the handler records a `Messages` row in state `received` and answers 204 at once, so Resend never waits on the work; Resend delivers each event at least once and retries a slow answer, and the row, with an in-memory record of what this process has handled, is what makes a second delivery of the same event do nothing. One worker (`mailer` in `internal/groups/mail.go`) then takes the messages in turn: fetches the raw message, drops it if it is one Loop already sent, auto-submitted or a mail system's notice (state `dropped`, with why); writes it whole to the mail bucket as `loop/<group>/<time>-<id>.eml` (state `stored`, the object named in the row); rewrites the headers (`groups.md`, Mail; `rewrite.go`); works out the members as they stand; and hands Resend one copy per member over its SMTP relay (`mail.Relay`, implicit TLS on 465, the API key as the password - the relay takes the message as bytes, so the body, the attachments and the threading headers go through untouched, where the HTTP API would have the message taken apart and put back together and would give every copy a Message-ID of its own), the envelope from the group's address to that one member, paced at two a second for Resend's rate limit. The row ends `sent` with the count of copies that went, and any that failed named in Detail, or `failed` when none did or an earlier step failed, with the step and the error. A restart re-queues every row still `received` or `stored`, so a message the instance died on goes out on the next start; a `failed` row is a person's to look at, and replaying the event from Resend's dashboard runs it again.

**Delivery trouble.** The same webhook is subscribed to `email.bounced`, `email.complained`, `email.delivery_delayed`, `email.failed` and `email.suppressed`. Each names the copy's sender - the group's address, which says which group - and recipient, and is appended to `Deliveries`; an event whose sender is any other app's address is not Loop's and is ignored.

**The archive.** Every message forwarded or dropped is in `gs://heliosian-mail` (`docs/deploy.md`), whole, as received, under the group and the time; nothing here serves it yet. `Messages` is its index.

**Unsubscribe.** Every copy's `List-Unsubscribe` is `https://loop.heliosian.com/unsubscribe/<token>`, the token the group name and the recipient's address signed with the session key (`internal/groups/unsubscribe.go`), with `List-Unsubscribe-Post: List-Unsubscribe=One-Click` beside it. `GET` on the link is the page with the button; `POST`, from the button or from a mail app's one-click, adds the `Unsubscribed` row and applies it in memory at once, and answers an empty 200 to a one-click and the page to the button. Both are public (`internal/auth`); the signature is the whole of the check.

`cmd/loadcheck` prints every group with its member count, its unsubscribed count and its subject switch.
