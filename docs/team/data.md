# Data model

The tabs, columns, and validation rules are in `internal/model/activities*.go`; this file carries only what reading that code cannot tell you.

The portal's data lives in one Google Sheet, `Events`, in the community shared drive, reached through drive membership like the other sheets. `EVENTS_SHEET` names it, and `tools/createtabs` reads that variable to lay it out from an empty spreadsheet titled `Events`.

## Tabs

- `Categories` — Category ID, Event ID, Title, Description, Image, Allow Adding, Show On Main Page, Direct Sign-Up, Volunteers Hidden, Hidden, Order. Direct Sign-Up, Volunteers Hidden and Hidden are an event category's volunteer settings (Volunteer settings, below); a page heading leaves them blank. Order is a sort key placing the category within its scope (`docs/storage.md`, Order). A blank Event ID makes a heading on the Opportunities page; an Event ID makes one of that root event's own categories, which the things under it are grouped by.
- `Activities` — Event ID, Calendar Event ID, Year, Title, Parent, Category, Status, Description, Image, Timing, Start, End, Location, Spots, Co-Leader Needed, Volunteers Hidden, Direct Sign-Up, Pretty ID, Allow Adding, Flyer Image, Highlight Headline, Highlight Body, Highlight Icon, Added By, Added, Order, Volunteers Complete, Priority. Event ID is the activity's own ID, the one every other tab here names it by. Calendar Event ID is the ID of the event a dated root is on the school calendar (`docs/when/data.md`), which its guest list, answers and calendar invites are keyed by; every activity is minted one when it is made or copied, dated or not, and the load refuses a row without one. A root folded into a school event (`sameEvent` in `internal/model/linked_events.go`) is that event instead. `Image` is the wide banner across the page and the card; `Flyer Image` is the event's poster, shown whole in the page's rail and, when present, on the share card instead of the banner. Both are stored image names, uploaded, found in the image libraries, or cropped from the page. `Order` is a sort key placing a thing among its siblings (`docs/storage.md`, Order), written by drag-and-drop on the page and in Volunteer settings; a thing moved under another parent loses its key and lands last there. The roots are listed in row order. `Volunteers Complete` is Yes when the organizers say the thing is staffed, whatever Spots and the count say - it wears the green Volunteers Complete check (which a thing whose spots are all taken wears as well) and takes no more sign-ups; no control in the app sets it (the editor keeps what is there), and a copy for next year starts with it off. The three `Highlight` columns are the page's callout - a headline, a few lines (with `**bold**` allowed) and an emoji - blank when there is none; a row with neither headline nor body has no highlight. Parent is an Event ID. Category is a Category ID: a page heading for a root, one of the root event's own for anything under it (or blank). `Priority` is an admin's mark on something the community most needs hands for, at any depth: only an admin's save writes it (anyone else's keeps what was there), a save marking the volunteers complete clears it and none can set it on a complete thing, it no longer counts once every spot is taken, a copy into the next year starts without it, the Opportunities page leads its chips with High Priority while anything this year carries it, and Heliosian's Team widget lists it under its Priority chip.
- `Volunteers` — Event ID, Email, Position, Note, Added By, Added.
- `Links` — Link ID, Event ID, Title, URL, Image, Description. A link is named by its Link ID - editing or removing one names it - so one activity may hold two links of one title.
- `Aliases` — Alias, ID: an id an activity or category used to have, and the id it has now (`internal/id`). See Keys are ids.

- `Redirects` — Type, Old, New, Date. Old is a path here as the site serves it (`/v/inight/poland`, `/dl/signup/s/768d91/…` from the old volunteer site; a bare word is `/v/{word}`, a whole link is read as its path), New a path here the same way or a whole `https://` address elsewhere, Type what wrote the row - `Activity` for a rename, `Admin` for Admin Tools - and Date when. A row with a blank Old or New is skipped. Followed ahead of sign-in and by the shell (`docs/team/team.md`, Redirects); a live address always wins over a redirect of the same name.
- `Settings` — Key, Value: `Expense Form URL` and `Intro`, both required.
- `Notifications` — Email, Kinds. One row per admin who chose Email notifications in Admin Tools; Kinds is the comma-separated notices they want, from `events`, `activities`, `signups` and `offers`.
- `Change Log` — the store's, one row per changed cell holding what it held before (`docs/storage.md`). Never read back.

**Column order does not matter, column names do.** Every write places each cell under the column of that name wherever the tab keeps it (`docs/storage.md`, IO), so columns may be rearranged by hand. Every tab needs the columns listed; a column the app does not read is somebody else's business and is left alone (`data.CheckColumns`), as is a tab the app never touches, such as one kept for backup.

## One table, one tree

There is no separate table of roles. A committee, a booth, or a shift is an activity like the event it sits under, distinguished only by naming that event in its `Parent` column; the roots — the things with no parent — are what the opportunities page lists. The tree nests to any depth: a booth can hold its own performance slot. `Group` is the sub-heading a child lists under on its parent's page and means nothing on a root. A child needs no `Category`: it takes its root's for tinting and filing.

`Parent` is the Event ID of another activity **in the same year**; the loader refuses a parent that does not exist, a row that is its own parent, a parent in another year, and a chain that loops. Anything under a parent may leave its own `Year` blank and takes the root's — only roots need one. Deleting something with children or volunteers is refused; deleting one takes its links with it. Moving a root to another year takes its whole tree with it. Any change to an activity's address - its `Pretty ID` or its `Parent` - writes the Redirects row from the old address to the new one, unless another activity now holds the old address, as after a take-over (below). All three are cascades on the store (`carryActivity` in `internal/model/activities_cache.go`), so they hold for any write, not only the editor's.

## Two kinds of category

A category row with no Event ID is a heading on the Opportunities page, and only a root activity may name one. A root whose Category is blank, or names an id that is not a heading, is shown under a built-in **Uncategorized** heading (id `uncategorized`), which appears last and only while something needs it; it cannot be edited, reordered or deleted, and saving a root as Uncategorized stores a blank. A child whose Category names anything but one of its own event's categories is treated as having none. A row with an Event ID belongs to that root event: the things under the event — at any depth — are grouped by these on its page, in their order, with the uncategorised ones last. Each event manages its own from its page, in Volunteer settings; the page's headings are managed from Admin Tools. Whoever runs an event may change its categories; the page's need an admin. A category never moves between scopes once made.

`Allow Adding` is what people who do not run a thing may do under it - into a category, or straight under an activity: `Yes` (add, and it goes live), `Approval Needed` (add, and it waits as Pending for an admin), or `No` (only the organizers add). It sits on both tabs: a category's cell, and an activity's cell (`Activities.Allow Adding`), which governs additions with no category under that activity and is the default for the event's own categories. A blank inherits - a category from its event, an activity from its parent - and an event or a page heading with nothing to inherit from takes `No`. Whoever runs a thing - an event's chairs on the event itself too - sets its `Allow Adding`, and whoever runs it adds freely and their additions are live at once; the form offers the choices as "Same as the event/parent", Yes, Approval needed, No.

`Show On Main Page` (default Yes) says whether a heading's events appear on the Opportunities page among everyone else's. A heading set to No still sits in the toolbar with its count, and choosing it there (or its chip) shows its events; it is a way to keep a long tail - old committees, standing needs - off the front without hiding it. It means nothing for an event's own categories, which the app leaves blank.

Copying an event to the next year copies its categories and links too, under fresh ids, and the copied children point at the copies.

## Keys are ids

Every activity has an `Event ID`, every category a `Category ID` and every link a `Link ID`, unique across the sheet, and everything that refers to one does so by id: a child's `Parent`, a root's `Category`, and the `Event ID` on every volunteer and link row. Titles are just titles — two booths under different events can both be "Set Up Crew", a rename touches one cell and nothing else, and every node lives at `/activities/{id}`. The app mints an id when it creates a row, copies included (`id.New` in `internal/id`: thirteen lowercase base-32 symbols, drawn again if any activity, category, link or alias already has it); rows added by hand need one too, the loader refuses two rows sharing one, and a Link ID must be an id of that form.

An id an activity or category used to have stays on the `Aliases` tab, pointing at the id it has now, and reaches the thing from outside: an id sent to the API, any segment of a page path (`/activities/{old id}/{old child id}`), and a Redirects row naming an old path all resolve through it. A page address reached only through an old id answers `301` to the thing's address as it is now (`Activities.Aliased`, in `model.ActivitiesRedirected`), since the page script knows no aliases. Inside the sheet an alias is never a reference: `Parent`, `Category` and the Event ID on volunteer and link rows hold the current id, and every write names the row by it, never by the id the request sent. A row with a **blank Event ID is a deleted activity** left in place: it is not loaded, and a volunteer or link row with a blank Event ID is skipped the same way. A child whose `Parent` is not a live row belongs to a deleted event and is skipped too, with everything under it; so is a volunteer or link row naming an id no live row has. A person listed twice on one thing counts once. Each load logs how many rows it skipped for each reason (`Activities.Skipped`), so a mistyped id shows up as a count rather than a silently missing row.

The cost is that the sheet no longer reads as prose on its own — a volunteer row names an id, not "Clean Up Crew".


`Pretty ID` is an optional friendly address: `applause` puts the activity at `team.heliosian.com/v/applause`, and every link to it and the share button use that address. Lower-case letters, digits and hyphens, at most 40; one address for one thing **across every year**. Saving refuses an address another activity holds in the same or a later year; one held by a prior year's activity is offered for renaming - to `applause-2025`, the address with that year - and taken once the editor agrees. Changing or removing one writes a row to `Redirects`, so the old address keeps working and the browser's address bar is corrected to the live one. Copying an event into the next year leaves the copy without one. A duplicate typed into the sheet loads with the latest year keeping the address (counted in `Activities.Skipped`).

A thing under an event is addressed under the event's path - `/v/inight/poland`, or `/v/inight/{id}` when it has no friendly name of its own, or `/activities/{event id}/...` when the event has none - so a child's friendly name only needs to be unique among its siblings, and `poland` can exist under every year's International Night. The bare `/activities/{id}` of a child still resolves, and the browser's address bar is corrected to the full path.

## Dates

Start and End are wall-clock, `2026-09-24 16:00` or `2026-09-24` for a whole day, with no time zone: an event at four o'clock is at four o'clock at the school. The client formats them as local time and the calendar file it downloads uses floating times. Timing is the free text shown when there is no date ("All Year", "Late February"). Added is a date, `2026-09-24`.

## Yes and No

Flag cells are `Yes`, `No`, or blank. For `Co-Leader Needed`, `Volunteers Complete`, `Priority` and a heading's `Show On Main Page` a blank takes the column's default - Yes for `Co-Leader Needed` and `Show On Main Page`, No for the rest - and the app writes Yes or No. `Allow Adding` is not a flag but a policy (above), and blank there means inherit.

## Volunteer settings

`Direct Sign-Up` (allow volunteers on the thing itself), `Volunteers Hidden` (only the organizers see who signed up) and, on an event's category, `Hidden` are Yes, No, or blank, and a blank means Default: the value of what the thing sits in. A thing directly under an event takes its category's value when it names one of the event's categories, and the event's when it names none; a category on Default takes its event's; anything deeper takes its parent's, whatever category it names; an event on Default allows volunteers and shows its list. The server works out every thing's value when the model loads (`resolveVolunteering` in `internal/model/activities.go`), and everything that decides who may sign up or who sees a list reads that value; the model the page gets carries both the stored cell (`directSignUpOwn`, `volunteersHiddenOwn`) and the value. A category's `Hidden` set to Yes hides the things filed under it, and everything under them, exactly as their own Hidden status would (`categoryHidden` on the activity): whoever runs them still sees them, muted. The Volunteer settings popup, beside the Edit button at the top of a page, lists the thing, the event's categories, and everything under it, each with Allow volunteers, Show volunteers and Allow new activities, every one a choice of its values or Default (an event, with nothing to inherit from, has no Default), tinted by the value it comes to, Default or not, and saved as it is picked - a thing's Allow volunteers offering Unlimited, Limited and No More, where Limited is `Direct Sign-Up` Yes with `Spots` set (5 when first picked, changed by clicking the number beside it) and Unlimited clears `Spots` - and an eye for Show activity: open or closed, a thing's status (Open or Hidden: whoever runs it may close it, but only an admin may turn down a Pending suggestion by hiding it) or a category's `Hidden` (Yes, or blank when open). Closing one closes everything under it, whose eyes show closed and cannot be opened until it is. Its rows drag by their grip: a thing dropped on the middle of another becomes one of its sub-activities, and dropped on its top or bottom edge - a line shows where - goes just before or after it among that one's siblings, moving to that parent and, directly under the event, that category; dropped on a category's heading it moves into that category; nothing drops inside itself. On an event its categories drag among themselves; there the popup also edits and adds categories. Beside each thing and category a pencil renames it in place and a + asks for a name alone and adds a thing under it (into that category, for a category) with every other field at the editor's defaults. A category's settings save through `POST /api/team/category/settings`.

## Status and spots

Status is one of `Pending`, `Open`, `Done`, `Hidden`, spelled exactly so. Spots is a positive count or blank for unlimited; whether something is full is the sign-up count against it, never a flag, so the two can never disagree.

## Images

An Image cell is an object under `activity-images/` in the media bucket, content-addressed and written by the image picker, or a path to a bundled file under `web/team/` or `web/public/team/`. A name that resolves to neither refuses the load. A role with no image shows its activity's.

## Saving an activity

A save names the activity's id and only the fields it changes (`POST /api/team/activity`); the server lays them over the activity as it stands, checks the result whole, and writes only the columns those fields own (`fieldColumns` in `internal/model/activities_writes.go`), so changing one field never rewrites another, or undoes someone else's change to it in the meantime. Adding sends every field. Whoever edits the activity - its co-chairs and those of everything above it, and an admin - may send any of them; an admin taking a pending activity to Open or Hidden with `status` is approving it or turning it down.

## A load either succeeds whole or refuses

The same stance as the other apps: a sheet that breaks a rule does not load, and the portal never serves a page quietly missing an event. A server that cannot load the sheet does not start, so a deploy waits on the sheet being fixed while the running revision keeps serving; a refresh that fails keeps serving the last good model and logs the reason. `go run ./tools/loadcheck` runs the same loader against the live sheets and prints the first thing it refuses.

## Sample data

`sampledata/events/` holds one CSV per tab: two school years, a nested role, a pending suggestion, a hidden activity, a private sign-up list, capped spots, and a done event, so every page and rule renders locally.
