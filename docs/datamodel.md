# The data model

`internal/db` declares the data model's tables, one sheet tab each, in `db.Tables`: every table's name, the spreadsheet it lives in, the columns no two rows may share (`Unique`), and each column's kind. Every row of every table has an `id` of its own, its first column, which every reference to it holds. A tab and its columns are named exactly as the table and its columns are (`PERSON`, `vc_name`), so the sheet, the code and a query share one name for everything. `tools/createtabs` lays out the five spreadsheets from it - `Data: People`, `Data: Groups`, `Data: Documents`, `Data: Mail` and `Data: Config`, each with its Change Log - and their ids are the `DATA_*_SHEET` variables (`docs/deploy.md`, Configuration values). A generated table (`EFFECTIVE_MEMBER`, `INBOX`) and a generated column (`PERSON.name_show`) are declared beside the stored ones and have no tab or column in a sheet: `Table.Stored` is what a tab holds.

## The store

`db.NewStore` is a `store.Store[db.Model]` over the five sheets (`docs/storage.md`, Store), one part per spreadsheet, each tab's columns its table's stored columns and its key `id`. The server builds it in `app.NewCore` on the same queue as the apps' store, so both load at startup, refresh together and commit in one order; `tools/loadcheck` loads it too and prints each table's row count, and the sample server reads `sampledata/data*/`.

A part's build checks every row (Cells, below), computes the generated columns into a copy of the row (`Table.Generate`: a person's `name_long`, `name_short` and `name_sort` are the override if set, else the import's, and `name_show` is `name_long`, else `Guest` for a guest, else `[Missing Name]`; a person's `phone` and a family's `address` and `phone` are blank unless the row's `phone_consent` or `address_consent` is `shared`, and are then the `_override` column if set, else the `vc_` one; any other group's `address` and `phone` are the override, else the `vc_` one), refuses two rows with the same `id` or the same unique columns, and indexes each table by `id` (`Rows.Get`), by its unique columns (`Rows.Find`: an address in `PERSON_EMAIL`, a group, person and role in `MEMBER`) and by every reference column (`Rows.Referencing`). People's build also refuses a person with addresses but not exactly one `primary`. Mail's part reads the other four, so a change to any sheet rebuilds it, and its build refuses any reference, in any table, that names no row (`Model.Has`). A commit the model refuses is refused whole, as for every part.

## Groups

A group's `kind` exists only where the group shows somewhere a different way: `family`; the school's `band`, `grade`, `classroom`, `crew` and `department`; When's `event`, `day` and `day_part`; Team's `activity`; Celebrate's `party` and `celebration`; `admins`, the groups `APP.admins` names; and `group`, every group that is only a set of people - the role groups, tags, Loop's lists, Heliosian's audiences and sections, room parents. A recurring event is an `event` with no `start` whose instances are its children. Where a `group` shows is its flags: `listed` puts a group in its app's lists, and a `group` in Who? and the rule and visibility pickers; `mail` gives a group an address and puts it in Loop. A `group` with neither is internal, reached only through whatever names it (`visible_to`, a party's `eligible`, `APP.admins`). The admins groups keep a kind of their own so that no app admin's grants over `group`s reach them.

A membership's `role` is `manager`, `member` or `waitlist`. A manager of a group manages every group under it through `parent`, and managing is the power a membership carries: seeing a group whatever its visibility, its members, rules, mail and payments, and setting any member's status. `lead` on a member row marks someone who leads the group, an event's leader, for the pages to show; it grants nothing, and rules and effective membership see an ordinary member. A group's `visibility` is `everyone`, `members`, `managers` or `group` (the effective members of `visible_to`); `status` is `pending` (managers and the app's admins alone), `open`, `done` (an activity that happened, still shown), `cancelled`, or `closed` (gone from every list and page, kept for the messages that name it).

## Consent step

Rows of people who have not consented never leave the model to anyone but the import. The consent step (`consentStep` in `internal/db/consentstep.go`) is the one place that decides it, and it decides nothing else: it runs once per build, on every load and every staged write, after every part has built (the store's `consent` step, `docs/storage.md`), and fills `Model.Shown`, one `View` per table of the rows that may be shown.

- A person is shown when they are a guest (`source=guest`, always) or their `consent` is `listed`; a family group when its `consent` is `listed`. Anything else is hidden, including a person with no `consent` yet: it fails closed.
- Any row that references a hidden row, in any reference column, is hidden too, and so on until nothing more is: their emails, photos, settings, birthday years, memberships, rules naming them, mail from and to them, groups they added, whatever names a hidden family.
- A shown row has its `private` columns (marked `.private()` in `internal/db/schema.go`) removed, so a reader sees only the generated `phone` and `address`, blank when withheld, and never a person's or family's `consent`.

Everything that serves people reads only through `Model.Shown`: every query run's row access (scans, probes, paths, includes, ancestors, the viewer and the policies' own reads), effective members and rules, signing in (`signedIn`, so a withheld person signs in as nobody), and a person's write, which finds the row it names and every reference it sets there, so naming a hidden row is "no such row". A run as the `import` system reader, and the triggers, read the whole tables (`Model.Table`); so does the consent import, which works out consent itself.

## Queries

A query is one fully bracketed prefix expression, the operator first in every bracket: `(from TABLE [@name] (where cond…) (order path asc|desc …) (limit N) (include path…))`. A condition is `and`, `or`, `not`, a comparison (`=`, `!=`, `<`, `<=`, `>`, `>=`), `(in x "a" "b")` or `(in x (select TABLE.column cond…))`, `(blank path)`, `(exists TABLE [@name] cond…)`, or a yes/no path on its own; a value is a path, a quoted string, a number, `true`, `false`, `today`, `now`, `(count TABLE [@name] cond…)` or `(sum path TABLE [@name] cond…)`. Upper-case names are tables. A path is columns joined by dots, each but the last a reference followed to the row it names; it starts at the innermost row being matched, or at a named one (`@g.visible_to`), or at `@viewer`, the person the query runs as. Several conditions in one bracket are anded.

`db.Parse` reads a query and checks it against the schema before anything runs: a column or table that does not exist is refused with the nearest name (`no column grde on PERSON; did you mean grade?`), and each literal is read as the type of what it is compared with, so an enum value it does not have, an ID of the wrong table, text where a number belongs or a malformed date is refused. `Query.String` renders the canonical form: a bracket that fits in 80 columns stays on one line, otherwise its arguments go one per line, aligned under the first, a `from`'s parts each on its own line indented two, and the rendering parses back to the same tree.

`Model.Run(query, db.Env{Viewer, Now})` answers a `db.Result`: the IDs of the matching rows in order, at most the limit, and every row reached - those and every row the includes reach - by table and ID, each once. Comparisons follow the column's kind: text and enums ignore case, references and IDs match exactly, numbers and amounts compare as exact decimals, a date against a moment as that day's midnight, and an order key by `store.CompareKeys`. A blank cell equals nothing and orders after everything, `!=` holds when exactly one side is blank, and `=` on a list of references holds when the list contains the value. An equality between a reference column of the row being scanned and something outside it is answered from the model's indexes rather than by scanning. An `exists` or `select` that names no row outside itself (`@viewer`, literals, `today` and `now` aside) is worked out once per run and reused, and `in` looks a value up in a `select`'s answer rather than walking it, so a policy like `household @viewer` costs one scan per request, not one per cell. `BenchmarkEveryPerson` and its neighbours in `internal/db/scale_test.go` time queries and a write's rebuild over a synthetic school sized by `scaleFamilies`.

## The query API

The API is JSON. A query is a JSON tree with the same shape as the language, one object per bracket: `{"from": "GROUP", "as": "g", "where": [cond…], "order": [{"path": "name_sort", "dir": "asc"}], "limit": 20, "include": ["person"]}`. A condition is `{"and": […]}`, `{"or": […]}`, `{"not": cond}`, `{"=": [a, b]}` and the other comparisons, `{"in": [x, "a", "b"]}`, `{"blank": x}`, `{"exists": {"from", "as", "where"}}`, `{"path": "hidden"}` for a yes/no column, or `true`; a value is a JSON string, number or boolean literal, `{"path": "person.grade"}` (`@` starting a named row), `{"today": true}`, `{"now": true}`, `{"count": {"from", "as", "where"}}`, `{"sum": {"path", "from", "as", "where"}}` or `{"select": {"from", "column", "where"}}`. `db.ParseJSON` reads it and `Query.Tree` writes it; the language (Queries, above) is the form for people, and `db.Parse` compiles it to the same tree, so both are checked and run the same way.

`QUERY /api/q` on every app's host - the HTTP QUERY method, safe and idempotent with a body - takes one query as the request body, `application/json` for the tree or `text/plain` for the language, and runs it as the signed-in person: the `PERSON` whose address in `PERSON_EMAIL` is the one signed in (Spoof Mode's, when spoofing), or nobody when the sheets hold no such address. It answers `{"now", "query", "result", "resources"}`, the resource API's envelope (`docs/api.md`, Reads): the school's time as the query saw it, the query in canonical text, the IDs it answers in order, and every row reached, the result's and its includes', keyed by table then ID, each once and as the reader may see it; a query sent as text also gets its JSON form as `tree`. A query that does not parse or check is a 400 with the reason, any other body a 415, and a body over 256 KiB a 413. Each query is logged with the viewer's person ID.

A request to `/api/q` or under `/api/do/` carrying `Authorization: Bearer <key>` passes sign-in without a session (`auth.Bearer`, the one path that does) and runs as the system reader `import` when the key is `IMPORT_KEY` (`docs/deploy.md`, the `heliosian-import-key` secret; the sample server's is `sample`), and is a 401 otherwise, never falling back to a cookie. The import has no viewer: it sees and writes exactly what the policies' `(system "import")` clauses grant (Veracross import, below), and the Change Log names it as the actor. Mutual TLS in its place waits on a load balancer in front of the service (#174).

`POST /api/q` takes an `application/json` batch of writes, `{"batch": [{"insert": "TABLE", "as": "name", "row": {…}}, {"set": "<id>", "cells": {…}}, {"delete": "<id>"}]}`, up to 16 MiB, and answers `{"result"}`, the ID each write touched. The server mints every ID: an insert's `id` and the tokens a row needs, and a write naming any ID column is refused. An insert's `as` names its new row within the batch, and a later write in the same batch says `@name` for it wherever an ID goes - a reference cell, or the row a set or delete names; a set or delete names only the row's ID, since its prefix says the table. A cell is text, a number, or `true`/`false` for a yes/no, and `""` blanks it. Each write is checked against the table's cells and then the write policies (Permissions, below) as the batch has left the model so far, and the batch is one transaction (`docs/storage.md`, Store): all of it goes in or none does, a refusal naming the write that failed. Addresses in `PERSON_EMAIL` are written in lower case, which the load requires, so the signed-in address finds its row.

What is more than writing rows is an imperative call under `/api/do/` (`internal/db/do.go`): a `POST` whose body is what that call takes, answered in JSON, run as the same caller as `/api/q` and writing through the same batch path, so the cells, the policies, the triggers and the one transaction are `/api/q`'s. `POST /api/do/photo` takes multipart form data: the `person` or the `group` the photo is of (exactly one), the `photo` file and, optionally, a crop box (`crop_left`, `crop_top`, `crop_width`, `crop_height`, whole pixels of the re-encode); it refuses what is not a JPEG, PNG, GIF or WebP within the pixel limit, or a box that is not four whole numbers with a width and height above zero, checks the insert against the policies before storing anything, stores the original as sent in the media bucket under `photos/`, named by its own SHA-256, and adds a `PHOTO` row naming it, with the box, ordered before that person's or group's other photos, answering `{"result", "hash"}`. A photo is only ever added.

Every picture is a `PHOTO` row, of a person or of a group - a person's portraits, a family's photos, a classroom's or grade's tile - as many as there are, the first in `order` the one shown; the load refuses a row naming both or neither. A photo is read by whoever may see its person or its group. A photo is its original (`photo`), private since it can carry location and face tags, and what the server makes from it (`internal/db/pictures.go`): the re-encode (turned upright as its EXIF says, every tag dropped, a JPEG at most 2048 pixels on its long side), the crop of the re-encode when the row has a box, and the thumbnail of the crop, else of the re-encode, each stored under `photos/` by its own SHA-256 with a `-thumb` beside it as `internal/blob` stores every image. Any write that adds a photo or changes its original or box hands it, once the commit is in, to one worker that makes the three one photo at a time and writes their names back (`reencode`, `crop`, `thumbnail`) with `ready` set, unless the original or box changed again meanwhile. A change to the original or box clears `ready` in the same write (a trigger), so a photo is current exactly when it is `ready`, and until then its made columns are blank or what an earlier original or box made. The worker's queue is in memory: at startup it queues every photo not `ready`, which picks up whatever a stopped instance left unmade. No policy lets anyone write the made columns or `ready`. An edit to a photo's original or box made by hand in the sheet does not clear `ready`, so it is not remade until something else changes it. `POST /api/do/calendar-pdf` takes multipart form data, the `pdf` file and the `url` it came from; it refuses what is not a PDF, and when a `DOCUMENT(kind=calendar)` already carries the PDF's hash it answers that document; otherwise it checks the insert against the policies, stores the PDF in the media bucket as `calendar/<sha256>.pdf` and adds a `DOCUMENT` row with `kind` calendar, that `object`, its `hash`, the `url` and today's `date`, answering `{"result", "hash"}`. `DOCUMENT.hash` is always the SHA-256 of the document's stored object, worked out from the bytes stored, and blank on a document with no object.

Triggers (`triggers` in `internal/db/trigger.go`) are writes that follow from a write, staged in the same transaction after it and checked against the cells but not the policies, since the code makes them, not the writer; a trigger's writes fire triggers in turn. A family's `title_auto` is its members' last names, kept in step whenever a person or a family membership changes: the last word of each `name_long` (the override, else the import's) of its members who are listed, not hidden and not deactivated, children before managers, each once whatever its case, leaving out a name that is one part of another's hyphenated name (Chang and Farh go when Chang-Farh is there), joined with ` & ` and followed by ` Family`, and blank when no one is left. A family's `title` is a name someone chose, shown in its place. Another trigger keeps school groups' members in step with people: when a person is added, or their grade, classroom, crew or department (the override, else the `vc_` column) or `deactivated` changes, their `MEMBER` rows in classroom, crew, grade, band and department groups become exactly one `member` row, status yes, in each of their classroom, crew and department and the grade group whose `slug` is `grade-` and the grade (`grade-k` … `grade-8`), and none at all once they are deactivated. A grade no group carries refuses the write. Nobody is a member of a band directly: a band's one rule includes itself with `descend`, so it holds everyone in the grades and classrooms under it.

## Permissions

Who may see and change what is written in the query language, in `policySource` in `internal/db/policy.go`, compiled when the package loads: code, never a sheet, since whoever could edit a policy could grant themselves anything. Whom a policy names is data - the members of an app's admins group, a group's `visibility` and `visible_to`, who manages what. Every clause for the same thing is or-ed, so each grant is a line of its own. The source is in sections by whom the clauses are for - definitions, everyone, each app's admins, super admins, and each system reader - and every clause carries a one-line `;` comment saying what it grants, so each can be checked against its purpose. Policies never decide consent: they see only the rows the consent step shows (Consent step, above), and decide who sees what among those. `;` starts a comment running to the end of the line anywhere in the language. A `define` no clause calls, directly or through another definition, refuses to load.

Nothing is readable until a clause says yes, rows and columns alike, so every read clause only ever adds readers.

- `(read TABLE condition)` decides which rows a reader sees, the row being `@row`. Every table has one; a table with none would show nobody anything.
- `(read TABLE (column…) condition)` decides which of those rows' cells a reader sees, and blanks a listed column where the condition fails; a column is read only on a row the reader already sees, so `true` means everyone who sees the row. The policies refuse to load unless every column that isn't `private`, in every table, is listed in some column clause, so a new column stays unreadable until a clause names it, and a column clause naming a `private` column is refused: the consent step keeps those from everyone but the import, which sees them whatever the clauses say.
- `(set TABLE.column condition)`, `(insert TABLE condition)` and `(delete TABLE condition)` decide writes, over the row before (`@old`) and after (`@new`). `Model.Authorize(env, db.Change{Table, Old, New})` checks one: an insert has no `Old`, a delete no `New`, and a set needs a clause for every column it changes. A change no clause allows is refused (`access.Forbidden`).
- `(define (name @row-parameter value-parameter …) body)` names a condition, or a `select`, that policies call by name: `manages` (a manager, with status yes, of the group or any group above it through `parent`), `household`, `role_group`, `self_or_household`, `groups_of`, `visible`, `sees_members`, `person_visible`, `sees_mail`, `document_visible`, `admin_of` and `super_admin`. A call is expanded where it stands, a bare column passed to it meaning that column of the row in hand.
- `(ancestors @g)` (a group and every group above it), `(system "name")` (the run is a named system reader, `Env.System`, granted only where a clause says so) and the names `@row`, `@old` and `@new` exist in policies alone; a client query using them is refused.

`Model.Run` applies the read policies to every row a client query touches - the rows it lists, every row an `exists`, `count`, `sum` or `select` inside it scans, and every row a path follows a reference to - and the column policies to every cell it reads, so a condition can't learn what the reader can't see. A reference to a row the reader can't see reads blank, in conditions and in what is answered. Policies themselves, and `EFFECTIVE_MEMBER`'s rules, run unfiltered.

The layer knows nothing of the apps on top of it but their admins: an app's admins are the effective members of its `APP` row's `admins` group (`admin_of`), and each app's grants are a block of clauses naming exactly the groups, by kind or flag, and the tables they open - a When admin reads every event and school day and their members, rules and mail, and sets an event's status and a member's role; a Loop admin does the same for every group with `mail`. Everything else in the policies is about people, groups, membership, managing and visibility.

## Effective members

`EFFECTIVE_MEMBER` is generated: who is in a group, each row's `id` derived from the group's and the person's (IDs, below), with each person's `status` from their member row and the `reasons` they are in (`member`, or `rule` and the rule's order). It starts from the group's `member` rows whose status is set and is neither `excluded` nor `cancelled`, adds everyone a rule selects, then takes away everyone a rule with `exclude` selects, everyone with an `excluded` member row and everyone deactivated, however they came in. A rule selects with every selector it fills in at once: a target group's own effective members (with its descendants through `parent` when `descend` is set), one person, free text found in a name or an address, or a person column (`property`, which the load refuses if `PERSON` has no such column, it is `private`, or no `true` column clause opens it to everyone who sees the person); rules and effective members read only shown rows (Consent step, above) holding `value`; then expands them to their `parents` (the managers of families they are in but do not manage), `children` (the members who are not managers of families they manage) or `household` (everyone in their families, and themselves), and keeps only those in `within`'s effective members. A group already being resolved further up the same chain contributes nobody, so lists that include each other resolve. Each group's members are worked out the first time a query asks, once per version of the model.

## Inbox

`INBOX` is generated: one row per person and document (`id` derived from both), for every newsletter, list or post whose `sent_to` or `for` groups hold, among their effective members, the person or anyone in a family the person is in. It is worked out the first time a query asks, once per version of the model, and a reader sees only their own rows.

## Veracross import

`tools/import` runs a fresh Veracross export and a fresh export of the school website's staff page (`docs/dev.md`, Tools), reads people, their emails, the family, role, classroom, crew, grade and band groups, the family and role groups' members and the bands' rules with `QUERY`s to `/api/q`, works out what differs, and sends it as one `POST` batch, all with the import key; `--dry-run` prints the batch and the number of photos it would add, and sends nothing. After writing it reads and plans again, refusing to go on unless that plan is empty, and then adds through `/api/do/photo` each Veracross and staff-page portrait the person does not already have, comparing by SHA-256; the Veracross portrait is added last, so it comes first. Then it runs the calendar import's PDF stage (Calendar import, below). It reads and writes nothing else, and the `(system "import")` clauses in the policies grant exactly that, but for their last section, which is the sync from the old sheets: it runs with the import key too, writes the old directory's hand-kept rows (overrides, extra addresses, family pictures, photos, tags, room parents, admins, colors, settings and every old ID as an `ALIAS`), and goes when the last app is cut over. An old crop was a separate, scaled and re-compressed image, so the sync works out each one's box by matching it against the re-encode of its original.

- **People.** An email identifies one person: export rows sharing an email are one person and rows with different emails are different people, whatever their names. Rows of the same role and name where one has no email are one person too; placeholder emails containing `.noemail` don't count. Names are compared as resolved (`Juni (Juniper) Ashdown` as `Juni Ashdown`), since a staff member's household copy often carries a parenthetical the staff export leaves out. Each is matched to a `PERSON` by an email in `PERSON_EMAIL`, else by `vc_name` when exactly one person not already matched by email carries it. Emails belonging to two people, a name two people carry, two export people matching one, or a parent and a staff member of one name where one of them has no email refuse the run. Anyone unmatched is inserted with `source` veracross. The import writes the `vc_` columns, the `name_*_import` columns (Veracross's `Juni (Juniper) Ashdown` read as preferred first name, legal first name in brackets, last name), and clears `deactivated`; a veracross person the export no longer lists gets `deactivated` set to now. Job title is Veracross's, else the staff page's; the bio is the staff page's, matched to staff by any of their emails on file - the export's, or another `PERSON_EMAIL` row recorded for a staff page that lists an older one - else by a name exactly one of them has.
- **Emails.** The export's emails become `PERSON_EMAIL` rows with `source` veracross. A new one takes over a veracross row whose email has gone, so the primary stays put; the first email of someone with none is primary.
- **Groups.** A student's classroom and crew and a staff member's department (Veracross's `person_department`, its names as they are) are matched to groups by title (a crew within its classroom), and a missing one is added, as are any of the nine grade groups (`grade-k` … `grade-8`) and their bands, and the role groups `students`, `parents`, `staff`, `adults` and `everyone`, `group`s found by slug; every group the import adds is `listed`. A grade's `parent` is its band, a classroom's is the band of its students' grades, set whenever it differs, and a crew's is its classroom; a classroom with students in two bands refuses the run. A band without a rule targeting itself with `descend` gets one.
- **Families.** A household is matched to the family whose managers are exactly its adults, else to the one with a member and a manager in it that shares the most adults; when two households match one family the one sharing more adults keeps it, the first in the export on a tie, and a household matching none gets a new one. Its `vc_address` and `vc_phone` are the household's, everyone in it is a `member` and its adults are `manager`s.
- **Memberships.** In family and role groups the import adds the rows it wants with status yes and removes the others belonging to people it manages - those it lists and every veracross person - so a deactivated person leaves their role groups but keeps their families. School groups follow from the trigger (The query API, above).

## Calendar import

The school's calendar reaches the data model from two sources, each in its own stage writing as `import` through the batch path: its public Google Calendar, from the server, and its published year calendar PDF, from `tools/import`. Both plan with the same code in `internal/db` (`calendarplan.go`), over the rows they read - the server from its own model, the tool through `QUERY /api/q` - so they agree on what a source's rows are.

- **What a source makes.** A Google event is a `GROUP` of kind `event` (`listed`, status open, visibility everyone) carrying the event's title, start, end, `all_day`, location and description, with a `GROUP_SOURCE` holding the same as Google has it, its key in `calendar_event` and the classifier's input hash in `hash`. An instance of a repeating event has as its `parent` an `event` with no `start`, the recurring event, found by its own source whose `calendar_event` is the repeating event's UID. An entry of the PDF's Important Dates is an `event` group the same way, its source naming the PDF's `DOCUMENT` instead; an entry on the same date with the same title (ignoring case and spacing) as an event Google brought is that event, given a second source. A group is deleted, with everything under it - its parts, categories, rules, members, document links and sources - once its last source is gone.
- **Who it is for and what it is.** Claude classifies each event into the `CATEGORY(scope=event)` rows that apply, the classrooms it concerns, and who of them it is for: `families`, `parents` or `staff`. That becomes the group's `GROUP_CATEGORY` rows and its rules: a rule per classroom expanding to the `household` for families or the `parents` for parents, or one rule on the `everyone`, `parents` or `staff` role group when it concerns every classroom or is for staff, so the event's effective members are exactly whom it is for.
- **School days.** A day is a `GROUP` of kind `day` on its date, filed under its `CATEGORY(scope=day_type)`, with a `day_part` child per part of that type's usual times - `DayTemplates` in `internal/db/daytypes.go`, keyed by the day-type and day-part category titles - each filed under its `CATEGORY(scope=day_part)`. A day for some classrooms carries a rule per classroom; one for all carries none. Each source owns its own days and neither stage touches the other's: the PDF stage writes a day for every weekday from its first-day to its last-day entry, Regular unless the grid shades it or an entry with a day type covers it, one day per day type when classrooms differ, and the first and last days' sources carry `marker`; the Google stage writes a day per weekday of an all-day event the classifier gives a day type, for the event's classrooms, and removes them with the event. Where the two disagree there are two days for one date and classroom, and what reads days decides.
- **Classifying.** Events go to Claude ten to a call, the answer one required object per event under a handle, each echoing its title so a skipped or swapped answer is caught and asked again once. The hash on a source covers the event's text and dates, the classroom vocabulary, the day types and the classifier's whole prompt, so an unchanged event is never sent twice and a renamed classroom or a reworded category reclassifies everything. A batch that fails leaves its events as they were, with their old hashes, so the next run asks about exactly them.

The Google stage (`CalendarWatcher` in `internal/db/calendargoogle.go`) runs in the server on Cloud Run alone, Cloud Run's `K_SERVICE` marking it, so a laptop's real-data server never writes the calendar. It reads the calendar named by `SchoolCalendarID` in `internal/db/calendar.go` through the Calendar API as `directory@`, single events from the first of July of the previous school year for three years, so Google expands repeating events itself; times are school wall-clock, all-day ends inclusive, and HTML descriptions flattened to text keeping each link's address. Only that window is mirrored: a source outside it is never removed. At startup it opens a watch channel posting to `https://when.heliosian.com/hooks/calendar` and runs once; each post kicks a run, at once or the moment the current one ends, so changes during a run collapse into one; every hour it runs unasked and renews the channel once it has under two hours left. A post carries the channel's token, an HMAC of the session key, checked before anything else. Its log lines are in `docs/deploy.md` (The school calendar watch).

The PDF stage (`tools/import`, `calendar.go` and `calendarread.go`) fetches the school's calendar page (`SchoolCalendarPage`), follows its PDF link, and stops there when a calendar `DOCUMENT` already has the PDF's hash and every source naming it carries the current reading's hash, which covers the reading prompts and the model. Otherwise it reads the PDF in stages, each its own Claude call at maximum effort: the legend, into wording, an estimated color and a day type per swatch; the Important Dates list, into entries whose day type comes only from a dismissal note in the wording; and the twelve month grids, one call per month over a crop of the page rendered at 300 dpi with poppler's `pdftoppm`, each read twice and a third time to break a tie, each read naming every day and echoing the grid's title so a changed layout fails loudly. It classifies the entries that are new, refusing to go on unless every one was classified, posts the PDF to `/api/do/calendar-pdf`, and sends one batch: its year's days replaced, entries kept, matched or added, and the sources of entries the PDF no longer lists removed. A `429` from the school's site is waited out and asked again four times over about a quarter of an hour.

## Consent

The opt-in form's responses live in the form's own spreadsheet (`PREFERENCES_SHEET`, tab `Sheet1`), which this service does not own and only reads. On Cloud Run the server keeps `PERSON.consent`, `address_consent` and `phone_consent` in step with it (`StartConsent` in `internal/db/consent.go`): a goroutine reads the responses at startup and every minute, and after each read, and whenever the data model changes, works out each person's consent from the last responses read and writes what differs through the batch path as `import`, so its own write finds nothing more to change. A swap only signals it, so no commit waits on it. It never runs on a laptop, so a real-data dev server never writes production.

- A response belongs to the person holding its email in `PERSON_EMAIL`, any of their emails; one matching nobody is skipped.
- Families sharing a member are linked, and the latest response from anyone in linked families governs everyone in them; someone in no family is governed by their own latest response.
- A governing opt-out withholds the person (`consent=withheld`); so does having no answer, for anyone not in the `staff` role group. Address and phone are `shared` only where every governing response shares them, and `withheld` for anyone withheld; staff with no answer share both. A family's `consent`, `address_consent` and `phone_consent` are `listed` or `shared` only when every one of its managers' is, and `withheld` for a family with no managers. A withheld address or phone is never shown, not even to its owner: the site and the API act as if there were none.
- A withheld person or family is never shown (Consent step, above), to anyone, themselves and admins included; only the import sees them. Veracross's own privacy has already been applied to the export; `vc_address_visibility` and `vc_phone_visibility` are only there to explain it on the profile. Guests are left alone.
- Every value is matched word for word - the opt-in answers, the two permissions, the timestamp format - and anything else stops the run with the reason logged, writing nothing, until the form or the code is fixed; an empty permission cell shares neither.

## IDs

An ID is a three-letter prefix naming what it identifies, then 11 symbols of upper and lower case letters and digits, about 65 bits; the prefixes are the `*Prefix` constants in `internal/db/id.go`. IDs are case-sensitive and are never trimmed: `db.ParseID` accepts only the exact form and answers the prefix, and `db.TableOf` the table keyed by that prefix, so an ID found anywhere - a URL, a log line, a cell - says which table holds it. `db.Mint` draws a new one, again while `taken` refuses it. A generated row has no stored ID to mint, so `db.Derive` makes one from what the row is: the first 64 bits of the SHA-256 of its parts, in the same 11 symbols, the same on every read; an `EFFECTIVE_MEMBER` row's is its group's and person's under `efm`. Two kinds are minted the same way but name no row: the secret tokens a saved view's feed (`SAVED_VIEW.token`, `fed`) and a mailed copy's links (`RECIPIENT.token`, `tok`) carry, which are kept apart from the row's own ID so the ID can be shown and passed around freely. A membership's `purchase_id` is text, the payment provider's reference.

## Cells

`Column.Check` and `Table.Check` read a cell as its kind requires: an enum one of its values in any case, a reference an ID whose prefix is its target table's (any table's for `MESSAGE.about` and `ALIAS.target`), a list of references comma-separated, a yes/no, a date or moment, an order key, an address or a link as `internal/cells` and `internal/store` read them everywhere else, and an amount as digits with up to two decimal places. A blank cell is accepted unless the column is required; a column a sheet holds that the table does not declare is ignored.
