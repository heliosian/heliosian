# The data model

`internal/db` declares the data model's tables, one sheet tab each but for `CHANGES`, which has one in every sheet (Changes, below), in `db.Tables`: every table's name, the spreadsheet it lives in, the columns no two rows may share (`Unique`), and each column's kind. Every row of every table has an `id` of its own, its first column, which every reference to it holds. A tab and its columns are named exactly as the table and its columns are (`PERSON`, `vc_name`), so the sheet, the code and a query share one name for everything. `tools/createtabs` lays out the five spreadsheets from it - `Data: People`, `Data: Groups`, `Data: Documents`, `Data: Mail` and `Data: Config`, each with its `CHANGES` tab - adding what is missing and changing nothing else - and their ids are the `DATA_*_SHEET` variables (`docs/deploy.md`, Configuration values). A generated table (`EFFECTIVE_MEMBER`, `INBOX`) and a generated column (`PERSON.name_show`) are declared beside the stored ones and have no tab or column in a sheet: `Table.Stored` is what a tab holds.

What a table, a column and each value of an enum mean is declared beside it in `db.Tables` (`Table.Description`, `Column.Description` set with `.about`, and `Column.Values`, each a `Value` with its own description), and the package refuses to load while any of them lacks one or an enum lists a value twice. `GET /api/openapi.json` carries them - a table's on its component, a column's first in its `description`, an enum's values in `x-enumDescriptions` - and the admin resources page shows them. This document covers what spans tables.

## The store

`db.NewStore` is a `store.Store[db.Model]` over the five sheets (`docs/storage.md`, Store), one part per spreadsheet, each tab's columns its table's stored columns and its key `id`. The server builds it in `app.NewCore` on the same queue as the apps' store, so both load at startup, refresh together and commit in one order; `tools/loadcheck` loads it too and prints each table's row count, and the sample server reads `sampledata/data*/`.

A part's build checks every row (Cells, below), computes the generated columns into a copy of the row (`Table.Generate`: a column the import writes and the app may override is three, `vc_X` the import's, `X_override` the app's and `X` generated, the override if set, else the import's - a person's `name_long`, `name_short`, `name_sort`, `grade`, `classroom`, `crew`, `department` and `job_title`; and `name_show` is `name_long`, else `Guest` for a guest, else `[Missing Name]`; a person's `phone` and a family's `address` and `phone` are blank unless the row's `phone_consent` or `address_consent` is `shared`, and are then the `_override` column if set, else the `vc_` one; any other group's `address` and `phone` are the override, else the `vc_` one; an address's `guest` is whether its `source` is `guest`), refuses two rows with the same `id` or the same unique columns, and indexes each table by `id` (`Rows.Get`), by its unique columns (`Rows.Find`: an address and `guest` in `PERSON_EMAIL`, so a guest may hold the same address as one person who isn't, a group and person in `MEMBER`) and by every reference column (`Rows.Referencing`). People's build also refuses a person with addresses but not exactly one `primary`. Mail's part reads the other four, so a change to any sheet rebuilds it, and its build refuses any reference, in any table, that names no row (`Model.Has`). A commit the model refuses is refused whole, as for every part.

## Groups

A group's `kind` exists only where the group shows somewhere a different way: `family`; the school's `band`, `grade`, `classroom`, `crew` and `department`; When's `event`, `day` and `day_part`; Team's `activity`, whose `timing` says in words when it happens where a `start` cannot ("All Year", "September/October"), and each school year a root `activity` every one of that year's activities sits under; Celebrate's `party` and `celebration`; `category`, a heading or filter things are filed under; `admins`, the groups `APP.admins` names; and `group`, every group that is only a set of people - the role groups, tags, Loop's lists, Heliosian's audiences and sections, room parents, a party's waitlist, a group's managers. A recurring event is an `event` with no `start` whose instances are its children. Any group may carry a `url`, a page elsewhere that it stands for, so a link is a group like any other, with managers, categories and pictures.

A thing's category is its `parent`: there is no table filing groups under categories and none per app. A category is a group of kind `category`; When's event categories stand alone at the top, with the day types (Regular, No Aftercare, Early Dismissal, No School) under Schedule, and `default` says whether When's filter starts with one on. Team's sit under each school year's root activity, each year with its own copy, `listed` off for one kept off the main page, and the headings of an event's activities are categories under the event. An app finds its categories by what they hold. Where a `group` shows is its flags: `listed` puts a group in its app's lists, and a `group` in Who? and the rule and visibility pickers; `mail` gives a group an address and puts it in Loop. A `group` with neither is internal, reached only through whatever names it (`visible_to`, a party's `eligible`, `APP.admins`). The admins groups keep a kind of their own so that no app admin's grants over `group`s reach them.

Who manages a group is a group: `managed_by` names the group whose effective members manage it, and a group's managers are those of its own `managed_by` and of every group above it through `parent`. Managing is seeing a group whatever its visibility, its members, rules, mail and payments, and setting anyone's place in it. A family manages itself. Any other managed group's `managed_by` is usually a plain group of its own, named `<name> Managers` and managing itself, so its managers add and remove one another; it sits under no parent, so nothing takes in its members by `parent`, and it starts as `listed` and as visible as the group it manages, usable like any other group. Groups that are one thing may share one, and an existing group, a team, may manage others. A trigger renames a `<name> Managers` group, a `<name> Waitlist`, and `<name> Going` and `<name> Not Going`, with the group they serve, only while its name still reads that way, so a name chosen by hand stays. Whoever sees a group reads its managers group and who is in it, so hosts and co-chairs show.

A person has one `MEMBER` row in a group, its facets columns of their own, so a co-chair who signed up is one row. No facet grants anything. `member` is being in the group by name, which a group's kind gives its meaning - a ticket on a party, a sign-up on an activity, on the guest list of an event, simply in it for any other kind - and only `member=yes` makes an effective member (Effective members, below). `lead` marks someone who leads the group, a co-chair, for the pages; whether they also manage is whether they are in its managers group. An answer about coming is a group too: a group that takes answers names two plain groups under it, `rsvp_yes` (`<name> Going`) and `rsvp_no` (`<name> Not Going`), listed and starting as visible as the group they answer, so its managers manage them. Saying yes or no is a membership in one, its `added` and `added_by` when and by whom; joining one takes the person out of the other (a trigger), and in neither is maybe or no answer. Whoever sees the group answers for themselves, their household and their guests there, and its managers for anyone, invited or not; an answer is never a ticket or a sign-up. A party that takes a waitlist names it in `waitlist`: a plain group under the party, so the party's managers manage it, named `<party name> Waitlist`, `listed`, and starting as visible as the party, whose members wait in the order their rows' `added` gives. Wanting two places is two members, the person and a guest of theirs, and giving a place removes the waitlist membership and makes them a member of the party. Whoever sees a party sees its waitlist group; who is on it, whoever its `members_visible_to` lets in, plus the party's managers, the people waiting, their households and whoever put them on it. An invitation is an outbound `MESSAGE` and its `RECIPIENT`s, a recipient's `sent` blank until it goes, never a membership. Who sees a group is a group: `visible_to` names the group whose effective members see it - `everyone` for all, the group itself for its own members, any other group - and blank leaves it to its managers and its app's admins, a hidden group; `members_visible_to` says the same of who, among those, sees who is in it, blank for its managers alone. `everyone` is the role group whose two rules take in every person who is not a guest (`property=source`, `veracross` and `manual`), so a signed-in guest sees only the groups they are in, and an app's and a widget's `visible_to` name it when they are for all. `status` is `pending` (managers and the app's admins alone), `open`, `done` (an activity that happened, still shown), `cancelled`, or `closed` (gone from every list and page, kept for the messages that name it).

## Documents

A document's bytes and the places they appear are two tables. `CONTENT` is bytes of one type: one row per SHA-256 and type (`hash` and `mime`, unique together), the object in the media bucket as `content/<sha256>` (`blob`) and its `size`; the same bytes of the same type arriving twice - a school logo in every newsletter, a calendar PDF posted again - are one row, and the same bytes are one object whatever their type, so a plain-text body and the markdown read from it that happen to match are two rows over one object. `DOCUMENT` is a place they appear, a node in a tree: what it is to the community, where it sits, and the facts of that one appearance (`name`, `published`, `author`, `url`, `filename`, `content_id` for a mail part's `Content-ID`, `message`, `key_points`). The type is the bytes' (`CONTENT.mime`), never the filename's. A `CONTENT` row nothing references - its documents deleted, by the classifier, the import or by hand - is deleted by the sweeper (`internal/db/sweep.go`, running in production), woken by every swap once the read a start makes again after `deployOverlap` (`docs/storage.md`) is in, so it never takes a row the previous revision's last writes still reference, and its object leaves the bucket once no other row names it. A write that stored bytes and then failed removes them unless a row holds them.

A root is a whole thing the community received or published - a newsletter, a list message or a Loop post whose content is the `.eml`, a page, a portal resource, a year calendar - and carries a `kind`. Everything else hangs under a root through `parent` and carries the `relation` it has to its parent instead: `part` for each MIME part of a message - its text and HTML bodies, its embedded images, its attachments, never the `multipart/*` wrappers, which only hold other parts - `linked` for something a message or page links to that was fetched as content of its own, and `extract` for text read out of its parent's content, itself `text/markdown` content. A part of a part - a forwarded message's attachment, the text of an attached PDF - sits under that part. The load refuses a document with both a `kind` and a `relation` or neither, and a `relation` without a `parent` or a `kind` with one. The same Google Doc linked from three newsletters is three `linked` nodes over one `CONTENT`, each under the newsletter that linked it.

What reads documents by kind - `INBOX`, the calendar import - reads roots, so parts and extracts never land in anyone's inbox. `extracted` is set once the server has made the nodes read out of a document's content; blank means that work is still to do. One worker does it (`Extractor` in `internal/db/extract.go`): woken by every swap once the read a start makes again after `deployOverlap` (`docs/storage.md`) is in, so a new revision never extracts again what the previous one just did, it takes each document with `extracted` blank whose content type has an extractor, writes the children and sets `extracted` in one write. A message (`message/rfc822`) gets a `part` per MIME leaf, its bytes, type read from them, decoded file name and `Content-ID`; an HTML part gets an `extract`, its markdown (`internal/tomarkdown`, the same reading Helios Ask's documents use), and so does a plain-text part unless an HTML part sits beside it in the same message, which makes the HTML the message's one body: that text part is marked `extracted` with nothing under it, so it is never searched. An HTML part also gets a `linked` node for each image it shows (`internal/db/extract_images.go`), in the same write as its markdown: an `http(s)` `<img src>` becomes a node holding only its address in `url`, still to fetch; a `data:` one is decoded into its content there and then; a `cid:` one is skipped, being one of the message's own parts already; and one whose `width` or `height` is 1 or less is skipped as a tracking pixel and never fetched. A type with no extractor - images, PDFs, calendar invites - keeps `extracted` blank until one is written, and bytes already stored are reused. A document is read by the effective members, and the managers, of the groups it or a document above it was `sent_to` (`document_visible`, which follows `ancestors`), so a part or extract of an email is the email's like the email itself; mail (`newsletter`, `list`, `post`) sent to no group yet is read by nobody, and any other document sent to no group - a year calendar - by everyone signed in. Super admins read every document, its groups and its bytes. `CONTENT` is read by whoever may read a document or a message holding it.

A `linked` node with a `url`, no `content` and `fetch` blank is still to fetch. One worker fetches them (`Fetcher` in `internal/db/fetch.go`, in production only), woken by every swap once the start's second read is in, like the extractor. It takes each host's nodes one at a time, up to eight hosts at once, and writes each answer in a write of its own: bytes it keeps become the node's `content`, which the extractor then reads like any other; an answer that will never change sets `fetch` instead - `gone` for a 4xx other than those below, `sign_in` for a 401 or 403 or a redirect to Google's sign-in, which waits for a fetch run with someone's own credentials, and `refused` for bytes it does not keep, which for now is anything not an image, anything over 25 MiB and an image 1×1 or smaller. A 429 is waited out in the worker, for its `Retry-After` or a minute, at most a quarter of an hour, and asked again up to four times; a timeout, a 408 or a 5xx leaves the node as it was, tried again at a later swap, three times at most until the server restarts. Each fetch is logged (`fetch: done`, `fetch: stopped`, `fetch: waiting`, `fetch: failed`).

A `sign_in` node is fetched from a laptop, as someone signed in to Google: `go run ./tools/fetchsignin` (needs `IMPORT_KEY`, as `tools/devenv` exports it) starts the capture browser if it is not running (`docs/dev.md`), stops at once unless that browser is signed in to Google, reads every `linked` node with `fetch` set to `sign_in` and no `content`, loads each address in the browser and posts what came back to `/api/do/fetched` with the import key. A page still asking for a sign-in, a 401 or 403, a 408, a 429 or a 5xx is logged and left as it is, so a later run tries it again; any other 4xx sets `fetch` to `gone`. It ends by counting the nodes filled, gone, refused, still needing a sign-in and failed.

An email's groups come from its mailing list, or, when it came through none, from Claude. `/api/do/mail` reads `List-Id` (`mailGroups` in `internal/db/mailroot.go`): a school list on `heliosschool.org` or the old `heliosns.org` goes to the group its members are - `<room>.parents` to that room's Loop list `<room>-parents`, the three band lists to `halcons-parents`, `jayvens-parents` and `cospreys-parents`, `<room>.students` to the classroom, `parentsandstaff` to `parents` and `staff`, `parents`, `parentsonly`, `new.parents` and `newstudentfamilies` to `parents`, `parentsandstudents` to `parents` and `students` - and any other list (`community`, `chat`, the teachers' own lists, an outside mailer's) to `everyone`; Loop's own lists (`*.loop.heliosian.com`) are refused, since Loop files the mail it sends. A message posted again gains any link it lacks. Mail with no `List-Id` waits for the classifier (`Classifier` in `internal/db/classify.go`, running in production, held like the Extractor until a start's second read is in): once the message's body is extracted it gives Claude (`ClassifyModel`) the HTML body's markdown, else the plain one's, with the school's classrooms and grades and the classrooms the sender teaches, and asks whom it was written to; classrooms send it to their `<room>-parents` lists, grades (named without classrooms) to their `grade-<x>-parents` groups, neither to `everyone`, and an email to a group smaller than any classroom or grade is deleted with everything under it.

## Consent step

Rows of people who have not consented never leave the model to anyone but the import. The consent step (`consentStep` in `internal/db/consentstep.go`) is the one place that decides it, and it decides nothing else: it runs once per build, on every load and every staged write, after every part has built (the store's `consent` step, `docs/storage.md`), and fills `Model.Shown`, one `View` per table of the rows that may be shown.

- A person is shown when they are a guest (`source=guest`, always) or their `consent` is `listed`; a family group when its `consent` is `listed`. Anything else is hidden, including a person with no `consent` yet: it fails closed.
- Any row that references a hidden row, in any reference column, is hidden too, and so on until nothing more is: their emails, photos, settings, birthday years, memberships, rules naming them, mail from and to them, groups they added, whatever names a hidden family.
- A shown row has its `private` columns (marked `.private()` in `internal/db/schema.go`) removed, so a reader sees only the generated `phone` and `address`, blank when withheld, and never a person's or family's `consent`.

Everything that serves people reads only through `Model.Shown`: every query run's row access (scans, probes, paths, includes, ancestors, the viewer and the policies' own reads), effective members and rules, signing in (`signedIn`, so a withheld person is refused), and a person's write, which finds the row it names and every reference it sets there, so naming a hidden row is "no such row". A run as the `import` system reader, and the triggers, read the whole tables (`Model.Table`); so does the consent import, which works out consent itself.

## Queries

A query is one fully bracketed prefix expression, the operator first in every bracket: `(from TABLE [@name] (where cond…) (order path asc|desc …) (limit N) (include path…))`. A condition is `and`, `or`, `not`, a comparison (`=`, `!=`, `<`, `<=`, `>`, `>=`), `(in x "a" "b")` or `(in x (select TABLE.column cond…))`, `(blank path)`, `(exists TABLE [@name] cond…)`, or a yes/no path on its own; a value is a path, a quoted string, a number, `true`, `false`, `today`, `now`, `(count TABLE [@name] cond…)` or `(sum path TABLE [@name] cond…)`. Upper-case names are tables. A path is columns joined by dots, each but the last a reference followed to the row it names; it starts at the innermost row being matched, or at a named one (`@g.visible_to`), or at `@viewer`, the person the query runs as. Several conditions in one bracket are anded.

`db.Parse` reads a query and checks it against the schema before anything runs: a column or table that does not exist is refused with the nearest name (`no column grde on PERSON; did you mean grade?`), and each literal is read as the type of what it is compared with, so an enum value it does not have, an ID of the wrong table, text where a number belongs or a malformed date is refused. `Query.String` renders the canonical form: a bracket that fits in 80 columns stays on one line, otherwise its arguments go one per line, aligned under the first, a `from`'s parts each on its own line indented two, and the rendering parses back to the same tree.

`Model.Run(query, db.Env{Viewer, Now})` answers a `db.Result`: the IDs of the matching rows in order, at most the limit, and every row reached - those and every row the includes reach - by table and ID, each once. Comparisons follow the column's kind: text and enums ignore case, references and IDs match exactly, numbers and amounts compare as exact decimals, a date against a moment as that day's midnight, a moment to the minute as its first second, and an order key by `store.CompareKeys`. A blank cell equals nothing and orders after everything, and `!=` holds when exactly one side is blank. An equality between a reference column of the row being scanned and something outside it is answered from the model's indexes rather than by scanning. An `exists` or `select` that names no row outside itself (`@viewer`, literals, `today` and `now` aside) is worked out once per run and reused, and `in` looks a value up in a `select`'s answer rather than walking it, so a policy like `household @viewer` costs one scan per request, not one per cell. `BenchmarkEveryPerson` and its neighbours in `internal/db/scale_test.go` time queries and a write's rebuild over a synthetic school sized by `scaleFamilies`.

## The query API

The API is JSON. A query is a JSON tree with the same shape as the language, one object per bracket: `{"from": "GROUP", "as": "g", "where": [cond…], "order": [{"path": "name_sort", "dir": "asc"}], "limit": 20, "include": ["person"]}`. A condition is `{"and": […]}`, `{"or": […]}`, `{"not": cond}`, `{"=": [a, b]}` and the other comparisons, `{"in": [x, "a", "b"]}`, `{"blank": x}`, `{"exists": {"from", "as", "where"}}`, `{"path": "hidden"}` for a yes/no column, or `true`; a value is a JSON string, number or boolean literal, `{"path": "person.grade"}` (`@` starting a named row), `{"today": true}`, `{"now": true}`, `{"count": {"from", "as", "where"}}`, `{"sum": {"path", "from", "as", "where"}}` or `{"select": {"from", "column", "where"}}`. `db.ParseJSON` reads it and `Query.Tree` writes it; the language (Queries, above) is the form for people, and `db.Parse` compiles it to the same tree, so both are checked and run the same way.

`QUERY /api/q` on every app's host - the HTTP QUERY method, safe and idempotent with a body - takes one query as the request body, `application/json` for the tree or `text/plain` for the language, and runs it as the signed-in person: the `PERSON` whose address in `PERSON_EMAIL` is the one signed in (Spoof Mode's, when spoofing), the person who isn't a guest when a guest holds the address too. A request from anyone else is a 403, on `/api/q` and under `/api/do/` alike, reads and writes: an address on no person, or one whose person is withheld (Consent step, below), `hidden` or `deactivated`. It answers `{"now", "query", "result", "resources"}`, the resource API's envelope (`docs/api.md`, Reads): the school's time as the query saw it, to the second, the query in canonical text, the IDs it answers in order, and every row reached, the result's and its includes', keyed by table then ID, each once and as the reader may see it; a query sent as text also gets its JSON form as `tree`. A query that does not parse or check is a 400 with the reason, any other body a 415, and a body over 256 KiB a 413. Each query is logged with the viewer's person ID. Every answer carries a `Trace` header (`internal/trace`): a JSON tree of spans, each with its start (`ms`) and wall time (`dur`) in milliseconds from the request's start and, for a timed span, the CPU the whole process spent meanwhile (`cpu`), which exceeds `dur` when the garbage collector works on other cores. Work done once per row is a tally instead, its `count` and summed `dur` with `counts` of outcomes: under `run`, `redact` and `include` per result row, and `policy` with one tally per table read (and its column grants), split by each clause tried, named by its comment, so a slow read names the clause it spends its time in. Policy time is spent inside `scan` and `redact`, not beside them.

A request to `/api/q`, under `/api/do/` or under `/api/blob/` carrying `Authorization: Bearer <key>` passes sign-in without a session (`auth.Bearer`, the one path that does) and runs as the system reader `import` when the key is `IMPORT_KEY` (`docs/deploy.md`, the `heliosian-import-key` secret; the sample server's is `sample`), and is a 401 otherwise, never falling back to a cookie. The import has no viewer: it sees and writes exactly what the policies' `(system "import")` clauses grant (Veracross import, below), and the Change Log names it as the actor. Mutual TLS in its place waits on a load balancer in front of the service (#174).

`POST /api/q` takes an `application/json` batch of writes, `{"batch": [{"insert": "TABLE", "as": "name", "row": {…}}, {"set": "<id>", "cells": {…}}, {"delete": "<id>"}]}`, up to 16 MiB, and answers `{"result"}`, the ID each write touched. The server mints every ID: an insert's `id` and the tokens a row needs, and a write naming any ID column is refused. An insert's `as` names its new row within the batch, and a later write in the same batch says `@name` for it wherever an ID goes - a reference cell, or the row a set or delete names; a set or delete names only the row's ID, since its prefix says the table. A cell is text, a number, or `true`/`false` for a yes/no, and `""` blanks it. Each write is checked against the table's cells and then the write policies (Permissions, below) as the batch has left the model so far, and the batch is one transaction (`docs/storage.md`, Store): all of it goes in or none does, a refusal naming the write that failed. Addresses in `PERSON_EMAIL` are written in lower case, which the load requires, so the signed-in address finds its row; the load also refuses a `.noemail` placeholder, which stands for no address at all.

What is more than writing rows is an imperative call under `/api/do/` (`internal/db/do.go`): a `POST` whose body is what that call takes, answered in JSON, run as the same caller as `/api/q` and writing through the same batch path, so the cells, the policies, the triggers and the one transaction are `/api/q`'s. `POST /api/do/photo` takes multipart form data: the `person` or the `group` the photo is of (exactly one), the `photo` file and, optionally, a crop box (`crop_left`, `crop_top`, `crop_width`, `crop_height`, whole pixels of the re-encode); it refuses what is not a JPEG, PNG, GIF or WebP within the pixel limit, or a box that is not four whole numbers with a width and height above zero, checks the insert against the policies before storing anything, stores the original as sent in the media bucket under `photos/`, named by its own SHA-256, and adds a `PHOTO` row naming it in `original`, with the box, ordered before that person's or group's other photos, answering `{"result", "hash"}`. A photo is only ever added. `POST /api/do/fetched` takes multipart form data: the `document`, a `linked` node with a `url` and no `content`, and either the `body` a fetch got or a `stop`, one of `fetch`'s values. A stop sets `fetch` to it. A body is kept by the fetch worker's rules: one it keeps becomes the node's `content`, stored in the media bucket under `content/` as the worker stores it, and blanks `fetch`; one it does not sets `fetch` to `refused`. It answers `{"result", "hash"}` when it kept the body, else `{"result", "fetch", "why"}`.

Every picture is a `PHOTO` row, of a person or of a group - a person's portraits, a family's photos, a classroom's or grade's tile - as many as there are, the first in `order` the one shown; the load refuses a row naming both or neither. A photo is read by whoever may see its person or its group. A photo is its `original`, private since it can carry location and face tags, and what the server makes from it (`internal/db/pictures.go`): the re-encode (turned upright as its EXIF says, every tag dropped, a JPEG at most 2048 pixels on its long side), the crop of the re-encode when the row has a box, and the thumbnail of the crop, else of the re-encode, each stored under `photos/` by its own SHA-256 and nothing else beside it: the thumbnail is an object of its own. Any write that adds a photo or changes its original or box hands it, once the commit is in, to one worker that makes the three one photo at a time and writes their names back (`reencode`, `crop`, `thumbnail`) with `ready` set, unless the original or box changed again meanwhile. A change to the original or box clears `ready` in the same write (a trigger), so a photo is current exactly when it is `ready`, and until then its made columns are blank or what an earlier original or box made. The worker's queue is in memory: at startup it queues every photo not `ready`, which picks up whatever a stopped instance left unmade. No policy lets anyone write the made columns or `ready`. An edit to a photo's original or box made by hand in the sheet does not clear `ready`, so it is not remade until something else changes it. `POST /api/do/calendar-pdf` takes multipart form data, the `pdf` file and the `url` it came from; it refuses what is not a PDF, and when a `DOCUMENT(kind=calendar)` already holds the `CONTENT` with the PDF's hash it answers that document; otherwise it checks the inserts against the policies, stores the PDF (Documents, below) unless a `CONTENT` row already has its hash, and adds a `DOCUMENT` row with `kind` calendar, that `content`, the `url` and the moment of the upload as `published`, answering `{"result", "hash"}` with the document alone in `result`. `POST /api/do/mail` takes a raw message as the `eml` file the same way and answers the same: it refuses what does not parse as mail or has no readable `Date:`, answers the root already holding the same bytes, and otherwise stores the bytes as `message/rfc822` and adds a root read from the headers alone - `name` the subject, `published` the `Date:` in school time, `author` the person holding the From address (blank when nobody does), and `kind` `list` for a `List-Id` on `heliosschool.org` or `heliosns.org`, else `newsletter` - with a `sent_to` link for each of its list's groups (Documents, above).

Search (`internal/db/search.go`) covers every shown group and person, and every markdown `extract` of a document. Each row's search input is built from what every reader of it may read - a group's name, subtitle, kind, the names of the groups above it, its times, timing, location and description; a person's shown name, pronouns, grade, classroom, crew, department, job title, facts and bio; an extract's email (its subject, kind, when it was sent and who sent it), the part it was read from (file name and type) and its markdown, which the searcher reads from the bucket once per `CONTENT` row and keeps in memory - and its entry is kept in the media bucket as `search/<SHA-256 of the input>.json`: a summary and keywords Claude writes (`SearchModel`, the prompt `searchSystem`), and the input in chunks, each with its Vertex vector. The name is the input alone, so an unchanged row is never sent again, and a changed model or prompt takes deleting every `search/` object for the worker to make them all again. After every commit and refresh (`queue.OnSwap`) the searcher works out every row's input off the request path, reads the entries it lacks from the bucket and, in production and the sample server, queues those the bucket lacks for its makers; a laptop's real-data server reads entries but makes none. Where entries are made, an entry no row's input wants any longer - a deleted group, person or extract, or a row whose input changed - leaves the bucket in the same pass, an entry finished for a row gone meanwhile is dropped rather than kept, and the first pass after startup lists `search/` and removes every object no row wants, catching what went while no server was watching. A maker that fails goes back on the queue after `searchBackoff`, keeping Claude's summary when only the embedding failed so Claude is not asked twice; an answer that asking again would repeat - cut short, refused or unreadable (`claude.ErrFinal`) - is logged and not asked again until a restart. The searcher's index is the generated `SEARCH` table, a row per group and person with its input, summary, keywords, how many chunks, its object and whether it is made, read by super admins alone; it is read from the index as it stands, so an entry made since the last commit shows at once. `go run ./tools/searchplan` counts the rows production would make and estimates what Claude and Vertex would cost, for running before anything that makes a backfill. `POST /api/do/search` takes `{"words"}` and answers a stream of server-sent events, run as the caller and keeping only rows the policies let them read, each a list of `{"id", "summary"}` in order: `words`, the rows whose input, summary or keywords hold the most of the words, at once and with no outside call; then `meaning`, ranked by the closest chunk to the words' own Vertex vector plus a share for the words they hold; or `error` if the meaning search fails.

A blob cell, in any table, holds its object's full name in the media bucket - `photos/<sha256>.jpg`, `pronunciation/<sha256>.mp3`, `content/<sha256>` - never a bare name whose folder the code would have to know. `GET /api/blob/{id}/{column}` (`internal/db/blobs.go`) is the one way to fetch one: it reads the row as the caller, as `/api/q` would, and answers the object when they may read both the row and that cell, typed by the row's `mime` where its table has one (`CONTENT`) and otherwise by the type stored with the object, always under a `Content-Security-Policy: sandbox` of its own, so a stored page or SVG opened directly runs nothing, and a 404 for anything else - a row or cell they can't see, a column that is not a blob, a blank cell, or an object the bucket lacks - so a private cell such as `PHOTO.original` is the import's alone. Its `ETag` is the object's name, so a browser's revalidation of an unchanged cell answers 304 without reading the bucket.

Triggers (`triggers` in `internal/db/trigger.go`) are writes that follow from a write, staged in the same transaction after it and checked against the cells but not the policies, since the code makes them, not the writer; a trigger's writes fire triggers in turn. A family's `name` is its members' last names, kept in step whenever a person or a family membership changes: the last word of each `name_long` (the override, else the import's) of its members who are listed, not hidden and not deactivated, students before everyone else, each once whatever its case, leaving out a name that is one part of another's hyphenated name (Chang and Farh go when Chang-Farh is there), joined with ` & ` and followed by ` Family`, and blank when no one is left. Another trigger keeps school groups' members in step with people: when a person is added, or their grade, classroom, crew or department (the override, else the `vc_` column) or `deactivated` changes, their `MEMBER` rows in classroom, crew, grade, band and department groups become exactly one row with `member=yes` in each of their classroom, crew and department and the grade group whose `slug` is `grade-` and the grade (`grade-k` … `grade-8`), and none at all once they are deactivated. A grade no group carries refuses the write. Nobody is a member of a band directly: the import gives a band a rule for each grade and classroom under it, so it holds everyone in them.

## Permissions

Who may see and change what is written in the query language, in `policySource` in `internal/db/policy.go`, compiled when the package loads: code, never a sheet, since whoever could edit a policy could grant themselves anything. Whom a policy names is data - the members of an app's admins group, a group's `visible_to` and `members_visible_to`, who manages what. Every clause for the same thing is or-ed, so each grant is a line of its own. The source is in sections by whom the clauses are for - definitions, everyone, each app's admins, super admins, and each system reader - and every clause carries a one-line `;` comment saying what it grants, so each can be checked against its purpose. Policies never decide consent: they see only the rows the consent step shows (Consent step, above), and decide who sees what among those. `;` starts a comment running to the end of the line anywhere in the language. A `define` no clause calls, directly or through another definition, refuses to load.

Nothing is readable until a clause says yes, rows and columns alike, so every read clause only ever adds readers.

- `(read TABLE condition)` decides which rows a reader sees, the row being `@row`. Every table has one; a table with none would show nobody anything.
- `(read TABLE (column…) condition)` decides which of those rows' cells a reader sees, and blanks a listed column where the condition fails; a column is read only on a row the reader already sees, so `true` means everyone who sees the row. The policies refuse to load unless every column that isn't `private`, in every table, is listed in some column clause, so a new column stays unreadable until a clause names it; a column no person reads is listed with `false` (`PERSON.signed_out` and `deactivated`, which the import alone is granted), since marking it `private` would strip it from the rows the policies themselves read. A column clause naming a `private` column is refused: the consent step keeps those from everyone but the import, which sees them whatever the clauses say.
- `(set TABLE.column condition)`, `(insert TABLE condition)` and `(delete TABLE condition)` decide writes, over the row before (`@old`) and after (`@new`). `Model.Authorize(env, db.Change{Table, Old, New})` checks one: an insert has no `Old`, a delete no `New`, and a set needs a clause for every column it changes. A change no clause allows is refused (`access.Forbidden`).
- `(define (name @row-parameter value-parameter …) body)` names a condition, or a `select`, that any query calls by name, a policy or a client's alike: the definitions are the Definitions section of `policySource`, each with a comment saying what it decides, compiled once when the package loads and never changed after, so a name means the same everywhere. A call is expanded where it stands, a bare column passed to it meaning that column of the row in hand.
- `(ancestors @g)` is a row and every row above it through `parent`, in any table whose `parent` names its own table (`GROUP`, `DOCUMENT`), and `(system "name")` holds when the run is that system reader (`Env.System`), so a person's query never meets it. A policy clause binds `@row`, or `@old` and `@new`, to the row it decides on; any query may name its own rows so too, so a condition copied out of a clause runs as `(from TABLE @row (where condition))`. Only `@viewer` can't name a row.

`GET /api/policies` answers every clause and definition with its section, its comment and its canonical form, in source order, which the reader keeps from the `;;` and `;` lines before each form. A clause's `actor` is the `admin_of`, `super_admin` or `system` call its condition is, or that an `and` starts with, and `rest` is what the condition requires beyond it (`true` when nothing); a condition naming no actor has a blank `actor` and the whole condition as `rest`. `GET /api/explain/{id}` (`internal/db/explain.go`) answers, for one row, whether each read clause of its table holds for the caller and which column clauses hold for each column, each verdict also saying whether its actor holds (always, for a clause naming none) and whether its rest does; it answers only when the caller may read the row, or when the signed-in person behind a Spoof Mode view could read it as themselves, and is a 404 otherwise, so it tells no one about a row they could not see.

`Model.Run` applies the read policies to every row a client query touches - the rows it lists, every row an `exists`, `count`, `sum` or `select` inside it scans, and every row a path follows a reference to - and the column policies to every cell it reads, so a condition can't learn what the reader can't see. A reference to a row the reader can't see reads blank, in conditions and in what is answered. Policies themselves, and `EFFECTIVE_MEMBER`'s rules, run unfiltered.

The layer knows nothing of the apps on top of it but their admins: an app's admins are the super admins and the effective members of its `APP` row's `admins` group (`admin_of`), and each app's grants are a block of clauses naming exactly the groups, by kind or flag, and the tables they open - a When admin reads every event and school day and their members, rules and mail, and sets an event's status and who manages it: makes a plain group, names it in the event's `managed_by`, and adds and removes its members; a Loop admin does the same for every group with `mail`. An app's admin changes the members of a managers group only when it is a plain group, neither a role group nor a mail list, managing nothing but that app's groups and itself, so pointing a group's `managed_by` at another group never lets them change who is in that group. Everything else in the policies is about people, groups, membership, managing and visibility.

## Changes

`CHANGES` is the history of every row: the store records one entry per row a commit inserts and one per cell it sets or deletes, cascades and triggers included, in the `CHANGES` tab of the sheet it changed, and the model reads the five tabs as one table (`db.EverySheet`). An entry is minted an `id` (`chg`), and holds `at`, the moment to the second in the school's time zone; `actor`, who the change was made as, and `real_actor`, who was signed in, the two differing under Spoof Mode, with work nobody signed in naming itself (`import`, `pictures`); `action`, `insert`, `set` or `delete`; the `table` and the `row` changed; and for a set or a delete the `column` and what it held before (`previous`). An insert names no column: its values are the row's. An entry joins the model in the same commit as the change it records (`docs/storage.md`, Change Log), and nothing writes one but the store: no policy lets anyone insert, set or delete one. `row` may name a row since deleted, so the build checks only that it is an ID of a current table, and dropping a table means deleting its rows' history with it; the consent step hides an entry that names a hidden row, as it would any row, and one about a `private` column, whose `previous` would otherwise carry the private value. The super admins read the rest (`(read CHANGES (super_admin))`).

## Effective members

`EFFECTIVE_MEMBER` is generated: who is in a group, each row's `id` derived from the group's and the person's (IDs, below), with the `reasons` they are in (`member`, or `rule` and the rule's order). It starts from the group's rows with `member=yes`, adds everyone a rule selects, then takes away everyone a rule with `exclude` selects, everyone with `member=excluded` and everyone deactivated, however they came in. A rule selects with every selector it fills in at once: a target group's own effective members (never those of the groups under it), one person, free text found in a name or an address, or a person column (`property`, which the load refuses if `PERSON` has no such column, it is `private`, or no `true` column clause opens it to everyone who sees the person); rules and effective members read only shown rows (Consent step, above) holding `value`; then `replace_with` replaces them with their `parents` (for a student, everyone in their families who is not one), `children` (for someone who is not a student, the students in their families) or `household` (everyone in their families, and themselves), a student being a member of the `students` role group, and keeps only those in `within`'s effective members. A group already being resolved further up the same chain contributes nobody, so lists that include each other resolve. Each group's members are worked out the first time a query asks, once per version of the model.

## Inbox

`INBOX` is generated, and holds no rows while the school's past mail is uploaded into `DOCUMENT`; a reader sees only their own rows.

## Veracross import

`tools/import` runs a fresh Veracross export and a fresh export of the school website's staff page (`docs/dev.md`, Tools), reads people, their emails, the family, role, classroom, crew, grade and band groups, the family and role groups' members and the bands' rules with `QUERY`s to `/api/q`, works out what differs, and sends it as one `POST` batch, all with the import key; `--dry-run` prints the batch and the number of photos it would add, and sends nothing. After writing it reads and plans again, refusing to go on unless that plan is empty, and then adds through `/api/do/photo` each Veracross and staff-page portrait the person does not already have, comparing by SHA-256; the Veracross portrait is added last, so it comes first. Then it runs the calendar import's PDF stage (Calendar import, below). It reads and writes nothing else, and the `(system "import")` clauses in the policies grant exactly that, but for their last section, which is the sync from the old sheets: it runs with the import key too, writes the old directory's hand-kept rows (overrides, extra addresses, family pictures, photos, tags, room parents, admins, colors, settings and every old ID as an `ALIAS`), and goes when the last app is cut over. An old crop was a separate, scaled and re-compressed image, so the sync works out each one's box by matching it against the re-encode of its original. The import key may also add a `linked` `DOCUMENT` still to fetch under an email's HTML part, so that HTML extracted before extraction placed its images can have them placed afterwards, and may fill one still to fetch - set its `content` and `fetch`, and store an image's `CONTENT` - which is what `tools/fetchsignin` does through `/api/do/fetched`.

- **People.** An email identifies one person: export rows sharing an email are one person and rows with different emails are different people, whatever their names. Rows of the same role and name where one has no email are one person too; placeholder emails containing `.noemail` don't count. Names are compared as resolved (`Juni (Juniper) Ashdown` as `Juni Ashdown`), since a staff member's household copy often carries a parenthetical the staff export leaves out. Each is matched to a `PERSON` by an email in `PERSON_EMAIL`, else by `vc_name` when exactly one person not already matched by email carries it. Emails belonging to two people, a name two people carry, two export people matching one, or a parent and a staff member of one name where one of them has no email refuse the run. Anyone unmatched is inserted with `source` veracross. The import writes the `vc_` columns, `vc_name_long`, `vc_name_short` and `vc_name_sort` among them (Veracross's `Juni (Juniper) Ashdown` read as preferred first name, legal first name in brackets, last name), and clears `deactivated`; a veracross person the export no longer lists gets `deactivated` set to now. Job title is Veracross's, else the staff page's; the bio is the staff page's, matched to staff by any of their emails on file - the export's, or another `PERSON_EMAIL` row recorded for a staff page that lists an older one - else by a name exactly one of them has.
- **Emails.** The export's emails become `PERSON_EMAIL` rows with `source` veracross. A new one takes over a veracross row whose email has gone, so the primary stays put; the first email of someone with none is primary.
- **Groups.** A student's classroom and crew and a staff member's department (Veracross's `person_department`, its names as they are) are matched to groups by name (a crew within its classroom), and a missing one is added, as are any of the nine grade groups (`grade-k` … `grade-8`) and their bands, and the role groups `students`, `parents`, `staff` and `adults`, `group`s found by slug, and `everyone` with its two rules when it is missing; every group the import adds is `listed` and visible to `everyone`, its members too. A grade's `parent` is its band, a classroom's is the band of its students' grades, set whenever it differs, and a crew's is its classroom; a classroom with students in two bands refuses the run. A band's rules are kept to one targeting each grade and classroom under it, and nothing else. Each grade has a Parents group (`grade-k-parents` … `grade-8-parents`, named like `Grade 3 Parents`), added when missing, whose rules are kept to the one targeting its grade with `replace_with` parents, so its effective members are that grade's parents.
- **Families.** A household is matched to the family whose parents (its members who aren't students) are exactly its adults, else to the one with a member and a parent in it that shares the most adults; when two households match one family the one sharing more adults keeps it, the first in the export on a tie, and a household matching none gets a new one. Its `vc_address` and `vc_phone` are the household's, everyone in it has `member=yes`, and its `managed_by` is itself; no one else may change who is in a family.
- **Memberships.** In family and role groups (but `everyone`, whose rules fill it) the import adds the rows it wants, sets `member` where it differs, and removes the others belonging to people it manages - those it lists and every veracross person - so a deactivated person leaves their role groups but keeps their families. School groups follow from the trigger (The query API, above).

## Calendar import

The school's calendar reaches the data model from two sources, each in its own stage writing as `import` through the batch path: its public Google Calendar, from the server, and its published year calendar PDF, from `tools/import`. Both plan with the same code in `internal/db` (`calendarplan.go`), over the rows they read - the server from its own model, the tool through `QUERY /api/q` - so they agree on what a source's rows are.

- **What a source makes.** A Google event is a `GROUP` of kind `event` (`listed`, status open, visible to `everyone`, its members too) carrying the event's title, start, end, `all_day`, location and description, with a `GROUP_SOURCE` holding the same as Google has it, its key in `calendar_event` and the classifier's input hash in `hash`. An instance of a repeating event has as its `parent` an `event` with no `start`, the recurring event, found by its own source whose `calendar_event` is the repeating event's UID. An entry of the PDF's Important Dates is an `event` group the same way, its source naming the PDF's `DOCUMENT` instead. Before that, Claude is shown each entry beside the events Google brought on its dates and answers which of them it is, however differently worded, possibly several ("Last Day of School, Graduation" is Google's two events) or none (`MatchPDF`); a matched entry gives each of those events a second source and makes no event of its own. A group is deleted, with everything under it - its parts, rules, members, document links and sources - once its last source is gone.
- **Who it is for and what it is.** Claude classifies each event into exactly one category - any category that is not a day type and sits at the top or under another category, Misc when no other fits, so no event is outside the categories - the classrooms it concerns, and who of them it is for: `families`, `parents` or `staff`. Schedule is only for an event about the school day itself; an event that also changes the day keeps its own category, and the change is its day. The category becomes the group's `parent` (a recurring event's instances stay under it and it takes the category of the latest one classified), and the rest its rules: a rule per classroom with `replace_with` the `household` for families or the `parents` for parents, or one rule on the `everyone`, `parents` or `staff` role group when it concerns every classroom or is for staff, so the event's effective members are exactly whom it is for.
- **School days.** A day is a `GROUP` of kind `day` on its date whose `parent` is its day type's category, with a `day_part` child per part of that type's usual times, titled with the part (Dropoff, School, Pickup, Aftercare) - `DayTemplates` in `internal/db/daytypes.go`, keyed by the day-type titles. A day for some classrooms carries a rule per classroom; one for all carries none. Each source owns its own days and neither stage touches the other's: the PDF stage wants a day for every weekday from its first-day to its last-day entry, Regular unless the grid shades it or an entry with a day type covers it, one day per day type when classrooms differ, and the first and last days' sources carry `marker`; a new version keeps each day an earlier version made on the same date with the same day type and classrooms, moving only its source to the new version, and removes or adds only the days that differ; the Google stage writes a day per weekday of an all-day event the classifier gives a day type, for the event's classrooms, and removes them with the event. Removing a day or an event removes everything that names it - its parts, rules, members, document links, sources and the `ALIAS` rows of old IDs pointing at it - so a day the latest PDF no longer shades goes, and its old link with it. Where the two disagree there are two days for one date and classroom, and what reads days decides.
- **Classifying.** Events go to Claude ten to a call, the answer one required object per event under a handle, each echoing its title so a skipped or swapped answer is caught and asked again once. The hash on a source covers the event's text and dates, the classroom vocabulary, the day types and the classifier's whole prompt, category descriptions included, so an unchanged event is never sent twice and a renamed classroom or a reworded category reclassifies everything. A batch that fails leaves its events as they were, with their old hashes, so the next run asks about exactly them.

The Google stage (`CalendarWatcher` in `internal/db/calendargoogle.go`) runs in the server on Cloud Run alone, Cloud Run's `K_SERVICE` marking it, so a laptop's real-data server never writes the calendar. It reads the calendar named by `SchoolCalendarID` in `internal/db/calendar.go` through the Calendar API as `directory@`, single events from the first of July of the previous school year for three years, so Google expands repeating events itself; times are school wall-clock, all-day ends inclusive, and HTML descriptions flattened to text keeping each link's address. Only that window is mirrored: a source outside it is never removed. At startup it opens a watch channel posting to `https://when.heliosian.com/hooks/calendar` and runs once; each post kicks a run, at once or the moment the current one ends, so changes during a run collapse into one; every hour it runs unasked and renews the channel once it has under two hours left. A post carries the channel's token, an HMAC of the session key, checked before anything else. Its log lines are in `docs/deploy.md` (The school calendar watch).

The PDF stage (`tools/import`, `calendar.go` and `calendarread.go`) fetches the school's calendar page (`SchoolCalendarPage`), follows its PDF link, and stops there when a calendar `DOCUMENT` already holds the `CONTENT` with the PDF's hash and every source naming it carries the current reading's hash, which covers the reading prompts and the model. Otherwise it reads the PDF in stages, each its own Claude call at maximum effort: the legend, into wording, an estimated color and a day type per swatch; the Important Dates list, into entries whose day type comes only from a dismissal note in the wording; and the twelve month grids, one call per month over a crop of the page rendered at 300 dpi with poppler's `pdftoppm`, each read twice and a third time to break a tie, each read naming every day and echoing the grid's title so a changed layout fails loudly. It classifies the entries that are new, refusing to go on unless every one was classified, posts the PDF to `/api/do/calendar-pdf`, and sends one batch: its year's days replaced, entries kept, matched or added, and the sources of entries the PDF no longer lists removed. A `429` from the school's site is waited out and asked again four times over about a quarter of an hour.

## Consent

The opt-in form's responses live in the form's own spreadsheet (`PREFERENCES_SHEET`, tab `Sheet1`), which this service does not own and only reads. On Cloud Run the server keeps `PERSON.consent`, `address_consent` and `phone_consent` in step with it (`StartConsent` in `internal/db/consent.go`): a goroutine reads the responses at startup and every minute, and after each read, and whenever the data model changes, works out each person's consent from the last responses read and writes what differs through the batch path as `import`, so its own write finds nothing more to change. A swap only signals it, so no commit waits on it. It never runs on a laptop, so a real-data dev server never writes production.

- A response belongs to the person holding its email in `PERSON_EMAIL`, any of their emails; one matching nobody is skipped.
- Families sharing a member are linked, and the latest response from anyone in linked families governs everyone in them; someone in no family is governed by their own latest response.
- A governing opt-out withholds the person (`consent=withheld`); so does having no answer, for anyone not in the `staff` role group. Address and phone are `shared` only where every governing response shares them, and `withheld` for anyone withheld; staff with no answer share both. A family's `consent`, `address_consent` and `phone_consent` are `listed` or `shared` only when every one of its parents' (its members who are not students) is, and `withheld` for a family with no parents. A withheld address or phone is never shown, not even to its owner: the site and the API act as if there were none.
- A withheld person or family is never shown (Consent step, above), to anyone, themselves and admins included; only the import sees them. Veracross's own privacy has already been applied to the export; `vc_address_visibility` and `vc_phone_visibility` are only there to explain it on the profile. Guests are left alone, so someone withheld, hidden or deactivated who is in a list or invited is held twice: their own row, never shown, and a guest with the same address, shown to whoever sees the members of a group the guest is in.
- Every value is matched word for word - the opt-in answers, the two permissions, the timestamp format - and anything else stops the run with the reason logged, writing nothing, until the form or the code is fixed; an empty permission cell shares neither.

## IDs

An ID is a three-letter prefix naming what it identifies, then 11 symbols of upper and lower case letters and digits, about 65 bits; the prefixes are the `*Prefix` constants in `internal/db/id.go`. IDs are case-sensitive and are never trimmed: `db.ParseID` accepts only the exact form and answers the prefix, and `db.TableOf` the table keyed by that prefix, so an ID found anywhere - a URL, a log line, a cell - says which table holds it. `db.Mint` draws a new one, again while `taken` refuses it. A generated row has no stored ID to mint, so `db.Derive` makes one from what the row is: the first 64 bits of the SHA-256 of its parts, in the same 11 symbols, the same on every read; an `EFFECTIVE_MEMBER` row's is its group's and person's under `efm`. Two kinds are minted the same way but name no row: the secret tokens a collection's feed (`COLLECTION.token`, `fed`) and a mailed copy's links (`RECIPIENT.token`, `tok`) carry, which are kept apart from the row's own ID so the ID can be shown and passed around freely. A membership's `purchase_id` is text, the payment provider's reference.

## Cells

`Column.Check` and `Table.Check` read a cell as its kind requires: an enum one of its values in any case, a reference an ID whose prefix is its target table's (any table's for `MESSAGE.about`, `ALIAS.target` and `CHANGES.row`), a yes/no, a date (`2026-09-24`) or a moment in the school's time zone, to the minute as people write one (`2026-09-24 16:00`) or to the second as the server stamps one (`2026-09-24 16:00:05`, `cells.StampFormat`), an order key, an address or a link as `internal/cells` and `internal/store` read them everywhere else, and an amount as digits with up to two decimal places. A blank cell is accepted unless the column is required; a column a sheet holds that the table does not declare is ignored.
