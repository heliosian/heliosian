# Fast queries

How to write a query the engine answers quickly, how to find out where a slow one spends its time, and how to measure a change so it counts. The language, the policies and the API are in `docs/datamodel.md` (Queries, The query API, Permissions); this document is the cost model behind them and the working method that has held up. The target is a page's first load under 100 ms on the server for every viewer, including the first load after a swap; a per-viewer answer cache does not count, since the first load is the one that matters.

## What a query costs

A run (`Model.Run`, or every query of a `RunAll` batch as one reader) does the same work for every row it touches, and the cost of a query is the number of rows it touches times the work per row. The pieces, in the order a scan does them (`scan.each` in `internal/db/query.go`):

1. **Candidates.** A scan either probes an index or walks its whole table. A probe is an equality or `in` between a reference or enum column of the row being scanned and something outside it: a literal, a list of literals, `@viewer`, an outer row's cell, or a `select` that names nothing of the scanned row. An `or` whose every branch is a probe, or such an `or`, probes too, as the union of its branches' rows, each once and in table order. With several probes the scan looks up by whichever answers fewest rows (`pickProbe`, `candidates`), an ID or reference before an enum, an equality before an `in` and an `in` before an `or`. Without one it walks every row of the table.
2. **Cheap conditions.** Conditions that read only literals, `today`, `now` and the row's own non-reference cells run first, in the order written, before anything else is paid for. `(= kind "event")`, `(blank start)`, `(>= end today)` and `(in slug "students" "parents")` are cheap; anything through a reference (`parent.kind`), anything naming another row (`@g`, `@viewer`), a definition call, an `exists`, a `select` or an `and`/`or` containing one of those is not. A test on the row's own reference column is not cheap either: a reference to a row the viewer can't see reads blank, so `(blank parent)` needs the parent's read policy before it can answer. An `and`, and so a definition, is cheap only when every part is: `own_group` tests `kind`, which is cheap, and `parent`, `url` and `visible_to`, which are not, so the whole of it waits for the read check, and the enum test inside it offers no probe.
3. **The read check.** Each surviving row goes through its table's read clauses as the viewer (`readable` in `internal/db/policy.go`), once per row per run, the verdict cached for the rest of the run. A clause that cannot read the row - one on every table (`read *`, `read * (*)`) or one that is just `true` - is tried once per run for its table or column (`everyRow`), and when it holds, no row of that table, or no cell of that column, is checked one by one, so a super admin pays nothing per row or per cell. Clauses that start with an actor test (`admin_of`, `super_admin`, `birthday_team`, `mode`) are tried first, so a viewer who is a super admin or the app's admin stops at the first of them; a parent falls through every one of them to the ungated clauses (`visible`, `sees_members`, `person_visible`), which read memberships. A system reader (`Env.System`) skips the check entirely.
4. **The other conditions**, in the order written, on the rows the read check let through.
5. **Redact, include, encode.** Each answered row has every column's grant checked and the ones the viewer may not see removed; each include follows a reference, read-checks and redacts the row it reaches, and so on down the path, once per row: a row the answer already holds whole - an earlier include's, or one of the answered rows when the query names no columns - is not checked or redacted again; the whole answer is encoded as JSON and compressed. Each is per row, so an answer of a hundred thousand rows is slow whatever the scan did.

Inside a condition, a `select`, `exists`, `count`, `sum` or definition call is itself a scan with the same costs, and three rules decide how often it runs:

- A `select` that names nothing outside itself and has no probe is **fused**: the run fills it, and every other such select on the same table in the batch, in one pass over the whole table (`fuse`). The pass runs each select's cheap conditions on a row first and read-checks the row only when some select's cheap filter admits it, so the pass is cheap when every fused select on the table has a cheap filter and costs the whole table as the viewer when any one of them has none: one unfiltered select makes the pass expensive for all. It is charged to whichever query first needs any fused select on that table, and the server runs a batch's queries in the sorted order of their names (`internal/db/http.go`), so the query it lands on is often not the one that put the costly select there. The trace counts the pass under `fuse`. A select with a probe costs its candidates alone.
- A scan that names nothing outside itself, or that is guarded (a client's, not a policy's), is **memoized** for the run by its text and the IDs of the outer rows it reads (`remembered`, `memoKey`). A definition called on a thousand groups is worked out once per group; a select that reads only `@viewer` is worked out once per run. A policy's own `exists` and `select` are memoized only when they read no outside row, since the row verdict is already cached.
- `in` and `tally` look a value up in the select's answer, a hash lookup per row; `exists` runs a scan per outer row.

Two facts about the data drive everything above. `EFFECTIVE_MEMBER` is large, since every event's audience is its membership, and is indexed by `group` and by `person`; looked up any other way it needs every group's members. And `GROUP` has thousands of rows of which a viewer's rail wants a few hundred, so any query that walks all of `GROUP` as a parent pays `visible` on every row.

## Writing the query

Each rule below comes from a query that was slow in production and the form that replaced it.

**Compare the row's own column with something outside it, never through a path.** `(= group.slug "everyone")` follows `group` on every membership row and read-checks every group it lands on. `(in group (select GROUP.id (= slug "everyone")))` probes the membership index for the one group the select answers. `TestInAConstantSelectProbes` holds the second form to a probe.

**Every branch of an `or` a probe, or none of the `or` probes.** `(or (= person @viewer) (in person (household @viewer)))` probes `person` twice and reads the union; add a branch that is not a probe - a path, an `and`, `false` - and the whole `or` walks the table. `TestAnOrOfProbesProbesEachBranch` holds the page queries of that shape to a probe and their answers to the walk's. The same goes for a select whose condition is an `or` with a path in it: `(select GROUP.id (or (in slug "students" "parents" "staff") (and (= kind "group") (= parent.kind "gradeband"))))` is fused over all of `GROUP` with no cheap filter, where two selects, one per branch, give the first a cheap filter and the second an enum probe. Splitting it counts only if every other fused select on the table in the same batch has a cheap filter too: measured on Who?'s batch, the split alone changed nothing, because the tag selects behind `navTags`, with `own_group`'s reference tests, kept the shared pass read-checking all but two of GROUP's rows.

**Give every select a probe when the group in hand is known.** A definition's select that names nothing outside itself is fused over its whole table on every request that calls it, six tables for `implementation_only` before each of its selects gained `(= <column> @g)`. With the row in hand named, the select probes that column's index for it and is memoized per group. Read `implementation_only` in `internal/db/policy.go` for the shape, and `TestABatchScansEachTableOnceForItsSelects`, which checks that the definition fuses nothing.

**Settle an exact count with an `exists` when the answer only needs a bound.** `implementation_only` asks whether exactly one row names a group, and its probed selects return every row that does: for an audience group such as `everyone`, about every group in the table, each run through `counted`'s reference follows. `sidebar_group` therefore tests `shared_audience` first, two distinct counted rows naming the group in `visible_to`, which an `exists` answers at the second row; the full count runs only for groups that test leaves open. The two forms answer the same rows by construction, and a whole-table query asserting that no row passes both is the check to run before trusting a short cut like it.

**Put the cheap conditions first and the definition calls last.** Cheap conditions run before the read check whatever their position, but among themselves and among the rest the written order holds, and a scan stops at the first condition that fails. `runCondition` and `joinedCondition` in `web/common/rail.js` test membership first and `(sidebar_group @g)` last, so the twenty-odd probes behind it run only on the groups the viewer runs or is in, not on every group of the table. `BenchmarkSidebar` keeps the same order; a condition order change shows there before it shows on a page.

**Filter on the row's own cells before anything reads other rows.** A date test such as `(or (blank start) (and (not (blank end)) (>= end today)) (and (blank end) (>= start today)))` runs before the read check and before any definition, so rows the page would drop in the browser anyway never reach the policies, redaction or the wire. Before moving a browser-side filter to the server, read what the browser does with the rows it drops: `liveLists` resolves an undated row's date through its parent chain, so the server-side form keeps undated rows and leaves them to the client.

**Fetch what the page draws, nothing else.** The largest savings so far were rows nobody used: event invitees read for a "member" mark that the viewer's own memberships answer (`navMine`), and every list's members loaded on the first page when only the opened list's are drawn (`fetchGroups` when a group's page opens). Before adding a query to a page's first load, name the element that draws each row of its answer; a row with no element is a row to cut. Then trim columns with `(columns …)`, which also limits the column grants checked, and include only the paths the page follows.

**Test membership from the viewer's side.** `(exists EFFECTIVE_MEMBER (= group @g.managed_by) (= person @viewer))` is a scan per group. `(in @g.managed_by (select EFFECTIVE_MEMBER.group (= person @viewer)))` is one memoized set per run and a hash lookup per group; `manages` is written this way. The same rewrite applies to any clause that asks whether the viewer is in a group named by the row.

**Share one run.** A page's first load is one `{"queries": …}` batch, so the policy verdicts, the memoized selects and the definitions one query works out are reused by the rest. The cost of a definition shows in whichever query first calls it; moving a query earlier or later in the batch moves the cost, not the total. A query sent on its own pays everything itself. The same holds for read checks: a verdict is cached for the run, so as a parent the first query to walk GROUP whole pays `visible` on every group and every later walker looks cheap. Fixing that first walker moves the cost to the next one, `effective` to `groups` to `navJoined` on Who?, and the cost leaves the batch only when no query in it walks the table whole.

**Count the viewer's rows, not the owner's.** A super admin is the cheapest viewer: every read check stops at a gated clause, so their numbers are a floor. A parent reaches `visible` on every group they do not manage, and `person_visible` on every person. Every change is measured as both before it counts, and a whole-table scan that looks fine as the owner is the one to suspect.

## Reading a trace

Every `/api/q` answer carries a `Trace` header (`internal/trace`; `docs/datamodel.md`, The query API). `go run ./tools/q read --trace '<query>'` prints it indented after the rows, as the signed-in super admin; `--spoof <address>` before `read` runs it as that person, and `--local <address>` sends to the laptop's `startserver --real` instead of production (`docs/dev.md`, Tools). What to look at:

- `request` is the whole, `run` one query, `scan` its candidates through the conditions and the read check, with `table` and `rows` set. A `scan` far longer than its `policy` tally is time in conditions, usually a fused select or an `exists`.
- Trace a query inside its batch, not alone. Alone, `effective` ran in 4 ms as the parent; in Who?'s batch it took 15 to 20, because the shared fused pass and the first whole-table read checks landed on it. The batch timer under `local/` prints one named query's `run` span from a warm round for this.
- `fuse` is a tally of whole-table passes by table. Any entry on a page's first-load batch is a select to give a probe. One pass per table per batch is the most a fused select can cost, since the pass fills every fused select on that table at once.
- `policy` has one tally per table read, with the row count and `held`, and one child per clause tried, named by the clause's comment, with its own count and time: a slow read names the clause it spends its time in. A `cached` count is rows whose verdict the run already had. A table with tens of thousands of checks in a query that answers forty rows is a scan or select walking that table.
- `redact` and `include` are per answered row; `GROUP columns` and its siblings under `policy` are the column grants. A large `redact` with few rows is a wide table answered whole, which `(columns …)` cuts.
- `cpu` above `dur` on a span is the garbage collector working alongside; a run that allocates a frame per candidate and a set per select shows it on big scans.

The browser side is `performance.getEntriesByType("resource")` in the capture browser (`go run ./tools/browse --eval`), which gives the request's wall time against the server's `dur`; the difference is the network and the encoding.

For engine work rather than query work, profile the benchmark: `go test ./internal/db -run NONE -bench BenchmarkSidebar -benchtime 60x -cpuprofile /tmp/sidebar.prof -o /tmp/db.test`, then `go tool pprof -top -cum /tmp/db.test /tmp/sidebar.prof` and `-peek` on `holds`, `readable` and `columnReadable`. `BenchmarkSidebar` is the rail's two queries as a parent over the synthetic school in `internal/db/scale_test.go`, sized by `scaleFamilies`; `BenchmarkEveryPerson` and its neighbors time whole-table reads and a write's rebuild. The profile is where the per-row machinery shows, string-keyed caches, clock reads in `holds` and `check`, and garbage, none of which a query rewrite reaches.

## Measuring a change

Single traces are not enough. Two runs of the same query against separate server processes differ by tens of milliseconds, and across a deploy by more, so a change smaller than that is invisible in one trace and a change that looks like a win in one may be noise. What has held up:

- **Send the page's real batch.** The batch is the page's `loadModel` queries with the rail's conditions expanded, as `web/who/state.js` and `web/loop/state.js` build it; capture it from the page (`navQueries` and the page's own queries in `web/common/rail.js`), not from memory, since the queries change. A tool that sends a batch file is a one-off under `local/<name>/` (`AGENTS.md`, Code), reading the `Trace` header of each answer and printing each query over some threshold.
- **Interleave and take medians.** Run the before and after batches in alternating rounds against one server, five rounds at least, and compare medians of the whole `request` and of each named query. Compare the two states against the same server process; a definition change needs the old definition's body written inline into the before batch, since the server holds only the new one. Nothing else runs on the laptop meanwhile: a sample-server capture started during the rounds doubled some of them.
- **Measure the cost per evaluation before shrinking candidates.** A one-query batch over the whole table, `(from GROUP @g (where (manages @g)) (limit 1))`, gives a condition's cost per row from its `scan` time less its `policy` tally. On the laptop `manages` is about 4 µs a row, a two-probe membership `exists` about 2 µs, `visible` 6 to 8 µs. When a scan already has few candidates, that is fixed cost, frames, the probe set built again per candidate, guarded cell reads and their tallies, and a cheaper lookup changes nothing: a lookup of an effective membership by its derived ID left `visible` where it was.
- **Laptop first, production second.** `eval "$(go run ./tools/devenv)" && go run ./tools/startserver --real --run <command…>` serves production's sheets on the laptop, runs the command against it and shuts down, one foreground command with no server to start or stop by hand; the command's first request builds the effective members, so send one warming request before the timed ones. The laptop is several times faster than production, and the ratio differs by machine; measure it once on the same batch and convert, but a change counts only once measured on production, through `tools/q` with `--spoof` for the parent. Ignore the first request after a deploy, which is instance warm-up.
- **As the owner and as a parent.** Pick a parent with no admin role: the first by address among the Parents group's members outside every admins group. Row counts as the owner come cheaply from the Heliosian MCP's `helios_query`, which runs as the person connected; a count for a parent is `tools/q --spoof`.
- **Same answers.** A speed change keeps every answer as it is unless it says otherwise. Compare the rows answered, not just the count, and read the page: `timeout 20 go run ./tools/startserver --capture <url> --wait <selector> --out local/screenshots/<name>.png`, one capture per run, whose log lists every query the page sent (`docs/screenshots.md`). Who?'s directory, a group page, Loop's front page and a Loop group page are the four that exercise the rail.
- **Say what is left.** After each change, list the named queries still over a few milliseconds on production and what each is paying for, in the terms above: a fused select, a whole-table read check as a parent, per-row redaction, encoding. The next change comes from that list, not from the profile's biggest function.

## Mistakes to not repeat

- Putting a path, an `and` or any other non-probe among an `or`'s branches: the whole `or` stops probing and reads the table. Keep every branch a probe, or move the rest out of the `or`.
- Treating a definition as free because it is a name. A definition is expanded where it stands and costs what its body costs; calling one before the cheap and membership tests calls it on every row of the table.
- Adding a `select` with no probe to a page's query and reading the laptop's owner numbers. The pass it adds costs the table's size as a parent, and the laptop hides it.
- Measuring as the owner only. The owner's read checks stop at the first gated clause; a parent's reach the membership clauses on every row.
- Trusting one trace. Take five interleaved rounds and compare medians.
- Loading rows for a flag. "Is the viewer in this group" is answered by the viewer's own membership rows, never by reading the group's.
- Moving a browser filter to the server without reading the browser's filter first. The browser may resolve what the row lacks (a date through its parent) and the server form has to leave those rows to it.
- Calling a laptop number a result. Production is the measurement; the laptop is the search.
- Letting a query's cost hide in another query of the batch. The first query to call a definition, to need a fused select on a table, or to walk a table whole pays for it; reading per-query times without that in mind blames the wrong query.
- Optimizing the select a slow query names instead of the pass it shares. The fused pass costs what its least-filtered select costs, which may sit in a different query.
- Shrinking a scan's candidates without first measuring its cost per evaluation. Few candidates and microseconds per row means the fixed cost is the problem, and the fix is in the engine's per-row machinery, not the lookup.
