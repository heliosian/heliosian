# Storage

Every app keeps its data in Google Sheets and the media and mail buckets, holds it in memory, and changes it one way. There are five layers, each reached only through the one below it:

1. **IO** (`internal/data`, `internal/blob`) - reads and writes a spreadsheet tab or a bucket object, and nothing else.
2. **Book** - one per spreadsheet: its tabs, and rows changed only as planned operations - matched against a set of tables, cascaded, turned into IO writes and Change Log rows - and then written. It knows nothing of a model.
3. **Store** - one over every spreadsheet: each sheet's tables as last read and the one model built from them, held in memory, and `Commit`, which plans a change through the sheet's book, rebuilds the model from the result, and writes it only if the model accepts it.
4. **Model** - one part per spreadsheet, each a pure function from its sheet's tables, and the parts it reads, to its piece of what the pages serve. It refuses tables that break the app's rules.
5. **Hooks** - what else happens when a tab changes, registered with the store: cascades inside a commit, side effects after one.

No handler, background loop, mail hook, import or tool writes a tab or an object any other way.

## IO

A tab is a header row and records keyed by column name; a cell's position in the row is never part of the contract, so columns may be rearranged, and added, by hand. The operations:

- **Read** a spreadsheet's tabs in one batched request (`Tabs`), header-only for the tabs nothing reads rows of.
- **Insert** rows, each cell under the column of its name, at an explicit address after the last used row - never the Sheets append call, whose table detection starts a row in the wrong column past a blank row.
- **Update** the named cells of every row matching the given columns; no row matching is an error. **SetMany** updates many rows keyed by one column in one write, with the same error for a key no row holds.
- **Upsert** is Update, inserting one row when none matches.
- **Delete** every row matching the given columns; no row matching is an error.

A row matches when each named cell equals the given value after trimming both and ignoring case (`data.Matches`). The store's memory half uses the same rule, so a write that changed memory finds the same rows in the sheet, and a sheet write that matches nothing means the two have split.
- **Sync** a tab to a list of rows, cell by cell: `tools/sheets sync`.

Every request goes through one retry of a quota refusal (`call` in `internal/data/sheet.go`). A column the operation names that the tab lacks is an error, from the sheet and from the CSV fake (`data.Dir`) alike. The schema operations - `Layout`, `AddTab`, `AddColumns`, `DropColumns`, `RenameTab` - live here too, and `internal/data` is the only package that talks to the Sheets API: every tool reaches a sheet through it.

`internal/blob` is the only package that talks to Cloud Storage, through two types. A `blob.Bucket` (`blob.Open`, one per bucket: `MediaBucket` and `MailBucket`) is plain objects - `Get`, `Put`, `Exists`, `Remove` - with no caching, and `PutMedia`, which writes an image's thumbnail and then the image, so an image in the bucket always has its thumbnail; the image search's records and stock pictures, Helios Ask's documents, Loop's mail archive and the bulk tools go through it. A `blob.Store` (`blob.New` over the media bucket) is the served media: `Put` writes content-addressed media through `PutMedia` and holds it, `Has` and `Prefetch` fetch what the sheets name, keeping each image's thumbnail in memory for good and the full object in a cache bounded by bytes (`internal/lru`), `Bytes` answers from that cache, reading the object again from the bucket when the cache has dropped it, and the app routes serve from there; Who?'s classroom and grade tiles are among it. Which folder holds each app's uploaded pictures is one table, `imageFolders` in `internal/blob/images.go`; the served folders, each app's folder route and its upload folder all come from it. A `blob.Images` (`blob.NewImages(store, apps...)`) is an app's pictures: a name under one of those apps' folders is the store's, anything else a file bundled under `web/<app>/` or `web/public/<app>/`, and it is both the loaders' `blob.Checker` and the share cards' `Read`. When is built over its own, Celebrate's and Team's, since a linked event wears its party's or activity's picture. Every object goes up through one upload call (`gcs.put`). An object is written before the commit that names it, outside the store: an object nothing names is harmless, and a row naming no object is the fault the loaders refuse.

## Store

`internal/store` is the store. `store.Store[M]` holds every spreadsheet's tables and builds one model `M` from parts. A `store.Part` is one spreadsheet - its book: each tab's name, the columns it must have, the columns that key a row (for the Change Log), and its cascade hook if it has one - the function that builds its piece of the model, the parts whose pieces that function reads (`Reads`), and what to log when it loads. `internal/model` declares the parts (`parts` in `internal/model/model.go`) and the one `model.Model` they fill, a field per sheet - `Config`, `Directory`, `Invites`, `Calendar`, `Parties`, `Activities`, `Birthdays`, `EmailLists`, `Home`, `Feedback`, `Documents` - with what reads across them as `Model` methods (`LinkedEvents`, `Audience`, `MagicTagsOf`, `HomeCategoriesFor`, `AdminList`, ...). The calendar's part reads the directory's (its roster), and Staff Birthdays' reads it too (which staff have a birthday). `store.New(parts, consent, source, writer, queue)` reads every part's spreadsheet, checks every tab's columns and the Change Log's, and builds the parts in the order their reads need, or refuses to start. After the parts, every build runs the `consent` step once over the whole model, on the load and on every staged change, and a consent step that fails refuses the change as a part would; the data model's decides what may be shown to people (`docs/datamodel.md`, Consent step), and the old model's does nothing. A sheet whose every tab of its own is append-only (below) writes no Change Log rows, so reads no Change Log either: the association's shared birthday sheet is one (`docs/birthday/data.md`). No app has a degraded mode for a sheet that will not load, and nothing checks for a missing model: a new revision that cannot load never takes traffic, the running one keeps serving, and a refresh that fails keeps the model it has. A tab may belong to another spreadsheet the app only reads - Who?'s consent-form responses - and is then read with the rest and never written: a commit naming it is refused, and it has no Change Log of its own.

A change is stated as operations on rows - `store.Insert`, `store.Upsert` (every matching row, or a new one when none matches), `store.Update` (every matching row, and nothing when none does), `store.Delete` - built by the owning package's `writes.go`, which decides whether the actor may make it (`docs/dev.md`, The rules live with the thing), and handed to `Commit(ctx, actor, sheet, ops...)`, naming the sheet they are for, the actor an `access.Actor` whose address the Change Log records. A commit has two halves that never wait on each other. Under the one commit lock, on `store.Queue`, it:

1. matches each operation against the tables as they stand, which gives the rows' previous values, and drops any that change nothing;
2. runs the cascade hook of every tab a change touched, which adds operations of its own, until none adds more;
3. rebuilds, from the changed tables, the part whose sheet changed and every part that reads it - a part that refuses rejects the whole change, and nothing is written;
4. abandons a refresh under way (below), swaps the tables and model in, and queues the IO writes and the Change Log rows on the one write queue (`store.Queue`);
5. releases the lock and returns.

The queued writes go to the sheet in as few calls as the changes allow (`Book.batches` in `internal/store/book.go`). An insert joins the latest earlier insert into its tab, and a set of one row's cells by its key joins the latest earlier such set on its tab, so every insert into a tab in a commit is one call, and every keyed set one more, however the commit interleaves its tabs. A write moves only earlier, and never past a write it could change the meaning of: on its own tab, an insert stays behind an update or delete that matches the row it adds, and a set behind the insert of its row and behind an update or delete that could reach the same row in a column either touches; on another tab, a write stays behind the insert of any row whose key it names, so a row is never written before a row it refers to and a sheet a write stopped half-way through still loads. Deletes keep their order: back-to-back deletes on one tab, each matching on the same single column, go as one call (`DeleteMany`, which reads the tab once and removes every matching row in one batch), and any other delete is a call of its own. The Change Log rows go last, in one call, once every tab write has. Commits waiting on the queue for the same sheet go together: a sheet has at most one write task queued, and when it runs it takes every commit's writes that have arrived since, in commit order, and batches them as one, so uploads arriving faster than the sheet takes them cost a few calls per drain rather than a few per upload. A commit waiting with `CommitAndWait` is released once the drain holding it is written.

A commit is a transaction of one. `Queue.Transact` holds the lock across several changes, to any sheets: each `Store.Stage(tx, sheet, ops...)` plans its operations against what the transaction has staged in that sheet so far and rebuilds the parts they change, inside the transaction, `Store.In(tx)` reads that staged model, and the transaction swaps the staged model in and queues every sheet's writes, in the order staged, only once all of them have built. A change that fails leaves nothing behind. Work to do once the change is in (`Tx.After`) - mail, logging - runs after the lock is released, and only if it went in. A batch of API writes is one transaction (`docs/api.md`, Writes), as is a copy to the shared birthday sheet, whose rows and marks are two sheets. `Store.Count(sheet, tab, match)` counts a tab's rows matching a set of cells.

Every swap, a commit's or a refresh's, runs the hooks registered with `Queue.OnSwap` under the lock: the API's model is published there, Who?'s geocoder is woken when the directory part changed (Hooks, below), and Staff Birthdays' invite sender is woken (`docs/birthday/birthday.md`). A hook must not commit; one that has work to do hands it to its own goroutine.

The memory half takes milliseconds and waits only on another commit's memory half; the IO half runs on the queue in commit order, and no request waits on it. The queue's one goroutine is the only thing that writes a sheet. Writes to one tab that follow each other go as one request: inserts as one Insert, and sets and updates that each name a row by a single column, and leave that column alone, as one SetMany - so an import that re-classifies every event, or a send that marks a whole guest list, is a handful of requests rather than one per row. An IO write the sheet refuses, the Change Log's included, ends the process there (`logging.Fatal`): memory is ahead of the sheet, and any write queued behind may build on the refused one, so none may run; the sheet keeps an unbroken prefix of what was committed, and the next start reads it. A mail hook - Loop's received mail, Helios When's calendar replies and bounces, the mail Helios Ask files among its documents - is the one caller on a request that waits for its IO: it commits with `CommitAndWait`, which takes the same place in the queue as `Commit` and then waits for that write to finish, never jumping ahead of what was queued before it. So the hook answers the mail provider only once what it took is in the sheet; a refused write ends the process before it answers, and the provider retries. The calendar, directory and documents imports, and Loop's filing of a sent post, wait the same way.

The half of this that is about rows - reading and checking the tabs, planning operations, writing a plan on the queue - is `store.Book`, which the store holds one of for each sheet. A tool that writes rows and serves no model opens the book alone, as Who?'s import does: it reads the tabs, plans its operations, builds the model from the planned tables itself, and writes the plan only if that model loads. Nothing about the sheet as it stood before is built, so a change that is only valid whole - a name Veracross changes and the `Name to Email` entry that follows it - goes through in one plan.

A tab declared `AppendOnly` is a record of events rather than state - Loop's Deliveries, Helios When's Bounces, Who?'s Geocode answers. Its rows are inserted and, through a cascade or by hand, deleted, never edited: the store refuses a Set or Update on one, and makes no Change Log rows for it, since no row ever held a value that another replaced - on a tab nobody edits the Change Log could only hold inserts, which carry nothing the tab does not. A tab whose rows are ever edited is never append-only, however many rows it gets.

The store reads every sheet at startup. After that every sheet is read together, in one refresh: one ticker, every five minutes (`Queue.Tick`), and once more thirty seconds after a start (`deployOverlap` in `internal/app`) - during a deploy the old revision keeps serving and writing while the new one reads, and that second read picks up what it wrote. The five-minute refresh is for what changes in the sheets by hand. A refresh is a task on the write queue: it reads every sheet and builds every part, and the media store's list of what is named, then swaps the whole model and that list in at once, or neither if any read or build fails. A commit that lands while it reads cancels it (the refresh's context), since its write waits behind the refresh on the queue and the sheet just read cannot hold it; the next tick reads again. Work accepted but not yet committed - a mail the documents' hook took, a Loop email list's post being filed - holds the queue (`Hold` and `Release` in `internal/store/queue.go`), so the shutdown drain waits for it.

A model is built from the tables alone, but for one app: Helios Ask's documents are objects in the bucket that the `Documents` tab only names. Its build reads each object a row names, keeping the documents it has read by object name, so a refresh fetches only the rows it has not seen; filing a document puts it in that memo before the commit, so a commit never waits on the bucket. Each load that swaps in - startup and every refresh - cuts the memo back to the documents its model holds, so a document whose row is gone leaves memory at the next refresh. A document filed while a refresh swaps in, ahead of its commit, can be cut with it; its commit then reads it from the bucket once.

## IDs

A row that anything else refers to is keyed by an ID, and every reference to it holds the ID, never a title or a name, so renaming a thing is one cell and nothing chases it. An ID is 13 symbols of lowercase Crockford base32 (`internal/id`), 65 bits; `id.Parse` lowercases and trims, so one typed in capitals still resolves, and refuses anything else. There are two kinds:

- **Minted** - `id.New`, 65 random bits, drawn again while the model already holds the ID or an alias of it. Every row an app creates gets one: parties, tickets, activities, events, groups, charities, tags, links and the rest, each app's `data.md` saying which column holds it. A row added to a sheet by hand needs one written in.
- **Derived** - `id.Of`, an HMAC of the thing's own key under the `ID_KEY` secret (`docs/deploy.md`), for things whose identity comes from outside: a person (their address after Email Aliases), a family, a classroom, a grade, a crew. Nothing stores them; the directory's model computes them on each load. The key never rotates, since a calendar Tags cell holds a classroom's derived ID.

A sheet whose rows once had other IDs has an `Aliases` tab (Alias, ID, `id.AliasColumns`): each earlier ID beside the ID the thing has now. Loaders read only current IDs; aliases are for names arriving from outside - a link, a mailed calendar entry, a stored path - which each app's lookups resolve on the way in, and a page reached through an alias answers 301 to its current address. Loop's `Aliases` tab has the same shape, its aliases being other mail addresses of a group. A friendly address - a party's or an activity's Pretty ID, an event's Address, a group's name, a celebration's code - is refused when it reads as an ID, so the two never collide.

## Order

A row's place in a list the app lets people arrange is its `Order` cell, never its place in the tab: people sort and rearrange the sheet freely. An order is a sort key - lowercase letters and digits, compared as text, never ending in 0 - so there is always a key between any two, one character longer when they sit side by side. Moving a row writes that row's key alone, an ordinary `set` in the Change Log with the key it had. `store.Order` gives keys for rows in the order wanted, keeping every key it can (the longest run already in order) and placing the rest between their neighbours. A blank key sorts after every key, blank rows in the tab's own order, so a row added by hand lands last; it gets a key the first time a move needs it. Anything else in the cell refuses the load.

Heliosian's lists - its Categories, Links, Visibility and Widgets tabs - allow no blank key: their load refuses one, and every row the app writes carries a key, a new one after the last of its list (`keyAfter` in `internal/model/home.go`). A move there is the row's own key, sent as its `order` field in a partial `edit` (`docs/api.md`, Heliosian): the browser picks a key between the moved row's new neighbours (`keyBetween` and `movedKey` in `web/common/order.js`, a port of `between` in `internal/store/order.go`) and the server checks it with `store.CheckKey`.

A list nobody arranges sorts by a real field of its rows instead - a celebration by its start, a ticket by when it was added, a Loop message by when it was received - blanks last. A list an editor saves whole, like a Loop email list's filter rules, is replaced whole in the editor's order whenever it changes.

## Cells

Every app reads the common kinds of cell through `internal/cells`, so the same value means the same thing in every sheet. A yes/no cell is `Yes` or `No` in any case and with any spaces around it, and blank means whatever that column's default is (each app's docs say which); anything else refuses the load. The apps write `Yes` and `No`. A title may not be blank, too long for its app, or have spaces around it. A link is an absolute `http` or `https` address with a host. A date is `2026-09-24` or `2026-09-24 16:00`, an Added cell either or blank. A comma list is split on commas, each item trimmed, blanks and repeats dropped, and written back joined with `, `.

## Hooks

- **Cascade hooks** belong to a tab (`store.Tab.Cascade`) and turn a changed row into more operations, inside the same commit: deleting a Heliosian link or category deletes its audience rows, deleting a Loop email list deletes its managers, rules, messages and deliveries with it, and deleting a Helios When invitation deletes its invites, groups and answers, a guest's address change carrying their answer with it, renaming or deleting a person Who? holds only in Overrides renames or deletes their tags, tag managers and photos, and deleting a Who? tag's row takes its people and managers with it while untagging its last person deletes the tag. Each sees the row before and after, and the tables as the commit has left them so far (Team reads the parent chain there to work out an activity's address), and returns operations; it writes nothing itself.
- **After-commit work** runs once the commit is in memory, off the store: mail a change sends, filing a sent Loop post into Helios Ask's documents, geocoding a new address (`model.Store.Locate`, woken by a swap hook whenever the directory part changed, which commits what it finds). One that changes stored data does it through a commit of its own, to the sheet that owns that data - another app's included.

## Change Log

Every spreadsheet has one `Change Log` tab, written by the store and by nothing else: Timestamp, Actor, Real Actor, Action, Tab, Key, Column, Previous. One row per cell a commit sets or deletes, and one row per row it inserts, cascades included:

- **Action** is `insert`, `set` or `delete`.
- **Key** names the row: each of the tab's key columns and its value, `Email=…; Year=…`.
- **Column** and **Previous** are the cell and what it held before the change. An insert has neither: before it the row did not exist, and its values are in the tab.
- **Actor** is who the change was made as, and **Real Actor** who was signed in, the two differing under Spoof Mode (`docs/toolbar.md`). Work nobody signed in does - the directory and calendar imports (`import`), the documents import (`importartifacts`), Who?'s geocoder (`geocoder`), the birthday reminders, Loop's mailer (`loop mailer`, which also files a sent post among Ask's documents), the mail Ask files (`ask mail`), the invite sweep (`invite sweep`) - names itself as the actor, and Real Actor is empty; a calendar reply or an outside guest's page names the guest.

What a row holds now is the tab itself; the Change Log is how to get back to what it held before. Nothing reads it back.

The data model's five sheets keep their history differently: a part may name a `store.ChangeLog`, the tab its entries go to and how each `store.Change` becomes a row, and the data model's parts name their own `CHANGES` tab (`docs/datamodel.md`, Changes). Its entries are rows like any other: they join the tab in memory in the same commit as the change they record, so the model holds every change the moment it is made, and are written after the commit's other writes, as the Change Log's are. A sheet with a part's own log has no `Change Log` tab of its own to check.

## The sheets

Every spreadsheet an app writes is a part of the one store (`parts` in `internal/model/model.go`): Staff Birthdays, Heliosian, HCA-Team, Helios Celebrate, Helios Loop, Helios When, Who?, Who?'s invite templates and greetings, Helios Ask's documents, Feedback, the platform's Config, and the association's shared birthday sheet. The server runs the one store, `model.Store` (`model.NewStore(source, writer, queue, deps)`), and every tool that reads a model builds the same one, every sheet and every part, so no store is ever partial. Beside it, on the same queue, the server runs the data model's store over the five `Data:` sheets (`docs/datamodel.md`). Helios When's import commits through the store: the server's own for the Google stage, and for the PDF stage the periodic job's own (`docs/when/data.md`, The import). The documents import builds one too (`docs/ask/artifacts.md`), and Who?'s import opens the directory's book (`docs/who/data.md`, Every write is a commit). Staff Birthdays' weekly copy into the association's own spreadsheet (`docs/birthday/data.md`) is a commit to that sheet, an outbound export of rows the app never reads back; a birthday team joiner's place on the app's Heliosian list is a commit to Heliosian's sheet (`model.Store.GrantApp`).

A `Change Log (old)` tab, where a spreadsheet has one, is a change log in an earlier shape that nothing reads or writes.
