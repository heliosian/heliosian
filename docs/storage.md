# Storage

Every app keeps its data in the data model's Google Sheets and the media bucket, holds it in memory, and changes it one way. There are five layers, each reached only through the one below it:

1. **IO** (`internal/data`, `internal/blob`) - reads and writes a spreadsheet tab or a bucket object, and nothing else.
2. **Book** - one per spreadsheet: its tabs, and rows changed only as planned operations - matched against a set of tables, turned into IO writes and `CHANGES` rows - and then written. It knows nothing of a model.
3. **Store** - one over the data model's spreadsheets: each sheet's tables as last read and the one model built from them, held in memory, and transactions, which plan changes through the sheets' books, rebuild the model from the result, and write them only if the model accepts them.
4. **Model** - one part per spreadsheet, each a pure function from its sheet's tables to its piece of the data model (`docs/datamodel.md`, The store). It refuses tables that break the model's rules.
5. **Hooks** - what else happens when the model changes, registered with the store: triggers inside a write, work after one, on a swap and on a tick.

No handler, background loop, mail hook, import or tool writes a tab or an object any other way.

## IO

A tab is a header row and records keyed by column name; a cell's position in the row is never part of the contract, so columns may be rearranged, and added, by hand. The operations:

- **Read** a spreadsheet's tabs in one batched request (`Tabs`), header-only for the tabs nothing reads rows of.
- **Insert** rows, each cell under the column of its name, at an explicit address after the last used row - never the Sheets append call, whose table detection starts a row in the wrong column past a blank row.
- **Update** the named cells of every row matching the given columns; no row matching is an error. **SetMany** updates many rows keyed by one column in one write, with the same error for a key no row holds.
- **Upsert** is Update, inserting one row when none matches; only `tools/sheets set` uses it.
- **Delete** every row matching the given columns; no row matching is an error.
- **Sync** a tab to a list of rows, cell by cell: `tools/sheets sync`.

A row matches when each named cell equals the given value after trimming both and ignoring case (`data.Matches`). The store's memory half uses the same rule, so a write that changed memory finds the same rows in the sheet, and a sheet write that matches nothing means the two have split.

Every request goes through one retry of a quota refusal (`call` in `internal/data/sheet.go`). A column the operation names that the tab lacks is an error, from the sheet and from the CSV fake (`data.Dir`) alike. The schema operations - `Layout`, `AddTab`, `AddColumns`, `MoveColumns`, `DropColumns`, `RenameTab` - live here too, and `internal/data` is the only package that talks to the Sheets API: every tool reaches a sheet through it.

`internal/blob` is the only package that talks to Cloud Storage, through `blob.Bucket` (`blob.Open(blob.MediaBucket)`): plain objects - `Get`, `GetVersion`, `Put`, `Generation`, `Exists`, `Remove`, `List`, `Older` - with no caching. Every write and delete names the generation it expects (`ifGenerationMatch`): `Put` with 0 creates an object and fails if one is there, `Put` or `Remove` with a generation fails if the object has been written since, and either failure is `blob.ErrChanged`, so two writers racing on one object show up as an error rather than one silently undoing the other. Every object goes up through one upload call (`gcs.put`), and `GET /api/blob/{id}/{column}` serves a stored byte from it (`docs/datamodel.md`, The query API). An object is written before the commit that adds the `CONTENT` row naming it, outside the store: an object nothing names is harmless until the sweeper removes it, and a row naming no object is the fault the loaders refuse.

## The media bucket

Every object the server keeps is in `blob.MediaBucket`, under one top-level folder for each kind of object; Helios Admin's dashboard (Data) gives each folder's objects and bytes, and `gcloud storage ls gs://heliosian-media/` lists the folders.

- `content/` holds every stored byte: each object named by the SHA-256 of its bytes in hex, with no extension, and named by the `blob` of every `CONTENT` row over those bytes, whose `mime` is its type. A document's and a mail's bytes and a document's thumbnail, a photo's original, re-encode, crop and thumbnail, a recording and the M4A made from it, a flyer as uploaded and its re-encode, a report's screenshot, and an image search hit's preview and picture are each a `CONTENT` row that a row's reference column names (`docs/datamodel.md`, Documents). Whatever stores bytes no `CONTENT` row of that hash and type holds writes the object before the commit that adds the row, and writes nothing when one does; the content sweeper deletes a `CONTENT` row nothing refers to, and on each tick removes every object under `content/` no row names that is more than `orphanAge` old (`internal/db/sweep.go`; `docs/datamodel.md`, Documents), so a picture or recording a newer one replaces, whose row is deleted, or whose write never committed leaves the bucket.
- `search/` holds the search maker's entries, each named by the SHA-256 of the text it was made from, with `.json` (`SearchObject` in `internal/db/search.go`); the searcher deletes the entries no row's text wants any more.

Only the content sweeper and the searcher delete objects.

## Store

`internal/store` is the store. `store.Store[M]` holds every spreadsheet's tables and builds one model `M` from parts. A `store.Part` is one spreadsheet - its book: each tab's name, the columns it must have, the columns that key a row, and the change log its changes go to - the function that builds its piece of the model from its own spreadsheet alone, and what to log when it loads. `internal/db` declares the parts (`db.NewStore` in `internal/db/store.go`), one per `Data:` sheet. `store.New(parts, finish, check, source, writer)` reads every part's spreadsheet, checks every tab's columns and the change log's, and builds the parts, or refuses to start. After the parts, every build runs the finishing step once over the whole model, on the load and on every staged change - the data model's consent step, which decides what may be shown to people (`docs/datamodel.md`, Consent step) - and a finishing step that fails refuses the change as a part would. A sheet whose every tab is append-only (below) writes no change log rows, so reads no change log either. No app has a degraded mode for a sheet that will not load, and nothing checks for a missing model: a new revision that cannot load never takes traffic, the running one keeps serving, and a refresh that fails keeps the model it has.

A change is stated as operations on rows - `store.Insert`, `store.Update` (every matching row, and nothing when none does), `store.Delete` - which the data model's writes build (`internal/db/writes.go`) after deciding whether the writer may make them (`docs/datamodel.md`, Permissions), and staged inside a transaction. `Store.Transact(ctx, actor, func(tx))` holds the store's one commit lock across every change it stages, to any sheets, the actor an `access.Actor` whose address the change log records. Each `Store.Stage(tx, sheet, ops...)`:

1. matches each operation against the tables as the transaction has staged them so far, which gives the rows' previous values, and drops any that change nothing;
2. marks the sheet's part, and every part that reads it, to be rebuilt the next time the transaction's model is asked for.

`Store.Built(tx)` rebuilds the parts the staged sheets change, inside the transaction, and `Store.In(tx)` reads that staged model; a part that refuses fails the transaction, and nothing is written. A plan copies a tab only when an operation changes it, so a data model part rebuilt for a staged change keeps the built rows of every table whose stored rows are the very slice they were built from, and runs only the sheet checks that read a table it built again (`sheetChecks` in `internal/db/store.go`): a write to `STOCK` builds `STOCK` and leaves the Documents sheet's `DOCUMENT` rows, by far its largest table, as they were. At the end the store's check hook runs over everything the transaction changed, then the transaction swaps the staged tables and model in and queues every sheet's IO writes and change log rows on the store's one write queue (`internal/store/queue.go`), in the order staged, and releases the lock. A build or check that fails refuses the transaction; a change that fails leaves nothing behind. Work to do once the change is in (`Tx.After`) - mail, logging - runs after the lock is released, and only if it went in; `Tx.Swapped` runs under the lock, right after the swap. `Transact` answers a channel that closes once the transaction's writes are in the sheet.

The queued writes go to the sheet in as few calls as the changes allow (`Book.batches` in `internal/store/book.go`). An insert joins the latest earlier insert into its tab, and a set of one row's cells by its key joins the latest earlier such set on its tab, so every insert into a tab in a transaction is one call, and every keyed set one more, however the transaction interleaves its tabs. A write moves only earlier, and never past a write it could change the meaning of: on its own tab, an insert stays behind an update or delete that matches the row it adds, and a set behind the insert of its row and behind an update or delete that could reach the same row in a column either touches; on another tab, a write stays behind the insert of any row whose key it names, so a row is never written before a row it refers to and a sheet a write stopped half-way through still loads. Deletes keep their order: back-to-back deletes on one tab, each matching on the same single column, go as one call (`DeleteMany`, which reads the tab once and removes every matching row in one batch), and any other delete is a call of its own. The change log rows go last, in one call, once every tab write has. Transactions waiting on the queue for the same sheet go together: a sheet has at most one write task queued, and when it runs it takes every transaction's writes that have arrived since, in order, and batches them as one, so writes arriving faster than the sheet takes them cost a few calls per drain rather than a few per write.

Every swap, a transaction's or a refresh's, runs the hooks registered with `Store.OnSwap` under the lock. A hook must not write; one that has work to do hands it to its own goroutine. The data model's workers wake on its committed triggers instead (`docs/datamodel.md`, Triggers), which a refresh runs for the rows it changed (`Part.Refreshed`).

The store also ticks, every `tickInterval` (`Store.Tick` runs it beside the refresh, `Store.OnTick` registers a hook), for what no write announces: a send that failed and is owed again (Helios When's and Staff Birthdays' senders, the fetcher), work that falls due with the date (Staff Birthdays' invites), search's full pass over every row, which catches what its incremental pass misses, and the content sweeper's pass over `content/`, which removes the objects a write stored and never committed a row for.

The memory half takes milliseconds and waits only on another transaction's memory half; the IO half runs on the queue in order, and no request waits on it. The queue's one goroutine is the only thing that writes a sheet. An IO write the sheet refuses, the change log's included, ends the process there (`logging.Fatal`): memory is ahead of the sheet, and any write queued behind may build on the refused one, so none may run; the sheet keeps an unbroken prefix of what was committed, and the next start reads it. A mail hook answers the mail provider once its transaction is in the model, its sheet writes queued; the school mail's hook also holds the queue while it files (`Hold` and `Release` in `internal/store/queue.go`), so a revision shutting down drains what it took.

The half of this that is about rows - reading and checking the tabs, planning operations, writing a plan on the queue - is `store.Book`, which the store holds one of for each sheet.

A tab declared `AppendOnly` is a record of events rather than state - the data model's `GEOCODE` answers. Its rows are inserted and deleted, never edited: the store refuses an Update on one, and makes no change log rows for it, since no row ever held a value that another replaced. A tab whose rows are ever edited is never append-only, however many rows it gets.

The store reads every sheet at startup. After that every sheet is read together, in one refresh: one ticker, every `refreshInterval` (`Store.Tick`, `internal/store/store.go`), and once more thirty seconds after the server starts listening (`deployOverlap` in `internal/app`) - during a deploy the old revision keeps serving and writing while the new one reads, so the start can read a transaction half-written (a row appended to one tab, the cell naming it not yet set on another), and a later read picks up what it wrote. The workers that write or delete on their own - the photo worker everywhere, and in production the consent import, search maker, Google Calendar watch, extractor, classifier, digest, fetcher, thumbnailer and content sweeper - start only once a refresh after the start has swapped a model in (`Store.Refreshed`); one that fails doesn't count, so they wait for the next. The ticker's refresh is a safety check for what changes in the sheets by hand. A refresh is a task on the write queue, so no sheet write runs while it reads, and every transaction whose write has not gone out is still waiting in its book. It reads every sheet without the commit lock, replays onto what it read the writes still waiting (`Book.replay`), and builds again only the parts whose read differs from the tables the store held, row for row, on top of the model the store held, so a refresh that finds no sheet edited builds nothing; then, under the commit lock, it replays the writes of the transactions that landed since and rebuilds the parts they change, and swaps the whole model in at once (`Settle` in `internal/store/store.go`). The `refreshed` log line gives how long it held the lock. If any read or build fails, a replayed transaction included - a row added by hand beside one a transaction added, say - nothing is swapped and the model stays as the transactions left it, until a later refresh reads the sheet with those writes in it.

## IDs

A row that anything else refers to is keyed by an ID, and every reference to it holds the ID, never a title or a name, so renaming a thing is one cell and nothing chases it. The data model's IDs, minted and derived, are in `docs/datamodel.md`, IDs. The old sites' IDs, 13 symbols of lowercase Crockford base32, live on only as `ALIAS` rows naming the row each became, so an old link still lands; a friendly address - a slug, a saved search's word - is refused when it reads as one of them (`id.Parse` in `internal/id`, `cells.CheckPretty`), so the two never collide.

## Order

A row's place in a list people arrange is its `order` cell, never its place in the tab: people sort and rearrange the sheet freely. An order is a sort key - lowercase letters and digits, compared as text, never ending in 0 - so there is always a key between any two, one character longer when they sit side by side, checked as a cell with `store.CheckKey` (`internal/db/cell.go`). Moving a row writes that row's key alone, an ordinary `set` in the `CHANGES` tab with the key it had: the browser picks a key between the moved row's new neighbors (`keyBetween` and `movedKey` in `web/common/order.js`, a port of `between` in `internal/store/order.go`) and sets it through `POST /api/q`, as Heliosian's edit panel does for its widgets, apps and links (`docs/home/data.md`, Ordering). `store.Order` gives keys for rows in the order wanted, keeping every key it can (the longest run already in order) and placing the rest between their neighbors; the Veracross import orders what it adds that way. A blank key sorts after every key, blank rows in the tab's own order, so a row added by hand lands last; it gets a key the first time a move needs it.

A list nobody arranges sorts by a real field of its rows instead - a celebration by its start, a ticket by when it was added, a Loop message by when it was received - blanks last.

## Cells

What a cell holds is its column's kind, checked on every load and write (`docs/datamodel.md`, Cells); `internal/cells` holds the readings the kinds share - a yes/no cell, a link, a moment, a comma list, a friendly address.

## Change log

Every data model sheet has a `CHANGES` tab, written by the store and by nothing else: one row per cell a transaction sets or deletes, and one row per row it inserts, triggers included, naming who it was made as and who was signed in, the two differing under Spoof Mode (`docs/toolbar.md`), and what the cell held before (`docs/datamodel.md`, Changes). A part names it as its `store.ChangeLog`: the tab its entries go to, its columns, and how each `store.Change` becomes a row. The log is written and never read: the load checks its header, a transaction appends its entries after its other writes, and no model holds them. What a row holds now is the tab itself; the change log is how to get back to what it held before.

## The sheets

The server runs one store over the five `Data:` sheets (`docs/datamodel.md`), on the one write queue, and every tool that reads the data model builds the same one, every sheet and every part, so no store is ever partial. Who?'s consent-form responses are read straight from the `Preferences` sheet by the consent import (`internal/db/consent.go`), outside the store, and never written. Staff Birthdays' weekly copy into the association's own spreadsheet is a write straight to that sheet's tab, outside the store: rows the app never reads back (`docs/birthday/birthday.md`, The weekly copy).
