# Data model

The tabs, columns, and validation rules are in `internal/calendar`; this file carries only what reading that code cannot tell you.

The calendar's data lives in one Google Sheet, `Calendar`, in the community shared drive, reached through drive membership like the other sheets. `CALENDAR_SHEET` names it, and `cmd/createtabs` reads that variable to lay it out from an empty spreadsheet titled `Calendar`.

## Tabs

- `Google Import` — Key, Start, End, Title, Location, Description, Updated, Sequence. A mirror of the school's public Google Calendar, one row per event instance, written only by the import.
- `PDF Import` — Key, Year, Start, End, Title, Day Type, Tags, Marker, PDF. What the import reads out of the school's published year calendar: one row per line of its Important Dates list and one per shaded day cell in its month grids, written only by the import. Marker is `First Day` or `Last Day` on the two days that bound a school year. PDF is the hash of the document and of the reading that produced the row.
- `Events` — Event ID, Start, End, Title, Location, Description, Tags, Day Type, Keywords, Added By, Added, Source, Sharing, Status, Image. Hand-added events no import carries - from Admin Tools' Add Event, from anyone's Add Event under the day, by hand, or written by a tool of your own, as the after-school clubs are. Sharing is who can find the event (`calendar.md`, Who can see an event): `Public`, on the calendar for everyone; `Link`, for anyone with its link; `Invite Only`, for whoever is on its guest list; blank reads as Public, and any other word refuses the sheet. An event that is not Public may carry no tags at all, being for whoever is sent it. Status is a public event's approval: Pending until an admin approves it, Approved, or declines it, Declined - either way the row stays; Cancelled for one its host called off, on nobody's calendar but found as its Sharing allows, which may carry no tags either; blank is on the calendar, and is what a Link or Invite Only event carries, needing no approval. Image names an upload in the shared blob store (`category-images/…`, as a category's does) the event's page wears; every model load asks the store for it, as for the tags' pictures and the invitations' flyers, so every instance serves it, and one that names nothing is logged and left. Source is the row's proof: a web address, which the event's page links to (the Veracross clubs page, say), or any words, shown as written. Event IDs are minted like the volunteer portal's, eight characters from a 32-symbol alphabet.
- `Enrichment` — Event ID, Tags, Day Type, Keywords, Input Hash, Model, Enriched. What Claude concluded about each imported event, written only by the import.
- `Overrides` — Event ID, Title, Start, End, Location, Description, Tags, Day Type, Keywords, Hidden, Note. Hand corrections to any event in the three tabs above. Blank keeps, `-` clears. Hidden `Yes` drops the event from every view. Which columns a row touches, and its Note, are shown to calendar admins on the event's page, where they can also set the Keywords cell (`calendar.md`).
- `Settings` — Email, Classrooms, Categories, Saved, Home Name, Home Emoji, Home Position. One row per address. Classrooms, Categories and Saved are a view saved earlier from the calendar's filter card, which stands in for the calendar's own defaults as that person's My Heliosian (`calendar.md`; the card no longer offers to save one, and forgetting empties the three cells). Home Name, Home Emoji and Home Position are what the person calls My Heliosian, marks it with, and where it sits among their saved calendars (`Feeds`, in the sheet's order) - 0 first - blank for the given name, no mark, and first. Whichever calendar is first is the person's default: the one the calendar opens to and Heliosian's Upcoming Events are read under.
- `RSVPs` — Email, Event ID, Answer, Answered, Answered By, Via. Each person's word on each event they answered: `yes`, `no`, `maybe` or `hidden` (`calendar.md`). One row per pair, replaced on each answer, removed when cleared. Answered By is who gave it - the person themselves, a parent for a child in their household, a host correcting it - and Via how: `page` from a page here, an outside person's own or Heliosian's cards, `calendar` from the reply a calendar app sent to the invite; Answered is when. Email is a guest's key (`guest-…`) for a guest named on a guest list without an address.
- `Invitations` — Event ID, Hosts, Audience, Guests, Message, Created By, Created, Sent, Title, Start, End, Location, Description, Flyer, Notify, Stepped Down, Hide Hosts. One row per event with a guest list (`calendar.md`, Invitations), made when a host first adds someone or saves the settings; the Event ID is an `Events` row's, or a party's as the calendar names it (`celebrate/{party id}`). Hosts are co-hosts by address beyond the event's own, comma-separated; Audience is unused since the picker's rework (kept for the rows that have it); Guests is no longer read - invitees may always bring guests - and kept for the rows that have it; Message the hosts' words on the invitation; Sent when the invites first went out, blank while the list is a draft. Who reads who is coming is not a setting: everyone who can open the event does (`calendar.md`, Who can see an event); the production sheet's Guest List column is unread and can be dropped. A row is deleted, with the event's Invites, Invite Groups and RSVPs rows, when a host deletes the invitation before sending. Title, Start, End, Location and Description are a party's invitation's own words in place of the party's, each blank for the party's; Start and End as the `Events` tab writes a moment, a Start the sheet cannot read dropped with a log line. Flyer names a picture shown whole on the invitation - an upload (`category-images/…`) or a bundled file. Notify is the hosts, comma-separated, who asked to hear by email as answers come in. Stepped Down is the address of whoever added a hand-added event, once they stepped down as its host (`calendar.md`, Invitations); blank while they host it, and a hand change to the event's Added By puts the new address in charge whatever this says. Hide Hosts is `Yes` while the hosts keep the event page's Hosts card to themselves, blank otherwise.
- `Invites` — Event ID, Email, Name, Guest Of, Via, Added By, Added, Sent, Token, Household, Opened. One row per person on an event's guest list: Email is their directory address, an outside address, or a guest's key; Name is kept for anyone the directory does not hold; Guest Of is the invitee who brought a guest; Via is how they came to be on it (`search` from Add Person, `outside` from Add Non-Helios, `group:<group id>` from a group, `guest` brought by an invitee; older rows may carry `family`, `classroom:<name>`, `list:<name>` or `tickets`); Sent when their invite went out, blank until it has - and the household of anyone whose row is sent has the event on their calendar. Token is the secret in an outside person's own page, `/ext/{token}` (`calendar.md`, Invitations) - 24 characters minted like a feed's when someone the directory does not hold is put on the list, blank for everyone it does; delete the cell to cut the page off. Household groups people from outside into a family: the address of the one they were added with, on each of theirs (a member named with no address is keyed like a guest); blank for anyone the directory holds, whose household is the directory's. Opened is when they first opened the invitation - the event's page, or their page from outside - written once by the app; mail opens are not read.
- `Bounces` — Email, When, Reason. One row per address the mail provider reported undeliverable (`POST /hooks/events`, a permanent failure), written by the app; the address then wears a warning on every guest list it is on (`calendar.md`, Invitations) until a host changes it. Delete a row to clear the warning.
- `Invite Groups` — Event ID, Group ID, Auto, Added By, Added, Sent, Removed, then a rule's cells as every app's rules tabs hold one: Kind, Roles, Search, Classrooms, Grades, Tags, Family (`internal/filter`; `docs/loop/data.md` reads them out). One row per group on an event's guest list (`calendar.md`, Invitations): Kind is always `include`, its tags read for the event's hosts (`docs/loop/loop.md`, A rule discloses the tags it names); Auto `Yes` or `No` (blank is Yes), whether newcomers who match are sent their invite as they come - they go on the list either way; Sent when everyone the group put on had been sent their invite, written by the first send that leaves none of them unsent, blank until then - and while blank, a newcomer lands unsent whatever Auto says; Removed is the addresses, comma-separated, the host took off the list after this group put them on, whom it does not put back. The people a group added carry `group:<Group ID>` as their Via in `Invites`.
- `Tags` — Tag, Description, Group, Default, Image. The vocabulary events are filed under, and the toggles a viewer has. The description is the definition the classifier is given, so an admin adds or rewords a tag without a deploy and the next import re-classifies against it. Group is the line of the filters the tag sits on - groups in the order their first tag has in the tab, a tag with no group on a plain line at the end - and Default is whether the tag starts on for someone who has not chosen - anything but `No` is on, so a blank column starts everything on. Image is the picture an event under the tag wears across the top of its page when it has none of its own - an uploaded object (`category-images/<hash>.<ext>`) or a file bundled under `web/calendar/` - resolved once per model load and dropped with a log line, never a refusal, when it names nothing. Group, Default, Image, Description, the row order and new rows are what Admin Tools writes to this tab (`calendar.md`); the built-in tags sit on `Other`, so a tag given that group joins them.
- `Day Types` — Day Type, then a start and end for each of the four blocks a day can have: Dropoff, School, Pickup, Aftercare. Hand-authored, since no source publishes bell times. A block with both cells blank does not happen that day, so `No School` is a row with nothing in it.
- `Day Overrides` — Date, Classrooms, Day Type, Note. Hand corrections to the day plan; blank Classrooms means every classroom.
- `Admins` — Email.
- `Feeds` — Token, Email, Name, Classrooms, Tags, Created, Emoji. The saved calendars people have kept from the calendar page or the Feeds page (`calendar.md`), one row each, each also a personal feed address: the token is the secret in the address, Email whose it is, Classrooms and Tags the filter, blank meaning every one, Emoji the mark the owner gave it for the rail (blank for the calendar icon). Written by the app; deleting a row is how an admin revokes a feed by hand.
- `Change Log` — Timestamp, Actor, Action, Tab, Key, Column, From, To, Real Actor. Real Actor is who was signed in when Actor is who the change was made as, the two differing under Spoof Mode (`docs/toolbar.md`), and blank for the import. Appended by the import with every cell it changes, so an event that moved or vanished can be traced, and shaped so a future notifier can read it; the app appends a row for every feed made or removed.

## Three layers, then two

An event's fields resolve import, then enrichment, then overrides. The import supplies what the source states. Enrichment adds what Claude concluded: its tags join the import's, its day type fills a blank one, its keywords join. An override replaces whatever both supplied.

Tags are one list saying what an event is and who it is for. The who is the narrowest audience as classroom names: a Cospreys CAFE is tagged Condors and Ospreys, a school-wide event carries every classroom, and a family's view matches on the classrooms among an event's tags. The what is the `Tags` tab's vocabulary, a Celebration of Learning, a Community event, Parent Ed, a Trip, a Deadline, or Parents, Staff, or Aftercare, as many as apply, a book club being Community and Parents; a viewer's toggles show an event when any of its tags is on. A tag that is neither a row of the tab nor a classroom the directory has refuses the load, which is why the import classifies against the directory's live classrooms and the tab's live descriptions and re-classifies everything when either changes. An event with no tags matches nobody, and the load reports it as a problem rather than guessing. An event with an audience but no category - classrooms alone - is filed under `Misc`, a tag the load supplies rather than the tab, so it has a toggle like everything else instead of showing whatever the filters say. Keywords never repeat a tag; the load strips any that do.

## Two sources, one event

The feed and the PDF describe the same days in their own words, so the load folds what adds nothing. Events are taken in order of preference - one carrying a year marker first, since the school year's bounds come from the PDF's markers, then the living source, a hand-added row over the feed over the PDF, then the longer span - and each is kept unless the ones already kept say everything it says. An all-day event says one thing per weekday per classroom: the day type it imposes, or its title when it imposes none, over the days it sits on (`Event.Dates`, below) rather than over its written span read afresh. So four one-day feed entries cover the PDF's four-day conference span, the PDF's two kindergarten half days sit inside the feed's four whatever the titles, and the feed's two weeks of MAP Assessment cover the PDF's one span written across the weekend between them, since a weekend is nobody's claim. The test here is the weekday and not the school day, because the feed carries years the PDF has never named - last year, the summer camps - whose entries fold by the same rule. A timed event says its start, end, tags, and title, the title read without case or spacing. What is folded is hidden and counted (`Model.Duplicates`), so the lists, the day plan, and the feeds see one. A span only partly covered, or a different classroom, is a disagreement, not a duplicate, and both stand until an override settles it.

## A load either succeeds whole or refuses

A rule broken refuses the load: a tag no row names, a date that does not parse, two events in one layer giving one classroom two different day types on the same date, an event with no tags, a timed event carrying a day type, which only a whole day can, a feed naming a classroom or tag the sheet does not have. The one disagreement that is not refused is with `No School`, which wins: a holiday the feed also marks as a no-aftercare day, or a conference range that runs across one, is still a holiday. A load error is fatal to the server at startup, as the directory's is; a refresh that fails logs the reason and keeps the last model serving. The import never builds the model: it pulls, writes, and warns about what it itself saw, and `go run ./cmd/loadcheck` is how an operator checks a sheet after an import, as for every other app.

## The day plan

Nothing materializes a school day in the sheet. The plan is computed at load: every weekday between a school year's `First Day` and `Last Day` markers is `Regular` for every classroom; then every all-day event carrying a day type stamps that type onto the dates it spans for the classrooms among its tags, PDF events first, then feed events, then hand-added events, each layer overwriting the one before; then Day Overrides overwrite all of them. Two events in one layer that disagree are a problem, above.

Which days an event sits on is settled once, as `Event.Dates`, and the day plan, the month grid, the day page, Heliosian's rail and Helios Ask all read that one answer. An all-day event carrying a day type describes school days, so one written from one school day to another is the school days between them: a conference week written across a weekend says nothing about the Saturday, sits on nobody's Saturday, and says nothing in the folding above. Everything else is taken at its word: a single day, a span that starts or ends on a weekend, a break, or a day outside the school year, since a range written from a Saturday means the Saturday, and any span with no day type to make, since a trip written from Thursday to Tuesday really does run over the weekend. A Day Override is one date and always lands. `Start` and `End` stay as written, and the feed keeps to them, so a span is one entry in a calendar app rather than a day each.

A viewer's day is one lookup per classroom their students are in, and the blocks come from the type's row. A kindergarten half day is a PDF or feed row tagged Hummingbirds alone, so only Hummingbirds get the shorter day. A day type is data: an admin adds `No Aftercare` or a conference variant as a row and it becomes something an override, an event, or the import can name. Only the four block names are fixed.

The two sources disagree about days often enough that the layering is the point. When the feed says kindergarten dismisses early for four days and the PDF says two, the feed wins because it is the living document, and a Day Override settles it once someone asks the office.

## School years and keys

A school year turns over on the first of July, so a July tuition deadline and June's last day of school belong to the same year. A `PDF Import` row's Year must be the school year of its start date, and each year present needs exactly one `First Day` and one `Last Day` row or the load refuses. A year with no PDF rows has no plan at all rather than a guessed one.

Feed keys are the feed's own UIDs, with an instance of a repeating event keyed as the UID plus its original start. PDF keys are the year, the date, and a slug of the title. Event IDs are unique across all three tabs, and an override or enrichment row naming an id no tab has is skipped and counted (`Model.Skipped`) rather than refused, since feed events vanish when the school cancels them.

## The import

The import is `internal/calendarimport`, two stages sharing the classifier and the sheet sync and never touching each other's rows. The Google stage runs in the serving binary, as the school's calendar changes and every hour besides (Keeping up, below). The PDF stage is the periodic sync job, `go run ./cmd/periodicsync` (dry run with `--dry-run`; `docs/dev.md` lists what it needs: `CALENDAR_SHEET`, `DIRECTORY_SHEET`, `PREFERENCES_SHEET` and `CONFIG_SHEET`, the same impersonated credentials as every other tool, and an Anthropic API key in `local/creds/anthropic.key` or `ANTHROPIC_API_KEY`). Either stage builds the audience vocabulary from the directory model first - the server's own, or one the job loads - and `Day Types` must already hold `Regular`, `No School`, and `Early Dismissal` rows, the names the PDF's legend maps onto.

The Google stage:

1. Reads the school's public Google Calendar through the Calendar API as `directory@` - the calendar id is `SchoolCalendarID` in `internal/calendar`, and the API has to be on in the project (`docs/deploy.md`, IAM, says how to check) - asking for single events from the first of July of the previous school year, three years on, so Google expands repeating events to one row each and applies its own overrides of single instances, and nothing downstream knows about recurrence rules. Keys are the events' iCalendar UIDs, an instance of a repeating event keyed as the UID plus its original start, the same keys the public `.ics` feed once gave, so the rows never changed hands. Times arrive with their offset and are written as school wall-clock. All-day ends arrive exclusive and are written inclusive. Descriptions arrive as HTML now and then and are flattened to text, keeping the address behind each link. Only that window is mirrored: a row outside it, and the enrichment of any event the run did not consider, is carried as it is and never removed.
2. Classifies every event whose input hash is new (Classifying, below).
3. Syncs the `Google Import` tab cell by cell through `internal/sheetsync`, mirror policy within the window, and its events' rows of `Enrichment` under the merge policy, which leaves the PDF stage's rows and those of events gone from the calendar as they are; then appends the change log.

The PDF stage:

1. Fetches the school's calendar page, follows its PDF link, and hashes the document together with the prompts that read it. A hash any `PDF Import` row already carries means neither the PDF nor the reading has changed and the rows stand. A new hash reads the PDF in stages, each its own Claude call: the legend, into wording, an estimated color, and a day type per swatch, since the school changes both wording and colors from year to year; the Important Dates list, into entries whose day type comes only from a dismissal note in the wording, because the list's colors are categories rather than day types; and the twelve month grids, one call per month over a crop of the page rendered at 300 dpi with poppler's `pdftoppm`, since the model reads a grid reliably only when its cells arrive large and the API scales a whole page down to about 1500 pixels. Each month is read twice, compared by day type, and read a third time to break a tie; each read must name every day of the month and echo the grid's title, so a lazy answer is impossible by construction and a page laid out differently fails loudly instead of reading the wrong month. The list's entries and the grid's shaded days are two sets of facts and become two sets of rows: an entry says what happens and to which classrooms, a shaded day says what kind of day it is for every classroom, titled with the legend's wording, and nothing merges them. The rows for that school year are replaced and other years' rows are kept, so the current year keeps its plan when the school posts the next year's calendar. These reads run on Claude Fable 5.1 at maximum effort: cheaper settings answered without looking often enough to matter, and the whole PDF costs a few dollars once per change.
2. Classifies every entry whose input hash is new (Classifying, below).
3. Syncs the `PDF Import` tab under the mirror policy and its entries' `Enrichment` rows under the merge policy, and appends the change log.

Classifying, in either stage, sends every event whose input hash is new to Claude in batches of ten, for audience, tags, day type, and search keywords. The hash covers the event's text and dates, the vocabulary, and the classifier's whole prompt, so an unchanged event is never sent twice and a renamed classroom, a reworded tag, or a change to the rules re-classifies everything. The answer is an object with one required property per event, so a skipped or doubled event is impossible by construction, and structured output constrains every term to the vocabulary; ten per call is as many as the schema compiler accepts.

A step that fails does not take the others with it. A PDF that cannot be read leaves the rows already there; a classification batch that fails leaves its events with whatever row they had, and their input hashes see to it that the next run asks about exactly those events again. Everything that did complete is written, and only then does the run report what failed - the job exiting non-zero, the server logging it.

Either stage is idempotent and cheap when nothing changed: one calendar read, or one page fetch and one PDF fetch, and no Claude calls. The calendar is read through the API rather than the public `.ics` feed because Google throttles the feed by client address, which Cloud Run shares with strangers, and refused the job by the hour; the API's quota is the project's own. A `429 Too Many Requests` from the page or the PDF is waited out and asked again, four times over about a quarter of an hour, with whatever `Retry-After` was sent logged beside each refusal, before the run gives up on it. The job runs from a laptop (`brew install poppler` supplies `pdftoppm`) and from its own image, the Dockerfile's `periodicsync` target, a Debian base carrying poppler rather than the server's distroless one - which is why the PDF stage stays a job - and the Cloud Run Job `periodicsync` runs it on Cloud Scheduler's cadence as the same identity as the server; `docs/deploy.md` says how to read the schedule and the recent runs.

## Keeping up

The serving binary keeps the Google Import in step with the school's calendar (`Watcher` in `internal/calendarimport`), on Cloud Run alone: Cloud Run's own `K_SERVICE` variable marks it, so a laptop's real-data server never watches or writes the import. At startup it opens a watch channel on the calendar through the Calendar API, which has Google post to `https://when.heliosian.com/hooks/calendar` whenever the calendar changes, and runs the Google stage once. Each post kicks a run: at once if none is under way, else one more run the moment the current one ends, so any number of changes during a run collapse into that one, which reads the calendar fresh - nothing waits and nothing is missed. A run that changed nothing is a few seconds of Sheets reads and the sync; one that classifies takes as long as its Claude calls. After every run the calendar model is refreshed ahead of its five-minute tick, so a change reaches the pages within seconds of Google's post. Every hour the same run happens unasked, for anything a post missed, and the channel - Google lets one live about a week - is opened afresh once it has under two hours left, the old one closed; on shutdown the channel is closed.

A post carries the channel's token, an HMAC of the session key, which the hook checks before anything else. The token is the same across restarts, so a channel a previous revision left open still passes until it expires, each of its posts one more harmless kick. Google's first post on a new channel says only that it is open and kicks nothing. The channel's id and expiry are in the service log (`calendar watch opened`), since Google offers no way to list channels; every post logs as `calendar changed` with the channel and Google's message number, and every run as `calendar import` with how long it took. `/hooks/` is where every inbound webhook lives, served with no session, each proving its caller its own way (`docs/dev.md`).
