# Data model

The tabs, columns, and validation rules are in `internal/model` (`home*.go`); this file carries only what reading that code cannot tell you.

Home's data lives in one Google Sheet, `Apps`, in the community shared drive, reached through drive membership like the directory's sheets. `APPS_SHEET` names it, and `tools/createtabs` reads that variable to lay it out from an empty spreadsheet titled `Apps`, alongside the directory and config sheets it lays out in the same run.

## Tabs

- `Categories` — Category ID, Title, Emoji, Style, Descriptions, Order. Descriptions is whether the category's widget shows each link's description, or each app's tagline, under its title: `Yes` or `No`, blank being Yes; the title's tooltip holds it either way. A new category's cell is left blank unless descriptions are off, and an edit writes it only when the checkbox changes, so a blank stays blank. `tools/createtabs` adds the column; the load needs it.
- `Links` — Link ID, Title, Description, URL, Image, Category, Visible, Added By, Added, Order. Category holds the category's Category ID.
- `Admins` — Email. Who may edit, beyond the platform super admins (`docs/config.md`).
- `Visibility` — App, Visibility, Emails, Tagline, Name, Order. One row per community app in the registry (`model.Apps`): whether everyone sees it or only its list - the people in its Emails cell and whoever its rules on `Audience` pick out - in the app switch of every app's toolbar, and on the front page's apps section - the name it goes by there and the line under it, and its place in the order. The server adds the row for an app that has none when it starts.
- `Audience` — Thing, Kind, Roles, Search, Classrooms, Grades, Tags, Family. The rules that keep an app, a category, a link or a front-page widget to some people (Rules, below): Thing says which - `app:<key>`, `category:<Category ID>`, `link:<Link ID>`, `widget:<name>` (`when`, `team`, `celebrate`, `school`, `birthday`, `todo`) - and the rest are one filter rule, the columns Helios Loop's `Rules` tab has after its Group. A thing with no rows has none. `tools/createtabs` makes the tab; the load needs it to exist.
- `Widgets` — Widget, Sidebar, Order. The front page's widgets' order, and whether each puts its first items in the rail (`home.md`): Sidebar `Yes` or `No`, blank being No, written only when the checkbox changes. One row per widget (`when`, `team`, `celebrate`, `school`, `birthday`, `todo`, `model.HomeWidgets`, and `category:<Category ID>` for every category but the events section, Rules below), Order its place, a sort key (Ordering, below). The server writes the row, after the last, for any widget without one when it starts, and an edit to a widget still without one writes it after the last too. A Widget the code does not have, or a second row for one, refuses the load. `tools/createtabs` makes the tab; the load needs it to exist.
- `Layout` — Row, Columns. How each row of the front page's widgets is split (`home.md`, Widgets): Row its number, counted from 1 without gaps, and Columns one of `model.RowLayouts` in `internal/model/home.go`. Rows past the last take the first of them. A gap in the numbering, a number used twice, or Columns not among those refuses the load. The edit panel's Layout tab writes only the rows it changes, and deletes rows from the end. `tools/createtabs` makes the tab; the load needs it to exist.
- `To Dos` — Email, To Do, State, Changed. What each person has done with a to-do on the Reminders widget (`home.md`): one row per person and to-do they marked, State `done` or `saved`, the row deleted when they clear it; Changed is when. To Do is the to-do's ID, derived from its email's key and its title (`toDoID` in `internal/model/todos.go`), so a to-do read again under the same title keeps everyone's marks. The marks are each person's own, never a household's. Any other State, or a row with no address or no ID, refuses the load. `tools/createtabs` makes the tab; the load needs it to exist.
- `Change Log` — the store's, one row per changed cell holding what it held before (`docs/storage.md`). Never read back.

## Rules

**The ID is the key.** Categories and links are keyed by their Category ID and Link ID: 13 lowercase Crockford base32 symbols (`internal/id`), minted by the app when an admin adds one, never changed, and unique across both tabs together. A missing or malformed ID, or one used twice, refuses the load. Everything that points at a category or link - a link's Category cell, an `Audience` row's Thing, the front page's edits - names it by ID, so a rename is one Title cell and nothing follows it; titles need not be unique. Deleting a link or category deletes its `Audience` rows with it, and a category its `Widgets` row too, a cascade on the store (`dropLinkAudience` and `dropCategoryRows` in `internal/model/home_cache.go`).

**Visible is Yes or No**, blank being No, read as every yes/no cell is (`docs/storage.md`, Cells).

**Style is `cards`, `tiles`, `events`, `apps` or `apps-grid`**, spelled exactly so, and every category needs one. Every category but the events section is drawn as a widget (`home.md`): `cards` its links as an icon grid, `tiles` its links as a compact list, `apps-grid` and `apps` the community apps as an icon grid and as a list, described with `events` below - the two are one section in two layouts, and every rule below said of `apps` holds of either; while the page is searched, `cards` and `tiles` are drawn as sections of feature cards and compact tiles. Each has a row in `Widgets` named `category:<Category ID>`, written after the last widget when the category is added (or, for one added by hand, when the server starts) and deleted with it; a `Widgets` row naming the events section or no category refuses the load. A blank or misspelled Style refuses the load rather than guessing a presentation, the same stance Visible takes — the front page's shape is a property of the sheet, not of what the renderer happens to fall back to.

**`events` is the one section that holds no links**: Helios When's upcoming events for the viewer, which the calendar supplies (`home.md`). The Style value is what marks the row as the app's own - no other column says so - and at most one row may carry this style, so it is found by that. Its Category ID is fixed, `model.EventsCategoryID` in `internal/model/home.go`: `tools/createtabs` seeds the row ("Upcoming Events" 📅, with an Order key) with it when it makes the tab, and the sample data carries it, so the sheet holds it like any other category and it is renamed, re-marked and moved like one. A sheet without an `events` row refuses the load. No link may name it as its category, and it cannot be deleted - only renamed and moved. **It is not drawn**: the widgets across the page's top (`home.md`) carry what is coming up, so the page, the search and the edit panel all pass it over (`linkCategories` in `web/home/state.js`); the server still loads it and sends it among the `link-categories`.

**`apps` is the other section that holds no links**: the community apps themselves - the toolbar's switch as feature cards, each with its mark and tagline, less any app the Visibility tab keeps from the viewer (`docs/home/home.md`). At most one category carries the style, no link may name it, and a category becomes it, through its Style cell in the sheet, only once its links are gone; the editor's Layout choice moves it between `apps-grid` and `apps`, and a links category between `cards` and `tiles`, never one kind into the other. Unlike the events section it is not required: with no row, the apps are in the toolbar alone. It cannot be deleted from the page, since the editor makes only link categories; a category becomes it again only through its Style cell.

**Visibility is `everyone` or `list`**, spelled so, and App is one of the registry's keys (`model.Apps`, the keys `web/common/appswitch.js` lists the switch by; Heliosian itself is not among them, being the front page and the way home); a second row for one app, or any other value in the Visibility column, refuses the load - a misspelled mode would narrow nothing, silently. A row whose App the running build does not know is logged and skipped rather than refused: a newer build writes the row for an app it carries the moment it starts, and the older build still serving beside it during a deploy must not die over an app it has never heard of. Emails is the list, separated by commas, semicolons, spaces or line breaks, forgiven case and duplicates, read only while Visibility is `list` but kept either way, so the list drawn up for an app is still there after it has been everyone's for a while; the app's rules on `Audience` are the list's other half, whose people are on it beside those named. `list` with an empty cell and no rules shows the app to nobody. Name is what the switch and the front page call the app, and Tagline the line under it; blank, the registry's own stands in for either. Order is the app's place in the switch and on the front page, a sort key (Ordering, below). A blank Name changes nothing in the app itself: each app's own tab title, drawer and login page carry the name its code gives it. This is visibility, never access: a direct link, a bookmark or a shared event page still opens the app to anyone signed in.

**A new app starts out of sight.** The registry is the code's: an app is added there when it is built, and the first server to start with it finds the tab has no row for it and writes one (`discover` in `internal/model/home_routes.go`) - `list`, nobody on it, the registry's tagline, an Order after the last - so a new app shows to nobody until an admin lets people in or switches it to everyone. Until that write lands, and for any row deleted by hand, the page reads a missing row the same way. An admin edits the tab from the front page, on each app's card in the apps section: a pencil opens the app's editor - its mark and address at the top, which are the code's and not for editing, so the window says which app it is whatever it is called; then the name, the tagline, Everyone or Only some people, and under the latter the rules and the people named, picked from the directory - saving through the app's `edit` on `/api/apps` (`docs/api.md`, Heliosian), which sends only what changed; the app's row in the edit panel is dragged to move it in the switch's order (Ordering, below). A long list can be pasted into the Emails cell by hand, live within the five-minute reload. The name and tagline reach every app's link previews too: `internal/app` hands each app its card style (`internal/sharecard`) built on functions that ask the registry at each use, so the preview tags' site name, the about and upcoming cards' title and subtitle, and the tagline set under a wordmark are the registry's, and every card's ETag carries both words, so a chat app that cached a card fetches the new one. A card that wears its app's lockup as drawn (Helios Celebrate's `web/public/celebrate/brand/logo-lockup.png`, from the designer's `Celebrate Logo.png`, and the others with a lockup) shows the lockup's own words in its header, which the registry does not reach.

**An audience is a list of filter rules**, the same rules a Helios Loop email list is made of, read by the same code (`model.Audience`, which Loop's email lists are read through, `EmailList.Members` in `internal/model/email_lists_audience.go`) against the same sources - the directory, and the tags the rules name, read for the admins (`docs/loop/loop.md`, A rule discloses the tags it names). A link, a whole category and an app's list each have their rows on `Audience`: include rules, whose matches are unioned, and exclude rules, whose matches are taken away; within a rule every choice must hold (`Parent` with `Jays` is the parents of Jays students; a student by their own classroom, a parent by their children's, staff by none, a teacher not being in the room they teach - `model.Directory.Facets`); Add family widens a rule's matches by the relatives asked for and the roles then keep their kind, as Loop reads them (`docs/loop/loop.md`, Rule). A rule that says nothing, names a role or relation the filter has no such thing as, or names a tag any way but by its ID (`tag:<id>`, `docs/who/data.md`, Tags are kept by ID) refuses the load, as Loop's would; a classroom or grade the directory has since renamed matches nobody. No rows at all keeps nothing from anyone - or, on an app's list, adds nobody to the people named. A rule's tags are the saving admin's own, or shared with them, to name (`AudienceSources.Writable`, the admins as the editors), and read while one of the admins may read them; a rule another admin wrote naming a tag of theirs is read out in the editor and can be removed but not changed, as in Loop. A category kept to some people goes to them whole, links and all, and to nobody else - a section students may not see is one row's Roles cell, `Parents, Staff` - and a link inside it may narrow further but not widen. The link, category and app editors' **Visibility** - the link's and the app's a tab of its own, beside Details - is the rule editor Loop's email list editor is (`web/common/rules.js`, with `rules.css`): each rule a band reading out its sentence - a Magic Tag's name in it a link to the thing itself, the email list in Loop, the activity in HCA-Team or the party in Celebrate, so it is a click from being changed - opened to its controls - role chips, a search box, Classroom, Grade, Tags and Add family dropdowns, the choices from `/api/classrooms`, `/api/grades?enrolled`, `/api/tags` and `/api/magic-tags` and the roles and relations on `home-settings` (the viewer's own tags, the tags shared with them and their Magic Tags among them, each by the key a rule holds) - with Add include rule and Add exclude rule, how many people each rule touches and who they pick out together (`/api/apps/audience/preview`, sent the thing's Audience key with the rules so a rule already on it passes as a save would) asked of the server as they change; the app's editor is the one above. A save replaces a thing's rows whole, refuses a grade or classroom the directory does not have, and deleting a link or category deletes its rows. An admin is sent every link, every category and every app, the links and categories not theirs marked `forMe: false` and the apps `me.listed: false` (an app's carrying its row too, for the editor), and the page shows those - and the hidden links - to them with a badge after the title saying who it is kept to. The rules themselves go to admins alone: anyone else is sent the sections and links that reach them with their rules emptied, so the page never tells a parent which roles, classrooms or tags a link was kept to (`model.Model.HomeCategoriesFor` in `internal/model/home_cache.go`). This is visibility, never access: the link's address is whatever it is.

**A category must exist before a link names it**, and cannot be deleted while a link still does.

**A category goes by an outline mark, not a picture.** Its Emoji cell (the column keeps its old name) is blank or `icon:<name>` - one of the marks the category editor offers (`categoryIcons` in `web/home/dom.js`, drawn from the shared icon table but for heliosian and when, the apps' own symbol_white exports, masked), drawn in the rail's text colour so it reads on any rail. Blank, or an emoji left from before the marks (still accepted, no longer shown), gets a mark read off the title: school, calendar, chat, or a grid. The editor stores the choice; the sheet can carry it by hand. A link without a picture of its own shows its category's mark.

**Link images are named, and the name must resolve.** An Image cell is either an object under `link-images/` in the media bucket, content-addressed like photos and written by the image picker (an upload, or a picture found through the search - `internal/imagesearch`, shared with HCA-Team - which fetches and stores it the same way), or a path to a bundled file under `web/home/` or `web/public/home/` (the way the sample data ships). A name that resolves to neither refuses the load, because a recorded image with nothing behind it is a bug, not a missing picture.

**A load either succeeds whole or refuses**, the same stance as the directory: the server does not start, or does not refresh, on a sheet that breaks a rule, and never serves a page quietly missing a link.

## Ordering

Categories, links, apps and widgets are ordered by their Order cells, sort keys (`docs/storage.md`, Order), and never by where their rows sit in the tab. Every row has one: a blank or malformed Order refuses the load, and whatever the app writes carries a key. Dragging a category, a link within its category, an app or a widget in the edit panel sends a partial `edit` with `order` alone for the row that moved, the browser working out a key between its new neighbours (`movedKey` in `web/common/order.js`), and writes that row's key alone. A new link or category gets a key after the last of its list, as does a link an edit moves to another category, and the server gives a new app's Visibility row and a missing widget's row one after the last when it starts. A row added to the sheet by hand needs a key written in.
